# Getting Started

This guide will walk you through the basic setup and usage of NestJS CRUD Automator.

## Installation

Version `3.0.2` is the published baseline before the current generated-route work. The source includes an intentional breaking capability boundary for generated service calls and must be released as a new major. Package versions remain owned by release automation, so pin the exact released version your application has verified and review [Migrating to 4.0](/docs/nestjs-crud-automator/guides/migrating-to-4-0).

## Prerequisites

Crud Automator 5.x runs on Node.js `^22.13.0 || >=24.11.0`, the range TypeORM 1 supports. The package is ES modules only. A CommonJS application loads it with `require()` as well, because these Node.js releases load ES modules through `require(esm)`.

Make sure you have the following dependencies installed in your NestJS project:

- `@nestjs/common` and `@nestjs/core` (>=12.3.2 <13)
- `@nestjs/swagger` (>=12.0.0 <13)
- `@nestjs/throttler` (>=6.7.1 <7)
- TypeORM (>=1.1.2 <2)
- class-validator (>=0.15.1 <0.16)
- class-transformer (>=0.5.1 <0.6)
- Lodash (>=4.18.1 <5)

Install peer dependencies if they are not already in your project:

```bash copy
npm install @nestjs/common@^12.3.2 @nestjs/core@^12.3.2 @nestjs/swagger@^12.0.0 @nestjs/throttler@^6.7.1 typeorm@^1.1.2 class-transformer@^0.5.1 class-validator@^0.15.1 lodash@^4.18.1
```

Keep the version ranges in the command, so npm does not pick a future major outside the supported ranges.

### Migration Notes

Crud Automator 5.0.0 moves to the current majors of its peers. NestJS 11, `@nestjs/swagger` 11 and TypeORM 0.3 are no longer supported; stay on 4.x until the application has moved. See [Migrating to 5.0](/docs/nestjs-crud-automator/guides/migrating-to-5-0) for every change in one place.

- Peer ranges are `@nestjs/common` and `@nestjs/core` `>=12.3.2 <13`, `@nestjs/swagger` `>=12.0.0 <13`, `@nestjs/throttler` `>=6.7.1 <7` and `typeorm` `>=1.1.2 <2`. `class-transformer`, `class-validator` and `lodash` keep their ranges. CI tests every lower bound: one consumer smoke job installs each peer at its floor, and the `@nestjs/swagger` job also runs 12.0.0 and the latest 12.x.
- `engines.node` is `^22.13.0 || >=24.11.0`, the range TypeORM 1 declares. Node.js 20 is not supported.
- The package ships one ES module build in `dist`. The `dist/esm` and `dist/cjs` folders and the `require` export condition are gone; `exports` has only `types` and `default`.
  - An ES module application imports it as before, with `moduleResolution` `bundler`, `node16` or `nodenext`: every relative import in the declarations carries its `.js` extension.
  - A CommonJS application keeps `require("@elsikora/nestjs-crud-automator")`, which Node.js loads through `require(esm)`. TypeScript 6 resolves `module: commonjs` without a `moduleResolution` setting as `bundler`, so it reads the types from `exports`; with an explicit `moduleResolution: node10` it reads the top-level `types` field, and TypeScript 6 then needs `"ignoreDeprecations": "6.0"` (otherwise TS5107). Both find the types. TypeScript 6 also defaults `types` to `[]`, so list `"types": ["node"]` when the application uses Node.js globals.
  - Deep imports such as `@elsikora/nestjs-crud-automator/dist/cjs/...` no longer resolve. Import from the package root.
  - An application that runs as native ES modules must type relation properties between entities that import each other as `Relation<T>`. See [Migrating To 5.0: Native ES Module Applications](/docs/nestjs-crud-automator/guides/migrating-to-5-0#native-es-module-applications).
  - CI checks five setups on the packed tarball: an ES module app with `bundler` resolution, one with `nodenext`, a CommonJS app with `node10`, a CommonJS app without `moduleResolution`, and an ES module app built by SWC from extensionless `@`-alias imports. Each is typechecked with `skipLibCheck: false` and run against Postgres on Node.js 22.13.0, 24.11.0 and 26.
- Every peer has an upper bound at the next major. What npm does with a release outside a range depends on the order:
  - Adding Crud Automator to a project that already has such a release fails with `ERESOLVE`, and nothing is installed.
  - Upgrading a peer of an existing installation to such a release, for example `npm install @nestjs/common@latest`, succeeds with exit code 0. npm only prints `npm warn ERESOLVE overriding peer dependency`, and `npm ls @nestjs/common` then reports the package as `invalid`. Check the tree with `npm ls` after upgrading a peer.
  - Package managers that do not enforce peers install either way and print an unmet peer warning.
- Crud Automator imports only the public `@nestjs/swagger` entry point. Importing `@nestjs/swagger/dist/*` in your own code no longer works either: from 11.4.3 the `exports` map closes those paths, and 12 exports only the root and `./plugin`.
- From `@nestjs/swagger` 11.4.3, `multipleOf` on a numeric query parameter moves from the parameter object into its `schema`. Regenerate API clients after the upgrade.
- `@nestjs/passport`, `@nestjs/platform-fastify`, and `fastify` are not peer dependencies: the published package does not import any of them. Install them only when your application uses Passport or the Fastify adapter. `CorrelationIDResponseBodyInterceptor` is written for the Fastify adapter, so an application that registers it needs `@nestjs/platform-fastify`.
- `TSwaggerComponentSchema`, `TSwaggerHeadersObject`, `TSwaggerReferenceObject`, `TSwaggerSchemaObject`, and `TSwaggerSecurityRequirementObject` are exported from the package root. Each one is the matching OpenAPI type from the installed `@nestjs/swagger`. See [Types](/docs/nestjs-crud-automator/api-reference/types#openapi-types).

## Basic Usage

### Step 1: Define Your Entity

Define your entity with `ApiPropertyDescribe` decorators to provide metadata for CRUD generation:

```typescript filename="user.entity.ts" copy
import { Entity, PrimaryGeneratedColumn, Column } from "typeorm";
import { ApiPropertyDescribe, EApiPropertyDescribeType, EApiPropertyStringType, EApiPropertyDateIdentifier, EApiPropertyDateType } from "@elsikora/nestjs-crud-automator";

@Entity("users")
export class UserEntity {
	@PrimaryGeneratedColumn("uuid")
	@ApiPropertyDescribe({
		type: EApiPropertyDescribeType.UUID,
		description: "User unique identifier",
	})
	id: string;

	@Column()
	@ApiPropertyDescribe({
		type: EApiPropertyDescribeType.STRING,
		description: "User name",
		format: EApiPropertyStringType.STRING,
		minLength: 3,
		maxLength: 50,
		pattern: "/^[a-zA-Z0-9_-]+$/",
		exampleValue: "john_doe",
	})
	username: string;

	@Column()
	@ApiPropertyDescribe({
		type: EApiPropertyDescribeType.STRING,
		description: "User email",
		format: EApiPropertyStringType.EMAIL,
		minLength: 5,
		maxLength: 255,
		pattern: "/^[\\w.-]+@([\\w-]+\\.)+[\\w-]{2,}$/",
		exampleValue: "user@example.com",
	})
	email: string;

	@Column({ type: "timestamp", default: () => "CURRENT_TIMESTAMP" })
	@ApiPropertyDescribe({
		type: EApiPropertyDescribeType.DATE,
		identifier: EApiPropertyDateIdentifier.CREATED_AT,
		format: EApiPropertyDateType.DATE_TIME,
	})
	createdAt: Date;

	@Column({ type: "timestamp", default: () => "CURRENT_TIMESTAMP", onUpdate: "CURRENT_TIMESTAMP" })
	@ApiPropertyDescribe({
		type: EApiPropertyDescribeType.DATE,
		identifier: EApiPropertyDateIdentifier.UPDATED_AT,
		format: EApiPropertyDateType.DATE_TIME,
	})
	updatedAt: Date;
}
```

`CREATED_AT`, `UPDATED_AT`, and `RECEIVED_AT` identify server-owned infrastructure timestamps. Generated CREATE, UPDATE, and PARTIAL_UPDATE body DTOs omit them while response DTOs retain them. The rule follows the identifier rather than the property name; use `DATE` for a writable business date.

### Step 2: Create a Service

Create a service with the `ApiService` decorator to add CRUD operations:

```typescript filename="user.service.ts" copy
import { Injectable } from "@nestjs/common";
import { InjectRepository } from "@nestjs/typeorm";
import { Repository } from "typeorm";
import { ApiService, ApiServiceBase } from "@elsikora/nestjs-crud-automator";
import { UserEntity } from "./user.entity";

@Injectable()
@ApiService<UserEntity>({
	entity: UserEntity,
})
export class UserService extends ApiServiceBase<UserEntity> {
	constructor(
		@InjectRepository(UserEntity)
		public repository: Repository<UserEntity>,
	) {
		super();
	}

	// Add custom methods beyond basic CRUD
	async findByEmail(email: string): Promise<UserEntity | null> {
		return this.repository.findOne({ where: { email } });
	}
}
```

### Step 3: Create a Controller

Create a controller with the `ApiController` decorator to generate all CRUD endpoints:

```typescript filename="user.controller.ts" copy
import { ApiController, EApiRouteType } from "@elsikora/nestjs-crud-automator";
import { UserEntity } from "./user.entity";
import { UserService } from "./user.service";

@ApiController<UserEntity>({
	entity: UserEntity,
	name: "Users",
	path: "users",
	routes: {
		[EApiRouteType.CREATE]: {},
		[EApiRouteType.PARTIAL_UPDATE]: {},
		[EApiRouteType.UPDATE]: {},
		[EApiRouteType.DELETE]: {},
		[EApiRouteType.GET]: {},
		[EApiRouteType.GET_LIST]: {},
	},
})
export class UserController {
	constructor(public service: UserService) {}
}
```

### Step 4: Register in Module

Register the entity, service, and controller in your module:

```typescript filename="user.module.ts" copy
import { Module } from "@nestjs/common";
import { TypeOrmModule } from "@nestjs/typeorm";
import { UserEntity } from "./user.entity";
import { UserService } from "./user.service";
import { UserController } from "./user.controller";

@Module({
	imports: [TypeOrmModule.forFeature([UserEntity])],
	providers: [UserService],
	controllers: [UserController],
	exports: [UserService],
})
export class UserModule {}
```

### Step 5: Enable Declarative Authorization (Optional)

Import `ApiAuthorizationModule` once in your root module and declare policies when you need RBAC. Policies are just injectable classes with a decorator. Mark controllers with `@ApiControllerSecurable()` to enable policy evaluation:

```typescript filename="app.module.ts" copy
import { Module } from "@nestjs/common";
import { ApiAuthorizationModule } from "@elsikora/nestjs-crud-automator";

@Module({
	imports: [
		/* other modules */
		ApiAuthorizationModule,
	],
})
export class AppModule {}
```

```typescript filename="policies/user-access.policy.ts" copy
import type { IApiAuthorizationRuleContext, IApiAuthorizationScope, TApiAuthorizationPolicyBeforeGetResult } from "@elsikora/nestjs-crud-automator";

import { ApiAuthorizationPolicy, ApiAuthorizationPolicyBase } from "@elsikora/nestjs-crud-automator";
import { UserEntity } from "../user.entity";

@ApiAuthorizationPolicy<UserEntity>({ entity: UserEntity })
export class UserAccessPolicy extends ApiAuthorizationPolicyBase<UserEntity> {
	public onBeforeGet(): TApiAuthorizationPolicyBeforeGetResult<UserEntity> {
		return this.allow({
			scope: (context: IApiAuthorizationRuleContext<UserEntity>): IApiAuthorizationScope<UserEntity> => ({
				where: { id: context.principal.id },
			}),
		});
	}
}
```

Policy hooks return arrays of rules. Use an empty array (`[]`) when no rules apply.

Once the module is imported, the guard is wired automatically and scopes/result transforms are applied to every securable generated route.

## Generated Endpoints

With the above setup, the following endpoints are automatically generated:

- `POST /users` - Create a new user
- `GET /users/:id` - Get a single user by ID
- `GET /users` - Get a PAGE list by default, or a CURSOR list when configured, with filtering and sorting
- `PUT /users/:id` - Update or replace a user
- `PATCH /users/:id` - Partially update a user
- `DELETE /users/:id` - Delete a user

## Nested Generated Reads

When a controller path inherits owner parameters, map every path parameter to a described direct scalar entity field on generated `GET` and `GET_LIST` routes:

```typescript filename="provider-game.controller.ts" copy
import { ApiController, EApiControllerGetListQueryUnlistedFields, EApiControllerRequestTarget, EApiRouteType, EFilterOrderDirection } from "@elsikora/nestjs-crud-automator";
import { GameEntity } from "./game.entity";
import { GameService } from "./game.service";

@ApiController<GameEntity>({
	entity: GameEntity,
	path: "providers/:providerKey/games",
	routes: {
		[EApiRouteType.GET]: {
			read: {
				scope: {
					parameters: [{ parameter: "providerKey", field: "providerId" }],
				},
			},
		},
		[EApiRouteType.GET_LIST]: {
			read: {
				scope: {
					parameters: [{ parameter: "providerKey", field: "providerId" }],
				},
			},
			request: {
				[EApiControllerRequestTarget.QUERY]: {
					order: {
						defaultOrder: [{ direction: EFilterOrderDirection.ASC, field: "name" }],
						fields: { name: { isEnabled: true } },
						tieBreakers: [{ direction: EFilterOrderDirection.ASC, field: "id" }],
						unlistedFields: EApiControllerGetListQueryUnlistedFields.REJECT,
					},
				},
			},
		},
	},
})
export class ProviderGameController {
	constructor(public service: GameService) {}
}
```

Automator generates the PARAMETERS DTO and Swagger path metadata from the mapped entity field. A manual PARAMETERS DTO cannot be combined with `read.scope.parameters`. GET keeps its generated primary-key parameter in addition to the inherited scope. GET identity or GET_LIST query predicates are AND-merged with path scope and then HOOKS/IAM scope, so later layers cannot overwrite earlier conditions.

For GET_LIST, a client `orderBy` replaces `defaultOrder`; `tieBreakers` are then appended with duplicate fields removed. A UUID `id` can be a server-only final tie-breaker without becoming a client-sort field. Default PAGE mode requires explicit `page` and `limit`. Opt-in CURSOR mode uses `limit` plus optional `after`/`before` and requires the complete primary key, single or composite, as its final explicit tie-breakers.

## Swagger Documentation

To enable Swagger documentation in your application:

```typescript filename="main.ts" copy
import { NestFactory } from "@nestjs/core";
import { DocumentBuilder, SwaggerModule } from "@nestjs/swagger";
import { AppModule } from "./app.module";

async function bootstrap() {
	const app = await NestFactory.create(AppModule);

	const config = new DocumentBuilder()
		.setTitle("Your API")
		.setDescription("API description")
		.setVersion("1.0")
		.addBearerAuth(
			{
				bearerFormat: "JWT",
				scheme: "bearer",
				type: "http",
			},
			"jwt",
		)
		.build();

	const document = SwaggerModule.createDocument(app, config);
	SwaggerModule.setup("api", app, document);

	await app.listen(3000);
}
bootstrap();
```
