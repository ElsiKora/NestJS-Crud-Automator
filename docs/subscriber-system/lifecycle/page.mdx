# Lifecycle

Understanding the execution order of subscribers and operations is crucial for implementing complex business logic correctly.

## Complete Execution Flow

### Create Operation

```
1. HTTP Request arrives at controller
2. Route subscribers: onBeforeCreate (priority: high → low)
3. Controller transformers (request)
4. Controller validators
5. Resolve the configured generated-route transaction mode
6. Request relation hydration
7. Service method: create() called
8. Function subscribers: onBeforeCreate (priority: high → low)
9. Repository: save() executed
10. Function subscribers: onAfterCreate (priority: high → low); a generated route drops their result and any change to context.result
11. Generated response reload through service.get() by the key TypeORM saved in step 9
12. Commit and post-commit lifecycle when the route owns the transaction
13. Controller transformers (response)
14. Route subscribers: onAfterCreate (priority: high → low)
15. Authorization result transforms
16. Relation projection and DTO serialization
17. HTTP Response sent to client
```

With route `REQUIRED`, steps 6–11 share one transaction manager, and step 12 completes before response handling. Omitted route config and `SUPPORTS` do not open a route transaction; an inner function configured as `REQUIRED` can still own its narrower transaction and commit before the generated response reload. A [generated `CREATE`](/docs/nestjs-crud-automator/guides/authorization#scoped-create) is the exception, scoped or not: under those modes it opens a route transaction as well, so function subscribers on steps 8–11 receive `eventManager`, and a row that step 11 cannot find through the scope rolls back and answers `403`. Step 10 has already run by then, so its side effects outside the transaction are not undone, and steps 13–16 do not run.

### Update Operation

```
1. HTTP Request arrives at controller
2. Route subscribers: onBeforeUpdate (priority: high → low)
3. Controller transformers (request)
4. Controller validators
5. Resolve the configured generated-route transaction mode
6. Request relation hydration
7. Service method: update() called
8. Resolve or join the configured function transaction
9. Function subscribers: onBeforeGet (priority: high → low)
10. Repository: findOne() through the resolved repository
11. Function subscribers: onAfterGet (priority: high → low)
12. Create detached top-level frozen currentEntity snapshot
13. Function subscribers: onBeforeUpdate (priority: high → low)
14. Merge the returned patch into the internal loaded entity
15. Repository: save() executed with updates
16. Function subscribers: onAfterUpdate (priority: high → low); a generated route drops their result and any change to context.result
17. Commit and post-commit lifecycle when UPDATE owns the function transaction
18. Generated response reload through service.get() by the key in the request path
19. Commit and post-commit lifecycle when the route owns the transaction
20. Controller transformers (response)
21. Route subscribers: onAfterUpdate (priority: high → low)
22. Authorization result transforms
23. Relation projection and DTO serialization
24. HTTP Response sent to client
```

When the route owns the transaction, UPDATE joins it and step 17 does not commit; response reload remains inside the route boundary before step 19. With omitted/`SUPPORTS` route config and function `REQUIRED`, step 17 commits the narrower function transaction before response reload, so a reload that misses the row (step 18 runs the GET function subscribers and the caller's scope) fails the route while the write stays; route `REQUIRED` rolls it back. A [scoped UPDATE](/docs/nestjs-crud-automator/guides/authorization#scoped-update) is the exception: under omitted/`SUPPORTS` route config it opens a route transaction, so step 17 does not commit, and a reload that misses the row rolls back and answers `403`. If the decorated GET misses, its GET error lifecycle runs, `onBeforeUpdate` is skipped, and the UPDATE error lifecycle receives the same error.

### Get Operation

```
1. HTTP Request arrives at controller
2. Route subscribers: onBeforeGet (priority: high → low)
3. Generated primary-key and inherited read-scope path parameters are transformed and validated
4. Resolve the configured generated-route transaction mode
5. Inside the optional route transaction, primary identity is AND-merged with path scope and then HOOKS/IAM scope
6. Service method: get() called with configured response relation loading
7. Function subscribers: onBeforeGet (priority: high → low)
8. Repository: findOne() executed
9. Function subscribers: onAfterGet (priority: high → low)
10. Commit and post-commit lifecycle when the route owns the transaction
11. Controller transformers (response)
12. Route subscribers: onAfterGet (priority: high → low)
13. Authorization result transforms
14. Relation projection and DTO serialization
15. HTTP Response sent to client
```

When `pathScope` is configured, the generated PARAMETERS DTO covers every controller-path parameter exactly once in addition to the row parameters. Conflicting row, path, or IAM conditions become match-nothing criteria; no later layer overwrites an earlier field.

Before step 2, every generated route validates and converts its path values once per request against its PARAMETERS DTO (on a securable route, `ApiAuthorizationGuard` already did it before authorization). `@ApiRouteCustom` routes do not run this step: only the guard of a securable IAM custom route runs its PARAMETERS DTO on the path values, and the handler reads them as canonical text in `request.params`. `onBefore*` route subscribers and later steps receive the typed values, such as a number for an integer `NUMBER` key. When that check fails, the route answers `400` and `onBeforeError*` subscribers see the raw string. The "transformed and validated" step then checks the values once more, because subscribers and transformers can replace them.

### Get List Operation

```
1. HTTP Request arrives at controller
2. Route subscribers: onBeforeGetList (priority: high → low)
3. Configured inherited read-scope PARAMETERS transformers and validators run outside the route transaction
4. Request QUERY transformers and custom validators run outside the route transaction
5. A configured typed query plan parses and validates the post-subscriber query into a canonical AST and applies `USE_DEFAULT` conditions when field groups are absent; a PAGE route without a typed filter validates the post-subscriber query against its QUERY DTO instead
6. Resolve the configured generated-route transaction mode
7. Inside the optional route transaction, query predicates are AND-merged with path scope and then HOOKS/IAM scope
8. Pagination mode and the effective client/default order plus de-duplicated tie-breakers are compiled into TypeORM options
9. PAGE calls getList(), dispatches GET_LIST function subscribers, and runs find/count; CURSOR evaluates one GET_MANY BEFORE chain, reuses its candidate `where`/`withDeleted`, then calls getMany() for one `limit + 1` window and, when a cursor is present, one opposite `take: 1` probe; GET_MANY AFTER subscribers run for each actual query
10. The generated route returns the PAGE count envelope or constructs the flat CURSOR envelope
11. Commit and post-commit lifecycle when the route owns the transaction
12. Controller transformers (response)
13. Route subscribers: onAfterGetList (priority: high → low), whose `DATA.query` is the same query object onBeforeGetList produced, not a validated or parsed copy
14. Authorization result transforms
15. Relation projection and DTO serialization
16. HTTP Response sent to client
```

On every GET_LIST route, legacy, typed or CURSOR, `onAfterGetList` and the error hooks receive in `DATA.query` the query that `onBeforeGetList` produced: the raw request query with its string values and any changes the before subscribers made. Validated and converted values are used only to build the database query.

The typed query parser is authoritative and does not depend on host `ValidationPipe` whitelist behavior. If a PAGE route omits typed filter configuration, it validates its QUERY DTO after route-before subscribers and QUERY transformers, independently of a host `ValidationPipe`; a failure reaches `BEFORE_ERROR` subscribers before any query runs. A controller `pathScope` uses a generated PARAMETERS DTO and cannot be combined with a manual PARAMETERS DTO. With no client order pair, `defaultOrder` precedes `tieBreakers`; with a client pair, it replaces defaults and still precedes de-duplicated tie-breakers. CURSOR requires the complete primary key, single or composite, as its final explicit tie-breakers, and both its window and probe keep query, path, and recalculated HOOKS/IAM predicates.

CURSOR does not introduce a second route authorization action: the route still runs the existing GET_LIST policy/`onBeforeGetList` hook. Its generated service execution runs GET_MANY BEFORE once per HTTP request, then reuses the detached candidate `where` and `withDeleted` for both queries. It re-protects mandatory scope/window predicates and framework-owned `order`/`take`, forces `cache: false`, shadows `select`/`skip`, and fails closed if later function, route, authorization, relation, or serialization work changes the protected row sequence/raw order tuple or flat cursor envelope. Direct GET_MANY service calls are unchanged and continue to run their ordinary subscriber lifecycle per call.

### Delete Operation

```
1. HTTP Request arrives at controller
2. Route subscribers: onBeforeDelete (priority: high → low)
3. Path parameters transformed and validated
4. Resolve the configured generated-route transaction mode
5. Service method: delete() called
6. Function subscribers: onBeforeDelete (priority: high → low)
7. Repository: findOne() to verify existence
8. Repository: remove() executed
9. Function subscribers: onAfterDelete (priority: high → low)
10. Commit and post-commit lifecycle when the route owns the transaction
11. Route subscribers: onAfterDelete (priority: high → low)
12. HTTP Response sent to client
```

For GET, GET_LIST, and DELETE, omitted route config and `SUPPORTS` open no route transaction. `REQUIRED` encloses the generated service operation and completes commit lifecycle before route-after; `MANDATORY` requires an outer owner, and `NONE` rejects one.

## Error Flow

Generated route error hooks have explicit boundaries:

```
1. Request-side failures run before-error hooks:
   - route before subscribers
   - request transformers
   - request validators
   - request relation loading
   - primary-key resolution
2. Service, response transformer, after subscriber, authorization result transform, relation projection, and serialization failures run after-error hooks.
3. Function-level failures dispatch function before-error or after-error hooks according to the same setup/before versus operation/after boundary.
4. A route-owned transaction rolls back hydration, generated operation, or response reload failures before route error subscribers observe the error.
5. Route-after failures occur after a route-owned commit and cannot be represented as database rollback.
6. Errors are rethrown after subscribers observe them.
```

## Priority Execution

### Before Hooks

Execute in priority order (high to low):

```typescript
// Priority 100 executes first
@ApiRouteSubscriber({ entity: Post, priority: 100 })
export class SecuritySubscriber {
	async onBeforeCreate(context) {
		console.log("1. Security check");
		return context.result;
	}
}

// Priority 50 executes second
@ApiRouteSubscriber({ entity: Post, priority: 50 })
export class ValidationSubscriber {
	async onBeforeCreate(context) {
		console.log("2. Validation");
		return context.result;
	}
}

// Priority 10 executes last
@ApiRouteSubscriber({ entity: Post, priority: 10 })
export class LoggingSubscriber {
	async onBeforeCreate(context) {
		console.log("3. Logging");
		return context.result;
	}
}
```

### After Hooks

Execute in priority order (high to low):

```typescript
// Priority 100 executes first
@ApiRouteSubscriber({ entity: Post, priority: 100 })
export class NotificationSubscriber {
	async onAfterCreate(context) {
		console.log("1. Send notifications");
		return context.result;
	}
}

// Priority 50 executes second
@ApiRouteSubscriber({ entity: Post, priority: 50 })
export class CacheSubscriber {
	async onAfterCreate(context) {
		console.log("2. Update cache");
		return context.result;
	}
}

// Priority 10 executes last
@ApiRouteSubscriber({ entity: Post, priority: 10 })
export class LoggingSubscriber {
	async onAfterCreate(context) {
		console.log("3. Logging result");
		return context.result;
	}
}
```

## Detailed Example with Logging

```typescript filename="example-with-logging.ts" copy
// Route Subscriber
@Injectable()
@ApiRouteSubscriber({ entity: PostEntity, priority: 50 })
export class PostRouteSubscriber extends ApiRouteSubscriberBase<PostEntity> {
	async onBeforeCreate(context: TApiSubscriberRouteBeforeCreateContext<PostEntity>): Promise<TApiSubscriberRouteBeforeCreateContext<PostEntity>["result"] | undefined> {
		console.log("[Route] onBeforeCreate - START");
		return context.result;
	}

	async onAfterCreate(context: TApiSubscriberRouteAfterCreateContext<PostEntity>): Promise<PostEntity> {
		console.log("[Route] onAfterCreate - END");
		return context.result;
	}
}

// Function Subscriber
@Injectable()
@ApiFunctionSubscriber({ entity: PostEntity, priority: 50 })
export class PostFunctionSubscriber extends ApiFunctionSubscriberBase<PostEntity> {
	async onBeforeCreate(context: TApiSubscriberFunctionBeforeCreateContext<PostEntity>): Promise<TApiFunctionCreateProperties<PostEntity>> {
		console.log("[Function] onBeforeCreate - START");
		return context.result;
	}

	async onAfterCreate(context: TApiSubscriberFunctionAfterCreateContext<PostEntity>): Promise<PostEntity> {
		console.log("[Function] onAfterCreate - END");
		return context.result;
	}
}

// Service
@Injectable()
@ApiService({ entity: PostEntity })
@ApiServiceObservable()
export class PostService extends ApiServiceBase<PostEntity> {
	async create(properties: TApiFunctionCreateProperties<PostEntity>): Promise<PostEntity> {
		console.log("[Service] create - Repository operation");
		return super.create(properties);
	}
}

// Console output for POST /posts:
// [Route] onBeforeCreate - START
// [Function] onBeforeCreate - START
// [Service] create - Repository operation
// [Function] onAfterCreate - END
// [Route] onAfterCreate - END
```

## Async Operations

All subscriber hooks are async and execute sequentially:

```typescript
async onBeforeCreate(context: TApiSubscriberRouteBeforeCreateContext<PostEntity>): Promise<TApiSubscriberRouteBeforeCreateContext<PostEntity>["result"] | undefined> {
  // Operation 1 completes first
  await this.validateData(context.result.body);

  // Operation 2 completes second
  await this.checkPermissions(context.result.authenticationRequest?.user);

  // Operation 3 completes third
  await this.enrichData(context.result.body);

  return context.result;
}
```

## Short-Circuiting

Throw an error to stop execution:

```typescript
async onBeforeCreate(context: TApiSubscriberRouteBeforeCreateContext<PostEntity>): Promise<TApiSubscriberRouteBeforeCreateContext<PostEntity>["result"] | undefined> {
  const user = context.result.authenticationRequest?.user;

  if (!user || user.role !== "admin") {
    // Stops here, error hooks are called
    throw new ForbiddenException("Admin access required");
  }

  return context.result;
}
```

## Modifying Data Through Pipeline

Each subscriber can modify the result:

```typescript
// Subscriber 1 (Priority 100)
async onBeforeCreate(context: TApiSubscriberRouteBeforeCreateContext<PostEntity>): Promise<TApiSubscriberRouteBeforeCreateContext<PostEntity>["result"] | undefined> {
  context.result.body.field1 = "value1";
  return context.result; // Passes to next subscriber
}

// Subscriber 2 (Priority 50)
async onBeforeCreate(context: TApiSubscriberRouteBeforeCreateContext<PostEntity>): Promise<TApiSubscriberRouteBeforeCreateContext<PostEntity>["result"] | undefined> {
  // Receives modified context from Subscriber 1
  context.result.body.field2 = "value2";
  return context.result; // Passes to next subscriber
}

// Subscriber 3 (Priority 10)
async onBeforeCreate(context: TApiSubscriberRouteBeforeCreateContext<PostEntity>): Promise<TApiSubscriberRouteBeforeCreateContext<PostEntity>["result"] | undefined> {
  // Receives context with field1 and field2
  context.result.body.field3 = "value3";
  return context.result; // Final result
}
```

## Transaction Boundaries

Generated CRUD routes can reuse `EApiFunctionTransactionMode` under route `transaction.mode`. Omitted configuration and `SUPPORTS` open no route transaction, except for a [generated `CREATE`](/docs/nestjs-crud-automator/guides/authorization#scoped-create), which always runs in one, and a [scoped `UPDATE` or `PARTIAL_UPDATE`](/docs/nestjs-crud-automator/guides/authorization#scoped-update). `REQUIRED` opens a `ROUTE`-owned transaction when no Automator owner exists; `MANDATORY` requires an active owner; `NONE` rejects active execution. Request transformers and validators run before a route-owned transaction. Request relation hydration, the generated service operation, and response relation reload run inside it. When the route opens and owns the transaction, commit and post-commit hooks finish before response transformers and route-after subscribers; a joined outer owner commits later. Custom routes do not use this route transaction setting.

`onAfterCommit` and `onAfterRollback` run once per matching function subscriber only after the outer `FUNCTION`, `ROUTE`, or named `SCOPE` owner confirms the database result. Their readonly context contains the transaction id and owner, the full ordered event trace, and subscriber-matched events. `NONE` and nontransactional `SUPPORTS` produce no post-transaction hooks.

A post-commit hook failure produces `ApiFunctionTransactionPostCommitException` with outcome `COMMITTED`; remaining commit hooks and commit-error lifecycle still run. An unconfirmed database COMMIT produces `ApiFunctionTransactionCommitUnknownOutcomeException` with outcome `UNKNOWN`, invokes commit-error lifecycle, and runs neither post-commit nor post-rollback hooks. Confirmed operation rollback preserves the operation error; additional rollback failures are exposed through `ApiFunctionTransactionRollbackException`.

Transaction error lifecycle methods are `onBeforeErrorCommit`, `onAfterErrorCommit`, `onBeforeErrorRollback`, and `onAfterErrorRollback`. Error-lifecycle failures are collected and do not recursively invoke the same lifecycle.

Function subscribers can participate in transactions when an `eventManager` is provided:

```typescript
async onBeforeCreate(
  context: TApiSubscriberFunctionBeforeCreateContext<PostEntity>
): Promise<TApiFunctionCreateProperties<PostEntity>> {
  const manager = context.DATA.eventManager;

  if (manager) {
    // All operations within same transaction
    const tags = await manager.save(TagEntity, [...]);
    const category = await manager.save(CategoryEntity, {...});

    context.result.tags = tags;
    context.result.categoryId = category.id;
  }

  return context.result;
  // If any operation fails, the transaction rolls back
}
```

## Application Shutdown

`ApiSubscriberModule` adds an application's subscribers to the process-wide `apiSubscriberRegistry` in `onModuleInit` and removes them in `onApplicationShutdown`. The registry keys subscribers by entity class, so subscribers of two entity classes that share a name stay apart; `getFunctionSubscribers` and `getRouteSubscribers` take the class. No consumer code is required. `app.close()` runs this hook without `enableShutdownHooks()`, which only makes process signals follow the same order:

```
1. onModuleDestroy hooks
2. beforeApplicationShutdown hooks
3. HTTP server closes
4. onApplicationShutdown hooks: subscribers are removed
```

Step 3 waits for the server to close, not for route handlers. A request whose connection stays open until its response keeps its subscribers. After close, the application's subscribers no longer run, so a later application in the same process, such as the next test or a hot reload, runs only its own subscribers.

Removal is by subscriber instance, so closing one application leaves another live application's subscribers registered.

Limits:

- A handler can finish after `app.close()` when its client disconnected during the request or the adapter uses `new FastifyAdapter({ forceCloseConnections: true })`. Its connection no longer holds the server open, so subscribers can be removed while it runs, and hooks it reaches after that, such as after-subscribers, are silently skipped. Automator does not track running requests.
- Two applications alive at the same time in one process still share the registry. Until one of them closes, a matching operation in either application runs the subscribers of both.
- Removal runs only when close reaches `onApplicationShutdown`. Subscribers can stay registered if another provider's hook throws during close, or if `TestingModule.init()` fails during bootstrap after discovery has run.

### Migration Notes

Before 5.0.0, subscribers were never removed. From 5.0.0, work in your own `onApplicationShutdown`, such as a final audit write or an outbox flush, can run without subscribers. Nest runs this hook by module depth, shallower modules first; at the same depth, a module imported later runs first. So a provider sees subscribers only if its module runs before `ApiSubscriberModule`:

| Provider's module                                 | Subscribers during its `onApplicationShutdown` |
| ------------------------------------------------- | ---------------------------------------------- |
| Shallower, including the root module              | Registered                                     |
| Same depth, imported after `ApiSubscriberModule`  | Registered                                     |
| Same depth, imported before `ApiSubscriberModule` | Removed                                        |
| Deeper than `ApiSubscriberModule`                 | Removed                                        |

Do not rely on import order. Move work that needs subscribers to `beforeApplicationShutdown`, which runs before step 3.

From 5.0.0, route subscribers of generated routes receive typed path values in `result.parameters` and `DATA.parameters`, such as the number `16` instead of the string `"16"` for an integer `NUMBER` key. `onBeforeError*` subscribers receive the raw string only when the path check itself rejects the request.

## Best Practices

### 1. Use Priority Wisely

```typescript
// Validation should happen first
@ApiRouteSubscriber({ entity: Post, priority: 100 })
export class ValidationSubscriber {}

// Business logic in the middle
@ApiRouteSubscriber({ entity: Post, priority: 50 })
export class BusinessLogicSubscriber {}

// Logging and notifications last
@ApiRouteSubscriber({ entity: Post, priority: 10 })
export class NotificationSubscriber {}
```

### 2. Keep Hooks Focused

```typescript
// Good: One responsibility per subscriber
@ApiFunctionSubscriber({ entity: Post })
export class SlugGeneratorSubscriber {
	async onBeforeCreate(context: TApiSubscriberFunctionBeforeCreateContext<Post>): Promise<TApiFunctionCreateProperties<Post>> {
		context.result.slug = this.generateSlug(context.result.title);
		return context.result;
	}
}

// Bad: Multiple responsibilities
@ApiFunctionSubscriber({ entity: Post })
export class MixedSubscriber {
	async onBeforeCreate(context: TApiSubscriberFunctionBeforeCreateContext<Post>): Promise<TApiFunctionCreateProperties<Post>> {
		// Don't do this
		context.result.slug = this.generateSlug(context.result.title);
		await this.sendNotification();
		await this.updateCache();
		return context.result;
	}
}
```

### 3. Handle Errors Gracefully

```typescript
async onAfterErrorCreate(
  context: IApiSubscriberRouteErrorExecutionContext<PostEntity>,
  error: Error
): Promise<void> {
  try {
    // Cleanup operations
    await this.cleanup(context.ENTITY);
  } catch (cleanupError) {
    // Don't throw errors in error hooks
    this.logger.error(`Cleanup failed: ${FormatErrorEvidenceForLog(cleanupError)}`);
  }
}
```

The formatter returns only a bounded error type and optional validated SQLSTATE. It does not serialize the cleanup error or subscriber context.
