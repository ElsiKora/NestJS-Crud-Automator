# Migrating To 5.0

Crud Automator 5.0.0 moves to NestJS 12, `@nestjs/swagger` 12 and TypeORM 1, ships as ES modules only, and tightens several runtime contracts. This page lists every breaking change. Each section links to the Migration Notes of the page that describes the change in full. Stay on 4.x until the application has moved to the new peers.

## Runtime And Peers

| Requirement         | 4.x          | 5.0                       |
| ------------------- | ------------ | ------------------------- |
| Node.js             | 20 and later | `^22.13.0 \|\| >=24.11.0` |
| `@nestjs/common`    | 11           | `>=12.3.2 <13`            |
| `@nestjs/core`      | 11           | `>=12.3.2 <13`            |
| `@nestjs/swagger`   | 11           | `>=12.0.0 <13`            |
| `@nestjs/throttler` | 6            | `>=6.7.1 <7`              |
| `typeorm`           | 0.3          | `>=1.1.2 <2`              |

1. Upgrade Node.js, NestJS, `@nestjs/swagger` and TypeORM first, following their own migration guides.
2. Install peers with explicit ranges. Every peer now has an upper bound at the next major, and upgrading a peer past it only prints `npm warn ERESOLVE overriding peer dependency`; check the tree with `npm ls`.
3. Replace `@nestjs/swagger/dist/*` imports with the package root. Swagger 12 exports only `.` and `./plugin`.
4. Regenerate API clients: `multipleOf` on a numeric query parameter moves from the parameter object into its `schema`.

See [Getting Started: Migration Notes](/docs/nestjs-crud-automator/getting-started#migration-notes).

## ES Modules Only

The package has one ES module build in `dist`. `dist/esm`, `dist/cjs` and the `require` export condition are gone; `exports` has only `types` and `default`.

- An ES module application imports the package as before, with `moduleResolution` `bundler`, `node16` or `nodenext`.
- A CommonJS application keeps `require("@elsikora/nestjs-crud-automator")`. Node.js loads it through `require(esm)`. TypeScript 6 resolves `module: commonjs` without a `moduleResolution` setting as `bundler`, so it reads the types from `exports`; with an explicit `moduleResolution: node10` it reads the top-level `types` field, and TypeScript 6 then needs `"ignoreDeprecations": "6.0"` (otherwise TS5107). Both find the types. TypeScript 6 also defaults `types` to `[]`, so list `"types": ["node"]` when the application uses Node.js globals.
- Deep imports such as `@elsikora/nestjs-crud-automator/dist/cjs/...` no longer resolve. Import from the package root.
- An application that runs as native ES modules itself must follow [Native ES Module Applications](#native-es-module-applications).

See [Getting Started: Migration Notes](/docs/nestjs-crud-automator/getting-started#migration-notes).

### Native ES Module Applications

In an application that runs as native ES modules (`"type": "module"`, built by `tsc` or by the Nest CLI SWC builder with `module.type: "es6"`), every relation property between entities that import each other must be typed `Relation<T>` from `typeorm`. This is required, not a style choice. With `emitDecoratorMetadata` (`decoratorMetadata` in SWC), the compiler writes each decorated property type into `design:type` while the module loads. In a cycle, one of the two classes is not initialized yet:

```typescript filename="book.entity.ts"
import { ManyToOne } from "typeorm";
import { AuthorEntity } from "./author.entity";

export class BookEntity {
	@ManyToOne(() => AuthorEntity, (author) => author.books)
	author: AuthorEntity; // emitted as design:type AuthorEntity
}
```

```text
ReferenceError: Cannot access 'AuthorEntity' before initialization
    at file:///app/dist/entity/book.entity.js:60:5
```

SWC emits `typeof AuthorEntity === "undefined" ? Object : AuthorEntity`, which fails the same way, because `typeof` on an import that is not initialized yet also throws. CommonJS output reads the value later, so a CommonJS build of the same code starts and the failure appears only after the move to ES modules.

Type both sides with `Relation<T>` and import it with `import type`:

```typescript filename="book.entity.ts" copy
import type { Relation } from "typeorm";
import { ManyToOne } from "typeorm";
import { AuthorEntity } from "./author.entity";

export class BookEntity {
	@ManyToOne(() => AuthorEntity, (author) => author.books)
	author: Relation<AuthorEntity>;
}
```

```typescript filename="author.entity.ts" copy
import type { Relation } from "typeorm";
import { OneToMany } from "typeorm";
import { BookEntity } from "./book.entity";

export class AuthorEntity {
	@OneToMany(() => BookEntity, (book) => book.author)
	books: Relation<Array<BookEntity>>;
}
```

`design:type` of such a property becomes `Object`, and the relation decorators keep using their `() => AuthorEntity` callbacks. Nothing else depends on the emitted relation type. Crud Automator reads `design:type` only in `filter-order-by-from-entity.utility.ts`, and only for a column without an explicit `type`, to decide whether it can be filtered and sorted. TypeORM reads it on relation properties only to detect lazy `Promise<T>` relations. The generated DTOs, the OpenAPI document and the responses are the same with and without `Relation<T>`.

With TypeScript 6, set `paths` without `baseUrl` (otherwise TS5101). An application that builds with SWC and typechecks with `tsc --noEmit` and `moduleResolution: bundler` keeps extensionless `@`-alias imports in source; SWC with `jsc.paths` and `module.resolveFully: true` writes them as relative `.js` specifiers.

## Generated Schema Names

Every generated DTO and OpenAPI component name starts with the controller's schema prefix, the class name without a trailing `Controller`, and no longer contains the entity name: `UserController` generates `UserGetResponseDTO` where 4.x generated `UserEntityGetResponseDTO`. Two controllers on one entity now get their own components instead of sharing one.

1. Regenerate API clients and update hand-written `$ref` strings and generated type names. `scripts/openapi-rename-map.mjs` in the package prints a map of old component names to new ones from the 4.x and 5.0 documents.
2. Nested DTOs are named `<Parent><Property>[<Variant>]DTO` after the DTO that holds them, and a property name keeps its letters: `createdBy` gives `CreatedByDTO` where 4.x gave `CreatedbyDTO`. A relation or dynamic object copied with `@ApiPropertyCopy` is named after the DTO it is copied into and the host property it decorates. A custom route inherited from a base class or a mixin is named after each decorated controller that inherits it. The GET_LIST wrappers are `<Prefix>GetListPageDTO` and `<Prefix>GetListCursorPageDTO` instead of `<Entity>GetList[Cursor]ResponseItemsDTO`.
3. Give every controller class a unique name within an application. `app.init()` fails for two controller classes with one prefix, for two different classes with one component name anywhere in the application's route schemas, including hand-written DTOs and plain controllers, and for a lazy type that cannot be resolved. Call `app.init()` before exporting the document with `SwaggerModule.createDocument`.
4. A polymorphic variant class that a generated route references through a contextual copy is no longer a component of the document. No operation reached `CardPaymentDto`, and the route uses `<Parent><Property><Variant>DTO`. Move client code to that name, or declare `@ApiExtraModels(CardPaymentDto)` to keep the component.

See [DTOs: Migration Notes](/docs/nestjs-crud-automator/core-concepts/dtos#migration-notes).

## Query Criteria That Would Widen A Query

A generated `get`, `getList`, `getMany`, `update` or `delete` call fails with `InternalServerErrorException` when its `where` has an `undefined` or `null` value, an empty relation object, an empty OR array or an empty OR branch. Before 5.0.0, TypeORM 0.3 dropped those conditions, so `get({ where: { id: undefined } })` returned the first row.

Remove a condition instead of setting it to `undefined`, and use `IsNull()` instead of `null`. See [Services: Migration Notes](/docs/nestjs-crud-automator/core-concepts/services#migration-notes).

## Error Bodies

- Every error body that passes through `CorrelationIDResponseBodyInterceptor` has `correlationID`, `statusCode` and `timestamp`. The OpenAPI exception schemas require only `statusCode` and `message` on every status. `error` is optional, because an object response keeps its own shape, so `throw new NotFoundException()` answers without it. `correlationID` and `timestamp` are optional, because a guard or the body parser answers without them unless `CorrelationIDResponseBodyExceptionFilter` is registered. `message` and `error` have no pattern.
- Routes declare what they can answer, so a client generated from the document changes. `401` is gone from routes without a guard, and any guard now declares `401` and `403`: `security.authentication`, `execution.guards`, or `@UseGuards` on the class or the route. `404` is gone from GET_LIST. A generated CREATE on a securable controller with `authorization` declares `403` for a body outside the policy scope, and no `404` unless it loads a request relation. Every route, GET and DELETE included, declares `413` and `415`.
- `response.errors` no longer accepts `hasBadRequest` or `hasInternalServerError`, because every route now declares `400` and `500`. Remove them from your custom routes. See [Error Handling: Migration Notes](/docs/nestjs-crud-automator/guides/error-handling#migration-notes).
- `details` on `400` and `409` is discriminated by a single `type` value per variant, and a to-many relation key on an update now answers `details.type: "TO_MANY_UPDATE_KEY"`.
- A duplicate key answers one `409` body from create and update on every driver: `message` `{ENTITY}_DUPLICATE_KEY` and `details: { "type": "UNIQUE_VIOLATION" }`. The driver fields `constraint`, `detail`, `field`, `table` and `value` are gone from `details` and from `ExceptionDetailsUniqueViolationDTO`. Read `message` and `details.type` instead; the driver error stays in the exception `cause` for logs. See [Error Handling: Duplicate key body](/docs/nestjs-crud-automator/guides/error-handling#duplicate-key-body-in-500).
- An object response is the application's body. An `error` or `message` it lacks stays absent, so a codes-only `new BadRequestException({ code: "X" })` gets neither, and `new NotFoundException()` keeps the `message` and `statusCode` Nest built. Read `error` and `message` as optional on these bodies. An `exceptionFactory` body that omits `message` differs from the generated DTO of that route, and the application owns that difference.
- A present field keeps its value only when it has the contract type: `statusCode` is an integer equal to the response status, `message` is a string or an array of strings, `error` is a string. Anything else, `null` included, is replaced: `statusCode` by the response status, `message` and `error` by the status text from `STATUS_CODES`. Keep structured error data in a field of its own.
- A string or an array response becomes `message`, next to `error` with the status text. An http-errors value and an unknown failure still get both fields.
- A sanitized `500` has `error: "Internal Server Error"` and `message: "Internal server error"`. Before 5.0.0, `error` was `"Internal server error"`.
- A thrown object counts as an http-errors value only with an integer `statusCode` from `400` to `599`, and its `message` is sent only with `expose: true`. An `HttpException` status must be an integer from `200` to `599`; any other value answers the sanitized `500`.
- Failures outside the handler chain, such as a `401` or `403` from a guard or middleware, an unmatched route and a malformed body, get the same contract through `CorrelationIDResponseBodyExceptionFilter`. Register it with `app.useGlobalFilters(new CorrelationIDResponseBodyExceptionFilter(app.get(HttpAdapterHost)))`, before any filter of your own.
- Outside HTTP, such as an RPC handler or a gateway, the interceptor and the filter pass the call through and log one warning per component instance, not once per call.
- The exception the interceptor rethrows holds the original failure as `cause`. An exception filter that logs the whole exception now also logs SQL text and parameters; log `FormatErrorEvidenceForLog(exception.cause)` instead.

See [Error Handling: Migration Notes](/docs/nestjs-crud-automator/guides/error-handling#migration-notes).

## Relation Responses

- A to-many relation in `relations.response.load.include` is sent as an array, `[]` when it has no rows. Before 5.0.0, an `OBJECT` reference sent `{}` and a `SCALAR` reference left the key out.
- An `OBJECT` reference on a key other than `id` sends that key, `{ "code": "a" }` instead of `{}`.
- For every reference shape, the application fails at startup when the reference key, `id` included, is not a described, non-nullable scalar of the related entity, when `id` is the key on a target with a composite primary key, when `load` has no `reference`, or when a `lazy: true` relation is in `include`. A `SCALAR` on an undescribed or nullable key used to send the value, so such a route needs `@ApiPropertyDescribe` on the key, or another key.
- The response schema of each route describes its relations as the route sends them: the scalar key for `SCALAR`, an object with the configured key for `OBJECT`, an array for to-many, with the type of the key on the related entity, so an integer `id` is no longer a UUID. A relation is required only when the route always sends it, because it is included or eager, whatever `isRequired` says. A to-one relation is `nullable` when TypeORM can return `null` for it, which includes a target with a `@DeleteDateColumn`. Regenerate clients from the new OpenAPI document.
- A generated `PUT` or `PATCH` answers with the row as `GET` reads it by the key in the request path, on every route. A relation key of the body no longer comes back on a route that does not load that relation, and an eager relation is `{ id }` with its stored value instead of the raw value of the body.
- A function `onAfterUpdate` subscriber no longer changes the response of a generated route, neither by its result nor by a change to `context.result` in place, so a field it masked comes back in clear text. Mask it in a route `onAfterUpdate` subscriber or a function `onAfterGet` subscriber.
- A generated `POST` reads its response by the key TypeORM saved for the inserted row, generated columns included, not by the object that `create()` returned. A function `onAfterCreate` subscriber that returned another key no longer pulls that row into the response, and neither its result nor a change to `context.result` in place reaches the response; mask a field in a route `onAfterCreate` subscriber or a function `onAfterGet` subscriber.
- When the read of the response misses the row, the route fails after the write: a body that moves the row out of the caller's scope or sets its `@DeleteDateColumn`, or a `GET` function `onBeforeGet` subscriber that filters out the row as the body left it, answers `404`; a `GET` function `onAfterGet` subscriber that throws on that row answers with its error. Under the default `SUPPORTS` the write stays; set the route to `REQUIRED` when a client must never see a failure for a write that landed.
- With TypeORM `replication`, a `POST`, `PUT` or `PATCH` route in mode `SUPPORTS` can read its response from a replica and answer values from before the write; mode `REQUIRED` reads it on the master.
- A generated route fails at startup when its service has no function it calls protected by its built-in decorator (`CREATE` and `GET` for `POST`, `UPDATE` and `GET` for `PUT` and `PATCH`, `GET` for `GET`, `DELETE` for `DELETE`), or when such a function runs in a transaction mode the route cannot give it: `MANDATORY` under a route in `SUPPORTS` or `NONE`, `NONE` under a route in `REQUIRED` or `MANDATORY`. A `POST` route always runs in a transaction, so it refuses route mode `NONE` and a `NONE` function under every route mode, and runs a `MANDATORY` function under every mode it accepts. Such a route used to answer `500` on each request. A `PUT` or `PATCH` route without `include` used to work without a `GET` function, and a `POST` route with a plain `create` override; both now need the built-in function. Remove a plain override and move its logic into function subscribers or a custom route: the built-in decorator on it would replace its body.

See [Relations: Migration Notes](/docs/nestjs-crud-automator/guides/relations#migration-notes).

## No `.env` Loading

Importing the package no longer runs `dotenv`'s `config()`, and the package has no `dotenv` dependency. `NCD_LOG_LEVEL` and every other variable come from `process.env` only. Load the file in the application, for example with `node --env-file=.env` or `ConfigModule.forRoot()` from `@nestjs/config`. Each logger reads `NCD_LOG_LEVEL` at its first message, so a value loaded during bootstrap applies. See [Utilities: Migration Notes](/docs/nestjs-crud-automator/api-reference/utilities#migration-notes).

## Subscribers Removed On Close

`app.close()` removes the application's subscribers from the registry. Work in your own `onApplicationShutdown` can run without subscribers, depending on module order; move work that needs them to `beforeApplicationShutdown`. See [Lifecycle: Migration Notes](/docs/nestjs-crud-automator/subscriber-system/lifecycle#migration-notes).

## Array Bounds

An `@ApiProperty*` request array without `minItems`, `maxItems` or `isUniqueItems`, possible from JavaScript or `any`, fails at decoration and names the DTO class, the property and the missing bounds. A `minItems` or `maxItems` that is not a non-negative integer, such as `NaN`, or an `isUniqueItems` that is not a boolean fails at decoration on any array, and so does an `isArray` that is not a boolean. That includes `maxItems: Number.POSITIVE_INFINITY` and a fractional bound, which compiled and worked before; declare a finite integer. Before 5.0.0 such a bound decorated and could then reject every value, such an `isUniqueItems` only reached the OpenAPI schema, and such an `isArray` skipped the bound checks. A response array (`isResponse: true`) may leave the bounds out, and the options type of every `@ApiProperty*` decorator says so, so code that narrows one of them on `isArray === true` reads the bounds as possibly `undefined`; also check `isResponse !== true`. `@ApiPropertyBoolean` takes the new `TApiPropertyBooleanProperties`. See [Property Decorators: Migration Notes](/docs/nestjs-crud-automator/api-reference/decorators/api-property#migration-notes) and [`@ApiPropertyObject`: Migration Notes](/docs/nestjs-crud-automator/api-reference/decorators/api-property/api-property-object#migration-notes).

## Free-Form Object Values

A free-form `@ApiPropertyObject` request value (`type: Object` or `type: undefined`) keeps its keys. A key `__proto__`, `constructor`, `hasOwnProperty` or `prototype` at any depth answers `400` on every `@ApiMethod` route; see [Request Body Limits](#request-body-limits). Before 5.0.0, `shouldValidateNested: true`, which every request array needs, attached `ValidateNested` to it: under a `ValidationPipe` with `whitelist: true`, `[{ "id": 1 }, { "id": 2 }]` reached the handler as `[{}, {}]`, a generated route stored the empty objects, and with `forbidNonWhitelisted: true` each key answered `400`. Nothing inside the value is validated now, apart from `isUniqueItems` comparing array items, so check it in the handler or declare a class. A free-form array item that is not an object answers `400` with `each value in <name> must be an object`, and that includes a nested array, which passed before. Remove `shouldValidateNested: true` from a free-form property: it no longer compiles and fails at decoration, and a free-form array does not need it. `type: [Object]`, which compiled and answered `500` on every request, fails the same way; use `type: Object`. See [`@ApiPropertyObject`: Migration Notes](/docs/nestjs-crud-automator/api-reference/decorators/api-property/api-property-object#migration-notes).

## Discriminator Keep Option

A nested `@ApiPropertyObject` discriminator now reads `shouldKeepDiscriminatorProperty` like a root-level one: only `false` removes the property. Leaving it out keeps the property. Before 5.0.0, leaving it out removed it, so a request property rejected every body that carried it and a response property left the discriminator out of the response.

`false` on a request property fails at decoration, naming the class and property: remove the option, because such a property rejected every body that carried it before too. A response that must keep leaving the discriminator out sets `shouldKeepDiscriminatorProperty: false` and `isResponse: true`.

On entity metadata used by GET and a write route, removing the option also brings the discriminator back into the GET response. To keep GET as it was, leave `false` and set `properties[route][BODY].isEnabled: false` on each write route. A read-only property with `false` now fails at import unless its write bodies are disabled.

A root-level `@ApiRouteCustom` body with `false` and a variant that requires the property through an `@ApiProperty*` decorator fails at startup, because every body answered `400`. Leave the option out or make the property optional. `validatorOptions.skipMissingProperties` stays allowed, and so does a variant that requires it only through raw `class-validator`, which startup cannot see and which still answers `400`. See [`@ApiPropertyObject`: Migration Notes](/docs/nestjs-crud-automator/api-reference/decorators/api-property/api-property-object#migration-notes).

## Generated Controller Method Types

`TApiControllerMethodName`, `TApiControllerMethodNameMap` and `TApiControllerTargetMethod` now give the names the methods have at runtime: `create`, `delete`, `get`, `getList`, `partialUpdate` and `update`. Before 5.0.0 they gave `${string}Create` and the like, so `controller.create` did not compile while `controller.xCreate` did, although no such method exists.

`TApiControllerMethod<E>` now declares `service.repository` as an optional `Repository<E>`. A value you annotate with this type no longer accepts a service whose `repository` is `private` or `protected` (TS2322): make the field public or drop the annotation. Services and controllers that do not use the type compile as before.

Call the methods by their runtime names. A cast on a value already typed with these types can go. `@ApiController` cannot change a class's type, so `new UserController(service).create` still does not compile: a decorated class still needs a type assertion or declaration merging. See [Controllers: Migration Notes](/docs/nestjs-crud-automator/core-concepts/controllers#migration-notes).

## Generated CREATE

Every generated `CREATE` runs in one transaction with its checks. Read [Authorization: Scoped CREATE](/docs/nestjs-crud-automator/guides/authorization#scoped-create) for the whole contract. These changes need work on your side:

- On a securable controller, declare a date and time primary key with `precision: 3` if its column can hold finer values, which PostgreSQL, CockroachDB, Oracle, and MSSQL `datetime2` do by default. The application fails at startup and names the column.
- Work on another `DataSource` in a subscriber does not roll back with the `CREATE`, so compensate for it yourself. A transaction scope on the same `DataSource` joins the `CREATE` and rolls back with it.
- `onAfterErrorCreate` runs after the rollback in a transaction a route or a function owns: read through `DATA.repository`, and move work that needs the transaction to `onBeforeErrorCreate`.
- A `CREATE` that loses a concurrency race answers `409` and leaves no row, so clients can send it again.
- A date and time primary key in the body that names a day or an hour the calendar does not hold, such as `2026-02-30T00:00:00.000Z`, `2026-04-31T10:00:00+03:00`, `2025-02-29 08:00:00Z` or `2026-01-01T24:00:00Z`, answers `400` with `at must be a valid ISO 8601 date-time` and no SQL runs. It used to be stored as the day or hour it rolls over into, such as March 2 for February 30. See [Impossible Calendar Dates](#impossible-calendar-dates).
- A create only inserts. A body that names the primary key of an existing row, soft deleted included, a cascade that would change an existing related row, and a `OneToMany` or inverse `OneToOne` item that names an existing row answer `409` `{ENTITY}_DUPLICATE_KEY` and change nothing, where they used to update that row and answer `201`. Send UPDATE or PARTIAL_UPDATE to change a row, and leave the key out of a create body unless it is new. In tests that stub `repository.save`, leave the key of a stored row out of the create body. See [Relations: Creating with Relations](/docs/nestjs-crud-automator/guides/relations#creating-with-relations).
- A CREATE route, generated or custom with `route.type` CREATE, whose `relations.request.load.include` enables a `OneToMany` or inverse `OneToOne` (no `@JoinColumn` on this side) fails at startup, because binding an existing row writes its foreign key. Remove the relation from the include and bind existing rows through the UPDATE of each related row, setting its to-one reference to the parent. The generated CREATE body no longer declares these relations, and a CREATE body that references existing rows through one (a key value, or an object with only the related primary key, alone or in an array) answers `400` `property <key> should not exist` when the host has no pipe or one with `forbidNonWhitelisted: true`; a pipe with only `whitelist: true` drops the key and the create answers `201`. New related rows with their own values still insert without a pipe. See the pipe table in [Relations: To-Many Request References](/docs/nestjs-crud-automator/guides/relations#to-many-request-references).
- A refused date and time primary key in a `CREATE` body now throws `ApiRequestValidationException`, so a filter that translates it with `ApiRequestValidationGetErrors` answers it in your own contract. The default body is unchanged. Each refused key is one failure, with its property path as `property` and the constraint `isDateFormatValue`, `createKeyNoTimeZone`, `createKeyFinerThanColumn` or `createKeyRepeatedHour`. See [Error Handling: Translating Request Validation Failures](/docs/nestjs-crud-automator/guides/error-handling#translating-request-validation-failures).

## Custom Routes On Securable Controllers

Startup now checks the custom routes of a securable controller. 4.x read the wrapper class that `@ApiController` returns, which holds no route, so the check never ran. An application with a route that breaks the rule fails to start with an error that names the controller and the method.

- Every `@ApiMethod(...)` and `@ApiRouteCustom(...)` route on a securable controller or its base classes declares `resource.action` and a `resource.entity` equal to the controller entity.
- The resolved mode of a custom route counts for the prerequisites, which is `security.authorization.mode` or `authorization.defaultMode` without it: a route that resolves to `hooks` needs a registered `@ApiAuthorizationPolicy(...)` for the entity, and a route that resolves to `iam` needs `policyNamespace`, `resourceDefinition` and document sources, also when the controller default is the other mode.

See [Authorization: Migration Notes](/docs/nestjs-crud-automator/guides/authorization#migration-notes).

## Unique Array Items

`isUniqueItems: true` on a request array now answers `400` for equal items, on every `@ApiProperty*` decorator and, when the application installs a `ValidationPipe`, on generated routes. An array whose items nest more than 64 levels answers `400` as well. Before 5.0.0 it only set `uniqueItems` in the OpenAPI schema. Set `isUniqueItems: false` on an array that accepts repeated values. See [Validation: Migration Notes](/docs/nestjs-crud-automator/guides/validation#migration-notes).

## Served Routes On Securable Controllers

On a controller decorated with `@ApiControllerSecurable()`, every route Nest serves goes through authorization, or the application does not start. Before 5.0.0 a plain `@Get` on such a controller, or a plain `@Post` override of a secured route, was served with no authorization: the policy was never asked and startup said nothing.

- A route with Nest decorators and without `@ApiMethod`, `@ApiRouteCustom` or generation now fails startup. The error names the controller, the method and the path. This includes `@All`, `@Sse`, a plain route inherited from a base class, a plain override of a generated or custom route, and a method of `generation.shouldWriteToController: false` exposed with a Nest decorator.
- Declare the route with `@ApiRouteCustom` or `@ApiMethod`, or move it to a controller that is not securable. There is no public or skip option, so a health check moves too.
- Route metadata written by hand counts only with `ApiAuthorizationGuard` or a subclass of it in `@UseGuards` on the method or the controller. A guard instance and `APP_GUARD` do not count.
- An application with a securable controller and no `ApiAuthorizationModule` now fails startup. With only plain routes `app.init()` fails, naming the controller and the module. With a generated, `@ApiMethod` or `@ApiRouteCustom` route Nest fails first, already on `compile()`, with its dependency error that names `ApiAuthorizationGuard`. Import the module, or remove `@ApiControllerSecurable()`. Before 5.0.0 such a controller started when it had only plain routes, and nothing validated it.
- A `@MessagePattern`, `@EventPattern` or `@SubscribeMessage` handler on a securable controller now fails startup, with or without `@ApiMethod`, because the caller of such a transport writes the payload the guard would read as the request, `user` included. Before 5.0.0 it answered with no authorization, or with `@ApiMethod` took the identity from the message. Move it to a controller that is not securable. A gateway with `@ApiControllerSecurable()` starts and denies every message.
- A handler replaced on the instance now fails startup, for example `this.report = this.report.bind(this)` in a constructor. Nest takes the guards from that function, so before 5.0.0 the route answered without authorization, generated routes included. Remove the assignment: Nest already calls a handler with `this` set to the controller. A request-scoped controller answers `403` per request instead, because its instance does not exist at startup.
- Route metadata written by hand without `route` now fails startup instead of answering `500` per request.
- `ApiAuthorizationBootstrapValidationService` now takes `MetadataScanner` and `ModulesContainer` as its second and third constructor arguments, which moves the others back. Code that calls the constructor by hand passes them in those positions.
- An override with no route decorator, a helper method and a controller that is not securable are unaffected.

A test harness that stubs `ApiAuthorizationRuntime` without the module is refused too. Import the module and replace the validation service and the runtime:

```typescript
import type { IApiAuthorizationDecision } from "@elsikora/nestjs-crud-automator";

import { ApiAuthorizationBootstrapValidationService, ApiAuthorizationModule, ApiAuthorizationRuntime, ApiSubscriberModule, EApiAuthorizationDecisionType, EApiAuthorizationMode, EApiAuthorizationPrincipalType, EApiPolicyEffect } from "@elsikora/nestjs-crud-automator";
import { Test } from "@nestjs/testing";

const allowDecision = (): IApiAuthorizationDecision<UserEntity> => ({
	action: "test",
	appliedRules: [],
	effect: EApiPolicyEffect.ALLOW,
	mode: EApiAuthorizationMode.HOOKS,
	permissions: [],
	policyId: "test",
	policyIds: [],
	principal: { attributes: {}, id: "test", roles: [], type: EApiAuthorizationPrincipalType.USER },
	resourceType: "UserEntity",
	trace: { decisionType: EApiAuthorizationDecisionType.EXPLICIT_ALLOW, mode: EApiAuthorizationMode.HOOKS },
	transforms: [],
});

const moduleReference = await Test.createTestingModule({
	controllers: [UserController],
	imports: [ApiAuthorizationModule.forRoot(), ApiSubscriberModule],
	providers: [UserService],
})
	.overrideProvider(ApiAuthorizationBootstrapValidationService)
	.useValue({})
	.overrideProvider(ApiAuthorizationRuntime)
	.useValue({ evaluate: async () => allowDecision() })
	.compile();
```

The replaced runtime returns a complete `IApiAuthorizationDecision`, with the enums rather than string literals: `EApiPolicyEffect.ALLOW` is `"Allow"`. A generated route runs the `transforms` of the decision on the response, so an object without them, such as `{ effect: "allow", principal: { id: "test" } }`, answers `500`. To test a `403`, return `EApiPolicyEffect.DENY` with `EApiAuthorizationDecisionType.EXPLICIT_DENY` in the trace. See [Authorization: Test Harness](/docs/nestjs-crud-automator/guides/authorization#test-harness).

This turns off every startup check, the one for plain routes and the path parameter comparison of each request included, so keep it in tests. The path values of a route are still checked: without startup the guard builds the rule of a custom route from its PARAMETERS DTO on its first request, so an upper-case UUID still returns `400` before the runtime and the handler, and a route whose DTO startup would refuse answers `500`. Before 5.0.0 such a test let a custom route pass the value as sent. A plain route still answers `403` there, because the class guard of `@ApiControllerSecurable()` stays on.

See [Authorization: Every Served Route Goes Through Authorization](/docs/nestjs-crud-automator/guides/authorization#every-served-route-goes-through-authorization).

## Routes Disabled On A Child Controller

`generation.isEnabled: false` on a child controller now stops the route the parent controller generates. Before 5.0.0 the child kept serving it over HTTP and in the OpenAPI document. The generated handler stays callable from the child's own methods, and a route the parent declares with `@ApiMethod` or `@ApiRouteCustom` under the same method name stays served.

If a child relied on the old behavior, remove `@ApiController` from the child so that it inherits the parent's routes and path as they are, replace it with `@Controller("own-path")` to serve those routes under a path of its own, or declare the route on the child with `@ApiRouteCustom`. See [`@ApiController`](/docs/nestjs-crud-automator/api-reference/decorators/api-controller/api-controller).

## Base Entity Type

`IApiBaseEntity` is now `object`. Its string index signature made every key of an `interface X extends IApiBaseEntity` a column: `getList({ limit: 10, page: 1 })` and `repository.update({ id }, { description })` did not compile, and `create({ notAColumn: 1 })` did.

Declare every key on the entity, and remove any cast you added to call `getList` or `update`. These also stop compiling:

- Index access to a key the entity does not declare. On a non-generic entity `(entity as Record<string, unknown>)[key]` is `TS2352`: use `keyof E`, `Reflect.get(entity, key)` or `as unknown as Record<string, unknown>`.
- A `declare module` augmentation of `IApiBaseEntity`, which gives `TS2300` even with `skipLibCheck`. Declare the shared keys on your own interface that extends `IApiBaseEntity`, and extend that in your entities.
- An `entity` option of `@ApiController` or of a property decorator, or an argument of `ErrorString` or `GenerateEntityInformation`, that is an instance of a class without a `name`, or `{ foo: 1 }`. Pass the class, or give the object a `name`. `{}` and any function still compile. `@ApiController` then throws when the class is decorated.
- A key `IApiEntity<E>` does not declare. It no longer extends `IApiBaseEntity` and has its own `name`.
- `ApiControllerTransformData<IX>(route.request, ...)` with the `request` of a `GET` or `GET_LIST` route on an interface entity, the same as on a class entity. Add `as Parameters<typeof ApiControllerTransformData<IX>>[0]`.

Inside code that is generic over `E`, `getList` needs `{ limit, page } as TApiControllerGetListQuery<E>`, and `scopeToOwner` with a literal needs `"ownerId" as keyof E` or no argument. See [Interfaces: Migration Notes](/docs/nestjs-crud-automator/api-reference/interfaces#migration-notes).

## Parent Classes Without A Name

`GenerateEntityInformation` and generated routes read the parent classes TypeORM maps and stop at the first parent class without a name. Columns and relations declared above such a class, for example by a mixin that returns `class extends Base {}`, are no longer read: TypeORM never mapped them. Name the class the mixin returns. A column declared again on a subclass is listed once, with the parent's declaration that TypeORM keeps.

See [Entities: Migration Notes](/docs/nestjs-crud-automator/core-concepts/entities#migration-notes).

## Explicit `@Expose` With `@ApiProperty*`

An explicit `@Expose` now keeps its name, groups and versions whatever the decorator order. Before 5.0.0 an `@ApiProperty*` decorator erased it silently when it ran after the `@Expose`: with `@ApiProperty*` above `@Expose`, with a lazy `entity` in either order, and when a child class redeclared a property whose `@Expose` is on the parent. Such a property now follows its `@Expose`, so its wire name changes. A request body is read from the exposed name, while validation errors name the declared property. `ClassSerializerInterceptor` and `instanceToPlain` write the exposed name. Remove the `@Expose` to keep the property name.

A response property is read from its property key and sent under its exposed name on every path, with or without `ClassSerializerInterceptor`, and the schema publishes the exposed name. Before 5.0.0 a generated route and `@ApiRouteCustom` without the interceptor read the exposed name and sent the property key. Swap the key and the name: `@Expose({ name: "id" }) gameId` becomes `@Expose({ name: "gameId" }) id`. A property under `@Exclude({ toPlainOnly: true })` is now left out of a response without the interceptor too.

A nested manual DTO on a generated route now keeps its `@Expose`, `@Exclude`, `@Transform` and `@Type`: a request uses the exposed name, an excluded property is neither stored nor returned, and a `@Transform` mask runs. A copied `toClassOnly` or undirected mask also runs on a generated write body, so a nested manual DTO used for both the request and the response now stores the masked value: give such a property a request DTO without the mask.

A request that sends a property of an `@ApiProperty*` decorator under its property key is now refused with a 400 naming the key, also next to the exposed name and in a nested object, an array item or a query. Before 5.0.0 the last of the two keys sent won, and under `exposeUnsetFields: false` the key alone bound. Send the exposed name. On the server, `plainToInstance` of a plain object that owns the property key is refused the same way, as a plain object is read as a request: a spread entity, a cached or raw-query row, or a plain object a handler returns under `@SerializeOptions({ type })` with `ClassSerializerInterceptor`. Pass a class instance, or build the object with the exposed names. A child class cannot expose another property under the property key of a renamed property of its parent, as class-transformer does not tell that check which class it converts: such a layout fails at startup, or at its first conversion when the child class is defined later. Rename one of them.

A named `@Expose`, own or inherited, next to `isExpose: false` or an `@Exclude` that applies to plain objects now fails at startup. `@Exclude({ toPlainOnly: true })` stays legal.

An application bundled with two copies of `class-transformer` now fails at decoration with `Cannot read class-transformer metadata`. The `class-transformer` peer range is `>=0.5.1 <0.5.2`. See [DTOs: `@Expose` Migration Notes](/docs/nestjs-crud-automator/core-concepts/dtos#expose-migration-notes).

## Request Body Limits

A request body deeper than 64 levels, or with an object holding more than 1000 keys, now answers `400` on every generated route, `@ApiRouteCustom` and `@ApiMethod` route, after the guards and before any pipe. The limits are fixed. Send a free-form object of more than 1000 keys as an array of entries. A plain Nest route is not covered, so bound it with the adapter's `bodyLimit`. See [Validation: Request Body Limits](/docs/nestjs-crud-automator/guides/validation#request-body-limits).

The same check answers `400` for a body with the key `__proto__`, `constructor`, `hasOwnProperty` or `prototype` at any depth, or with a NUL character in any string or key, on every database driver. Rename such keys in client payloads, and send binary data as base64. A row already stored with such keys is still read, on `GET` and on page and cursor `GET_LIST`. See [Validation: Reserved Keys And NUL](/docs/nestjs-crud-automator/guides/validation#reserved-keys-and-nul).

The refusal runs ahead of your pipe, so an `exceptionFactory` does not translate it. If your `400` bodies follow a contract of your own, such as codes only, add a filter that translates `ApiRequestValidationException`, from the exception itself or from its `cause` chain:

```typescript filename="filters/api-validation.filter.ts" copy
import { ArgumentsHost, BadRequestException, Catch } from "@nestjs/common";
import { BaseExceptionFilter, HttpAdapterHost } from "@nestjs/core";
import { ApiRequestValidationGetErrors, CorrelationIDNormalizeException } from "@elsikora/nestjs-crud-automator";

@Catch()
export class ApiValidationFilter extends BaseExceptionFilter {
	constructor(private readonly adapterHost: HttpAdapterHost) {
		super(adapterHost.httpAdapter);
	}

	catch(exception: unknown, host: ArgumentsHost) {
		// Leave RPC failures to the default handling
		if (host.getType() !== "http") {
			return;
		}

		const errors = ApiRequestValidationGetErrors(exception);
		// Use the same factory as your ValidationPipe's exceptionFactory
		const translated = errors ? new BadRequestException({ code: "VALIDATION_FAILED", errors: errors.flatMap((error) => Object.keys(error.constraints ?? {})) }) : exception;

		super.catch(CorrelationIDNormalizeException(translated, host, this.adapterHost), host);
	}
}
```

Register it with `app.useGlobalFilters(new ApiValidationFilter(app.get(HttpAdapterHost)))`. See [Error Handling: Translating Request Validation Failures](/docs/nestjs-crud-automator/guides/error-handling#translating-request-validation-failures).

## List Query Rules

A generated `GET_LIST` route validates its query against the published OpenAPI schema itself, with or without a host `ValidationPipe`, and typed and legacy routes apply the same rule. A request outside it returns `400` before any SQL runs. Change these requests if your clients send them:

- `orderDirection` is lowercase `asc` or `desc`, and `orderBy` and `orderDirection` are sent together or not at all.
- `limit` and `page` are required, and `limit` is at most 100. `isnull` and `notnull` take no value.
- An integer filter value is canonical decimal text and a boolean filter value is `true` or `false`, on typed and untyped filters alike, as in every other request value: `1e2`, `1.0`, `016` and a boolean `1` or `0` return `400`.
- Filter values follow the entity property: number bounds, string length, format and pattern. An empty or malformed number or uuid value, such as `amount[value]=`, returns `400 FILTER_NOT_VALID` instead of `500` on PostgreSQL or no rows on SQLite.
- A `date` column filter is `YYYY-MM-DD` text, a `time` column filter is `HH:mm:ss` text, and both are compared as written in every time zone. A date-time filter is the UTC instant `YYYY-MM-DDTHH:mm:ss.sssZ`, as `Date.prototype.toISOString()` writes it; a value without milliseconds, with an offset or without a zone returns `400`.
- A membership filter with one value, such as `status[operator]=in&status[values]=active`, now works.
- A boolean filter no longer offers `excl`: `EFilterOperationBoolean.EXCL` is removed, the operator enum in OpenAPI drops it, and `isActive[operator]=excl` returns `400`. It ran a text `LIKE` on a boolean column, which PostgreSQL rejects and SQLite and MySQL compare with the stored `1` or `0`. Use `ne` or `notin`.
- A filter or an order on a column the list response hides returns `400` before any SQL: a `select: false` column, `isExpose: false`, a disabled GET_LIST response side, a response guard the route's guard does not match, or a field a manual list response DTO leaves out. Filter by a field the response publishes. A typed `filter.fields` entry that enables such a column, or a manual QUERY DTO that publishes a filter group on one, fails at startup, and a PAGE route with a manual list response fails at startup until its generated filters match that response: set `request.query.filter.fields.<field>` to `{ isEnabled: false }`, leave the field out of a `REJECT` allowlist, or set `properties.getList.query.isEnabled: false` on the property. On a route without a `filter` section, the first two make its filter a typed plan. A field an authorization rule's `resultTransform` removes at request time is not covered, since the rule reads describe and TypeORM metadata: disable its filter yourself.
- A numeric enum filter takes the number the schema publishes, such as `level[operator]=eq&level[value]=1`, on every route and in every pipe mode. Only the exact text of a member stands for it, so `1.0` or the member's name returns `400`.
- A partial operator is held to the field's whole rule: `mail[operator]=cont&mail[value]=exam` on an email field returns `400`, with or without a host pipe.
- A TypeORM value transformer on a `date` column now receives `YYYY-MM-DD` text in `to`, never a `Date`. One that handles only a `Date` answers `500` where it used to answer `200`, and startup cannot detect it, so change your transformers to accept the text.
- Build server-side temporal values as Date. Strings must be UTC instants with Z. A Date built from zone-less text is read in the process TZ. A route subscriber may write a `Date` into a date-time filter, and a typed `defaultCondition` takes a `Date` or a UTC instant string; another string returns `400` from a subscriber and fails at startup in a `defaultCondition`.
- On a route without a typed `filter`, any query key its QUERY DTO does not publish returns `400` with `property <key> should not exist`, and a filter the route cannot apply never answers the unfiltered list (see [Query Validation Without a Typed Plan](/docs/nestjs-crud-automator/guides/filtering-and-sorting#query-validation-without-a-typed-plan)). This includes a cache-buster such as `_=1730000000` (jQuery `cache: false` and some HTTP clients add one), `utm_source` and other tracking parameters, a misspelled filter such as `nmae[value]=x`, and `id[...]` on the root primary key. Stop sending them, declare them on a manual QUERY DTO, or add a typed `filter` to filter by the primary key.
- A filter through a to-many relation, such as `tags.name[...]` on a `@OneToMany` or `@ManyToMany` property, returns `400`, and a generated DTO and OpenAPI no longer list it. It used to filter the list on these routes. Use a typed plan's to-one paths, a generated controller on the child table, or a custom method.
- A filter on a column that a manual QUERY DTO does not declare returns `400`. Declare its `[operator]` and `[value]` or `[values]` properties. The route used to apply it from entity metadata.
- On a manual QUERY DTO with `@Expose({ name: "sort" })` on `orderBy`, `orderBy=x` returns `400` with `property orderBy should not exist`. It used to skip the validators on the property. Send the exposed name.
- With a manual QUERY DTO, an incomplete filter group returns `400 FILTER_NOT_VALID`: `label[value]=x` or `label[operator]=eq` alone, both `[value]` and `[values]`, a value next to `isnull` or `notnull`, or a value key its operator does not take. `in`, `notin`, `excl` and their case-insensitive forms take `[values]`, `between` exactly two, and every other operator one `[value]`, as on a generated DTO. `eq` with `[values]` used to compare against the joined text, and an empty `[values]` used to answer no rows.
- A manual QUERY DTO that publishes a filter group the route cannot apply, on an unknown column, the root primary key, a hidden column, a bare relation, a deep path or a to-many path, fails at startup and names the controller, the DTO and the key. So does a filter property exposed under another name, such as `@Expose({ name: "q" })` on `label[value]`, which used to return every row.

A fractional `multipleOf` on a request number is now an exact decimal check, in filter values and request bodies alike. With `multipleOf: 0.01`, `0.1` passes and `1.005` returns `400`; it used to reject every value, and a step of `2.5` checked multiples of `2`. The constraint name stays `isDivisibleBy`.

`DTO_GENERATE_CONSTANT.MINIMUM_FILTER_PROPERTIES` is removed. A typed filter config no longer needs a cast to list comparison operations on a `string` date, time or decimal property, and a typed `defaultCondition` on a `date` or `time` field takes text, not a `Date`. See [Filtering and Sorting: Migration Notes](/docs/nestjs-crud-automator/guides/filtering-and-sorting#migration-notes) and [Typed Plan Migration Notes](/docs/nestjs-crud-automator/guides/filtering-and-sorting#typed-plan-migration-notes).

## Service Repositories Checked At Bootstrap

A singleton `@ApiController` with an enabled generated route fails at application bootstrap unless `service.repository` is a TypeORM repository. A controller whose generated routes are all disabled is not refused. Before 5.0.0, the service repository was not checked. The error names the controller, the entity, and the missing part. A repository from a second installed copy of TypeORM and a Proxy-wrapped repository pass. Nest runs no bootstrap hook on a request-scoped controller; see [Testing: Request-Scoped Controllers](/docs/nestjs-crud-automator/guides/testing#request-scoped-controllers).

A plain-object repository mock or a mocked service in a test of such a controller now fails at bootstrap. Provide a real repository of an in-memory DataSource and stub its methods instead. An entity with PostgreSQL column types, which SQLite rejects, needs no database: build the metadata of a PostgreSQL DataSource without connecting, and pass its repository, or an object with its `metadata` and `manager`. See [Testing: PostgreSQL-Typed Entities Without A Connection](/docs/nestjs-crud-automator/guides/testing#postgresql-typed-entities-without-a-connection) and [Testing: Migration Notes](/docs/nestjs-crud-automator/guides/testing#migration-notes).

## CURSOR Routes Checked At Bootstrap

A CURSOR GET_LIST route on a database other than PostgreSQL, or with an order field whose storage CURSOR cannot prove, fails at application bootstrap with an error that names the route and the active driver. Before 5.0.0, the application started and every request to the route answered `500`. On a production database CURSOR cannot serve, switch such a route to PAGE. In a test, keep the route and run it on a PostgreSQL DataSource, which needs no connection: see [Testing: CURSOR Controllers](/docs/nestjs-crud-automator/guides/testing#cursor-controllers). See also [Pagination: Migration Notes](/docs/nestjs-crud-automator/guides/pagination#migration-notes).

## Date Body Values

Under a host `ValidationPipe`, a request value of an `@ApiPropertyDate` property, or a date property described with `@ApiPropertyDescribe`, takes the same published form as its list filter. That holds on generated CREATE, UPDATE, and PARTIAL_UPDATE bodies and on custom routes. Anything else returns `400` before any SQL runs:

- A `DATE` value is `YYYY-MM-DD` text for a day that exists and stays that text. With `transform: true` it used to become a `Date` at UTC midnight, which stored the previous day in time zones west of UTC. A TypeORM value transformer on a `date` column now receives the text in `to` on writes too.
- A `TIME` value is `HH:mm:ss` text and stays text. A valid time of day used to return `400`.
- A `DATE_TIME` value is the UTC instant `YYYY-MM-DDTHH:mm:ss.sssZ`, as `Date.prototype.toISOString()` writes it. Any text `new Date()` could read used to pass, including `March 1 2026`, `1`, zone-less text read in the process time zone, and epoch numbers.
- A one-element array on a single property returns `400`, and so does a date or date-time in year `0000`. Bodies and filters accept years 0001 to 9999.
- The rule holds under `enableImplicitConversion`. A `DATE_TIME` property typed `Date` used to accept anything class-transformer turned into a `Date`, and a `DATE` or `TIME` property typed `Date` used to refuse a valid value.
- The message is `<property> must be in <form> format` with constraint `isDateFormatValue`, instead of `<property> must be a Date instance` with `isDate`.

Type `DATE` and `TIME` properties of request DTOs as `string`, and change custom handlers that call `Date` methods on them. Without a host pipe a generated route does not check the body, as before: it passes the text to TypeORM, so an impossible date such as `2026-02-30` can be stored as another day, stored as sent, or answer `500`. See [Impossible Calendar Dates](#impossible-calendar-dates).

`@ApiPropertyString` with `format: EApiPropertyStringType.DATE` now fails at decoration, on request and response properties, and an entity property described with `@ApiPropertyDescribe({ type: EApiPropertyDescribeType.STRING, format: EApiPropertyStringType.DATE })` fails when a generated DTO is built from it, naming that DTO. It accepted any text `new Date()` could read and turned it into a `Date`. On a DTO use `@ApiPropertyDate` with `EApiPropertyDateType.DATE`, or `DATE_TIME` for an instant. On an entity use `@ApiPropertyDescribe({ type: EApiPropertyDescribeType.DATE, format: EApiPropertyDateType.DATE, identifier: EApiPropertyDateIdentifier.DATE })`.

## Impossible Calendar Dates

The entry points below check that date text names a day and a time of day that exist. February 30, April 31, February 29 in a common year, month `13`, hour `24`, and minute or second `60` answer `400` before any SQL, with the body of that entry point, instead of rolling over into the next day or month as a JavaScript `Date` would:

| Entry point                                                              | Body                                                                           |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| A date and time primary key in a generated `CREATE` body                 | `message: ["<key> must be a valid ISO 8601 date-time"]`                        |
| A `DATE` or `DATE_TIME` property of a body under a host `ValidationPipe` | `message: ["<property> must be in <form> format"]`                             |
| A `DATE` or `DATE_TIME` path value                                       | `message: ["<parameter> must be in <form> format"]`                            |
| A `GET_LIST` filter value                                                | `FILTER_NOT_VALID`, or the QUERY DTO message on a route without a typed filter |
| A CURSOR token value                                                     | `CURSOR_NOT_VALID`                                                             |

The day is checked as the text writes it, before an offset moves the instant, so `2026-02-28T23:00:00-05:00` is accepted and names March 1 in UTC. Of these, only the date and time primary key of a `CREATE` body used to roll over; the others already refused such values and now share the check.

The library does not check these, so validate them yourself:

- A `date` primary key in a generated `CREATE` body. The generated body DTO does not declare a primary key, so a host pipe does not check it either, and the route writes it from the request. SQLite stores `2026-02-30` as sent, and the row cannot be reached through its key afterwards; PostgreSQL answers `500`.
- `DATE` and `DATE_TIME` properties of a generated write body without a host `ValidationPipe`. The route passes the text to TypeORM unchecked. On SQLite a `DATE_TIME` value such as `2026-02-30T00:00:00.000Z` is stored as the day it rolls over into, month `13` as an unreadable value, and a `DATE` value as sent; on PostgreSQL a `DATE_TIME` value rolls over or answers `500`, and a `DATE` value answers `500`.

IAM conditions compare text and do not read dates.

## Path Values

A generated route, and a securable custom route with a PARAMETERS DTO in IAM or HOOKS mode, check each path value against its column before authorization and before any query, with or without a host `ValidationPipe`. A value outside the column rule returns `400` instead of a database error or `404`:

- Integer text is canonical decimal text: `/items/016` and `/items/-0` return `400`.
- A UUID is lower-case: `/items/AAAAAAAA-...` returns `400` with `id must be a lower-case UUID` instead of being lower-cased, because a database reads either letter case as one key while a policy compares text. Send the lower-case UUID.
- From 5.0.1 the same holds for the body and the query: a UUID that is not lower-case returns `400` (`uuidNotCanonical`, `ownerId must be a lower-case UUID`) on every route of `ApiMethod`, with or without a host pipe, and a generated GET_LIST filter returns `400 FILTER_NOT_VALID`. 5.0.0 lower-cased them silently.
- A `DATE_TIME` path value is the published `YYYY-MM-DDTHH:mm:ss.sssZ` text: `/stamps/2026-11-02T10:00:00Z` and the microsecond text `/stamps/2026-11-02T10:00:00.123456Z` return `400`. A row whose `timestamptz` key holds microseconds cannot be addressed by a generated route; keep such keys at a precision of 3 or less.
- A decimal, numeric, float, double or money column as a path value fails at startup on a securable route, in HOOKS mode as in IAM mode. Use an integer, UUID or text key.

A securable `@ApiRouteCustom` or `@ApiMethod` route with a path parameter must give its handler and its policy the value authorization saw, in IAM and HOOKS mode alike, or the application fails at startup with an error that names the controller, method, and parameter. The path parameters are those of the whole path: the global prefix, the `RouterModule` path, nested modules included, the controller path, and the route path.

- Declare a `dto[EApiDtoType.PARAMETERS]` that describes every path parameter, preferably with `ApiPropertyCopy`, or with an `ApiProperty*` decorator. An `@ApiMethod` route with a path parameter becomes an `@ApiRouteCustom` route with that DTO. On a HOOKS route only `ApiPropertyCopy` and `ApiProperty*` count, so replace a bare `@IsInt() @Type(() => Number)` or `@IsString()`.
- Describe the parameters of the global prefix and the `RouterModule` path too; a route `setGlobalPrefix` excludes has no prefix parameters. A generated route under such a parameter becomes an `@ApiRouteCustom` route with a PARAMETERS DTO that describes it, because `pathScope` binds only controller path parameters.
- On an IAM route, generated or custom, that neither lists nor creates, serve each `resourcePath` placeholder as a path parameter: move a generated GET, UPDATE, PARTIAL_UPDATE, or DELETE route that lacks one to `@ApiRouteCustom` under that path parameter copied with `ApiPropertyCopy`, or authorize the route in HOOKS mode. Such a placeholder rendered as `*` before, so a Deny on a value of it never matched. Declaring the route a list (`route.type` `GET_LIST` or the action `list`) keeps the placeholder only if the handler applies `decision.scope.where` to its query, and its IAM action becomes `<policyNamespace>:list`, so a separate action such as `export` merges into `list`.
- Replace a wildcard (`*`, `*name`, `{*name}`) in any part of a securable route's path with named path parameters.
- Remove pipes other than `ValidationPipe`, and the `expectedType`, `transformerPackage`, and `validatorPackage` options of a `ValidationPipe`, from `@UsePipes` on the method and the controller, and pipes from `@Param`, such as `@Param("id", ParseIntPipe)`; the PARAMETERS DTO converts the value. A global pipe of the host is not checked, so keep it to `ValidationPipe`.
- Give `@Param("id")` a type that compiles to `String` or `Object`: `string`, `unknown`, `any`, or a union, not `number` or a class. Read a converted value from `@Param()` typed as the PARAMETERS DTO under `ValidationPipe({ transform: true })`.

A request whose `request.params` holds a path parameter startup did not record for its route, such as one an earlier guard or middleware adds, answers `500` before the policy, the handler, and any query.

A HOOKS policy now reads `context.parameters` as the canonical text, so `/016` and an upper-case UUID return `400` before it runs.

On a securable route the guard refuses the value ahead of your pipe, with `ApiRequestValidationException`, so the filter shown under [Request Body Limits](#request-body-limits) translates it too. See [Validation: Migration Notes](/docs/nestjs-crud-automator/guides/validation#migration-notes).

## IAM Conditions On Boolean Columns

An IAM `resource.*` condition, or an exact row-scoped Deny pattern such as `bool:item/true` for `resourcePath: "bool:item/{isFeatured}"`, on a boolean column compiles only for `true`, `false` or that exact text, which now bind as booleans. A boolean column is one TypeORM types as `boolean`, `bool` or `bit`, or one described as `BOOLEAN`, at any step of `queryPath`: on the entity, inherited from a parent class, inside an embedded entity, or any number of relations away, with or without `@ApiPropertyDescribe`. Such a value used to bind as text, so on SQLite a Deny on `"true"` excluded no row, on MySQL it excluded the other rows, and on PostgreSQL an Allow on `"yes"` matched the rows holding `true`, which the in-memory evaluator rejects. Any other value, such as `"1"`, `"TRUE"`, `"yes"` or the number `1`, no longer compiles: an Allow statement with it is not matched, and a matched Deny with it denies the whole request with `403`. Write `true` or `false` in these conditions and patterns.

A `queryPath` that the TypeORM metadata of the resource entity cannot resolve to a column, such as a misspelled property or a path that ends on a relation, no longer compiles either: an Allow statement with it is not matched, and a matched Deny with it denies the whole request with `403`. Fix the `queryPath` in `fields`. The same holds for every `resource.*` key of a resource entity that no TypeORM decorator maps, such as one registered only through an `EntitySchema`; its keys used to bind values as text.

A list, object or `null` condition operand is logged as a warning when the document loads and fails closed: the key fails for an Allow and holds for a Deny, whose other keys still decide whether it matches. It used to answer `500`. See [Allow Scopes](/docs/nestjs-crud-automator/guides/authorization#allow-scopes).

## IAM Conditions Through Missing Relations

A `resource.*` condition whose `queryPath` crosses a relation now treats a row with that relation missing as the in-memory evaluator does: as a missing key, at any depth of to-one relations. A Deny `StringEqualsIfExists` such as `owner.company.name` used to keep rows whose owner or company is `NULL`, which the simulator denied; it now hides them, and keeps only rows where the relation exists and the column differs or is `NULL`. An Allow `StringEqualsIfExists` on such a path now also includes rows with the relation missing, which it used to hide. On root and embedded columns nothing changes. Two Allow keys on one `queryPath` in one statement now both apply: different values allow no row, where the last key used to win. A `StringEqualsIfExists` through a relation to an entity without a primary column no longer compiles.

A relation is missing when its foreign key is `NULL`, when the row it names is soft-deleted, or when the key names no row because no foreign key constraint holds it; a Deny `StringEqualsIfExists` now hides all three and an Allow `StringEqualsIfExists` now includes all three, so isolate tenants with `StringEquals`.

A loaded resource, as in `ApiAuthorizationSimulator` with `resource` or a runtime call from your own code, is now read through each field's `queryPath`. A field `resource.ownerId` with `queryPath: "owner.id"` used to read a property named `ownerId`, so it disagreed with the scope; load the relations a `queryPath` crosses. A `resource.*` key that no field maps now fails closed in memory: it fails for an Allow and holds for a Deny. A `resourcePath` placeholder that names a field renders the value at its `queryPath`. See [Deny Semantics](/docs/nestjs-crud-automator/guides/authorization#deny-semantics).

## IAM Fields Through To-Many Relations

A `resourceDefinition` field whose `queryPath` crosses a OneToMany or ManyToMany relation, such as `tags.name`, now stops startup with an error that names the field and the relation. Such a path has no single value: a Deny `StringEquals` on it used to serve rows whose related rows matched, and an Allow `StringEqualsIfExists` matched rows with no related row. A definition that skips startup validation, as one passed to `ApiAuthorizationSimulator`, fails closed: an Allow key on it is not matched and a Deny key on it holds. Map a column of the resource or of a to-one relation instead, such as a denormalized flag. See [Deny Semantics](/docs/nestjs-crud-automator/guides/authorization#deny-semantics).

## Generated Row Routes And Path Parameters

Generated GET, PATCH, PUT and DELETE now address every primary key column. Before 5.0.0 they took only the first, so most rows of a composite key could not be reached, and writes under `/parent/:parentId/item/:id` ignored `parentId`: they changed or deleted a row of another parent. A single-column key without path parameters keeps its route and OpenAPI document byte for byte.

**A composite key.** The route becomes `/:tenantId/:id`. To keep a shorter path, name its columns on the controller:

```typescript
@ApiController<WalletTransactionEntity>({
	entity: WalletTransactionEntity,
	path: "wallet-transactions",
	rowPath: { fields: ["id"] },
	routes: {},
})
```

A `timestamptz` key column with a precision above 3, an unset precision, another date and time type, or a `datetime` with a precision above 3 now fails at startup while it is in the path. A `datetime` with no precision or precision 0 to 3 stays allowed on SQLite, MySQL and MariaDB. Leave it out with `rowPath`, as above, or change the column. On such a route, more than one matching row answers `500`, and a write answers `500` before any change when a left-out date and time column holds a finer value than a millisecond. Before 5.0.0, PATCH and PUT inserted a duplicate row there, and DELETE answered `204` without deleting.

**The route `read` key is removed.** Move the mapping to the controller as `pathScope`. It now binds the parameters on every generated route:

```typescript
// Before
@ApiController<GameEntity>({
	entity: GameEntity,
	path: "providers/:providerKey/games",
	routes: {
		[EApiRouteType.GET]: { read: { scope: { parameters: [{ parameter: "providerKey", field: "providerId" }] } } },
		[EApiRouteType.GET_LIST]: { read: { scope: { parameters: [{ parameter: "providerKey", field: "providerId" }] } } },
	},
})

// After
@ApiController<GameEntity>({
	entity: GameEntity,
	path: "providers/:providerKey/games",
	pathScope: { parameters: [{ parameter: "providerKey", field: "providerId" }] },
	routes: {},
})
```

**Every controller path parameter must be bound** when a generated route is enabled, so a controller that starts today with an unbound, wildcard or optional parameter fails at startup. Add it to `pathScope`, or disable the generated routes. A controller of custom routes only, with all six generated routes disabled, keeps any path.

**A bound field leaves the generated body.** CREATE takes the value from the path. A body naming the bound field is refused by a `ValidationPipe` with `forbidNonWhitelisted`; with any other pipe or none, a different value answers `400` and an equal one passes.

**A key column in a PATCH or PUT body must equal the path.** Before 5.0.0, a body such as `{ "id": "I2" }` on `PATCH /parent/P1/item/I1` moved the row `I2` of another parent into `P1`, and a composite key column in the body inserted a duplicate row. Now a differing key value, or a key column the path leaves out, answers `400` with nothing changed, whatever pipe runs and even when a request transformer pins the key in the body. A key or bound value in the body must be the string the path carries, a date and time in its canonical UTC millisecond form, so a number such as `{ "id": 5 }` on `/item/5` or an epoch for a date key also answers `400`. A date and time key column that a relation sets in a CREATE body, such as `at` in a `slot` over `(tenantId, at)`, is checked and parsed like the column itself. A relation that joins a bound column and other columns, such as `(tenantId, parentId)`, keeps its other columns: the route writes them as the entity's own, so each must be declared on the entity. Such a relation must be an object: `null` or a single value answers `400`; clear it with its own column, such as `{ "parentId": null }`.

**A relation agrees with the entity's own columns.** On every generated write, with or without a path binding, a relation whose join columns the entity declares, over one column or several, is written through the entity's own columns. A relation value that differs from the entity's own column, as the body, a transformer or the path sets it, now answers `400` before the write; before 5.0.0 the relation's value silently won, so a body could store another tenant than a transformer pinned, or a relation over a key column wrote the row and then answered `404` or `500`. A join column the body does not set takes the value of the relation the route writes, after route subscribers and request transformers, and on PATCH and PUT a key column keeps the row's value; a relation they remove sets no column. A relation object must name each join column by a single value, so an object or an array in its place answers `400`. A relation object with other values of the related row still reaches a cascade. `null` for a relation over a key column now answers `400`, because it cannot be cleared.

**A relation is published as the value of the column it references.** A generated BODY DTO used to publish every relation as a UUID scalar. A relation over one column now has the type and format of its referenced column, so a relation to a `varchar` key is a string, and the route accepts that value, a `Date` a transforming pipe made from it, or an object naming it; an object naming none of the join columns answers `400`. It leaves the body where its column is bound by the path or is a key column on PATCH and PUT. A relation over several join columns is now an object of the join columns the client may write, each with the type and format of the related column; a column the path binds, and every key column on PATCH and PUT, leaves it. Describe each referenced column, of a relation over one column too, with `@ApiPropertyDescribe` on the related entity, or startup fails. Regenerate clients built from the old schema.

**Names.** The PARAMETERS DTO of a bound route is `<Prefix><Route>ParametersDTO`, without a signature. `IApiControllerPropertiesRouteBaseRead`, `IApiControllerPropertiesRouteReadScope`, `IApiControllerPropertiesRouteReadScopeParameter` and `TApiControllerReadDirectScalarField` are replaced by `IApiControllerPropertiesPathScope`, `IApiControllerPropertiesPathScopeParameter` and `TApiControllerPathDirectScalarField`.

See [Controllers: Row Paths And Composite Keys](/docs/nestjs-crud-automator/core-concepts/controllers#row-paths-and-composite-keys).
