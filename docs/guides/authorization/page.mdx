# Authorization

NestJS CRUD Automator ships with a single authorization pipeline and two first-class authoring modes:

- `hooks`: entity-scoped `@ApiAuthorizationPolicy({ entity })` classes
- `iam`: storage-agnostic policy attachments and IAM documents

`@ApiControllerSecurable()` takes no options. It enables the authorization pipeline for a controller, but the selected mode and all authorization configuration live in `@ApiController({ authorization: ... })`. A generated route can override the controller default with `routes[routeType].security.authorization.mode`. `@ApiMethod` custom routes use `metadata.security.authorization.mode`, while `@ApiRouteCustom` uses top-level `security.authorization.mode`. A route without a mode falls back to `authorization.defaultMode`. Each route still runs in exactly one mode.

## Module Setup

Import `ApiAuthorizationModule` once. Use `forRoot()` for plain value-based setup. Use `forRootAsync()` when `principalResolver`, `hookPermissionSources`, `iam.attachmentSources`, or `iam.documentSources` must come from Nest DI.

```typescript filename="app.module.ts" copy
import type { IApiAuthorizationPrincipal, IApiHookPermissionSource, IApiPolicyAttachmentSource, IApiPolicyDocumentSource, IApiResolvedPolicyAttachments } from "@elsikora/nestjs-crud-automator";

import { Module } from "@nestjs/common";
import { TypeOrmModule } from "@nestjs/typeorm";

import { ApiAuthorizationModule, EApiAuthorizationCacheMode, EApiAuthorizationPrincipalType, EApiPolicyEffect, EApiPolicySourceType, AuthorizationResolveDefaultPrincipal } from "@elsikora/nestjs-crud-automator";

const hookPermissionSource: IApiHookPermissionSource = {
	async getPermissions(principal: IApiAuthorizationPrincipal): Promise<ReadonlyArray<string>> {
		const permissions = principal.claims?.permissions;

		return Array.isArray(permissions) ? permissions.filter((value): value is string => typeof value === "string") : [];
	},
};

const iamAttachmentSource: IApiPolicyAttachmentSource = {
	async getAttachments(principal): Promise<IApiResolvedPolicyAttachments> {
		return {
			attachments: [
				{
					policyId: "user-items",
					principalId: principal.id,
					principalType: principal.type,
				},
			],
			boundaries: [],
		};
	},
};

const iamDocumentSource: IApiPolicyDocumentSource = {
	async getDocumentsByIds(ids) {
		return ids.map((id) => ({
			document: {
				Statement: [
					{
						Action: ["admin:item:list", "admin:item:read"],
						Condition: {
							StringEquals: {
								"resource.operatorId": "operator-1",
							},
						},
						Effect: EApiPolicyEffect.ALLOW,
						Resource: ["gameport:admin:item/*"],
						Sid: "AllowOperatorItems",
					},
				],
				Version: "2012-10-17",
			},
			id,
			namespace: "admin:item",
			sourceType: EApiPolicySourceType.MANAGED,
			version: "2026-03-14",
		}));
	},
};

@Module({
	imports: [
		TypeOrmModule.forRoot(/* ... */),
		ApiAuthorizationModule.forRoot({
			cache: {
				mode: EApiAuthorizationCacheMode.SOURCE_FIRST,
			},
			hookPermissionSources: [hookPermissionSource],
			iam: {
				attachmentSources: [iamAttachmentSource],
				documentSources: [iamDocumentSource],
			},
			principalResolver: {
				resolve(user) {
					if (!user || typeof user !== "object" || !("account" in user)) {
						return AuthorizationResolveDefaultPrincipal(user);
					}

					const payload = user as {
						account: { id: string; operatorId: string };
						access: { permissions: Array<string>; roles: Array<string> };
					};

					return {
						attributes: { operatorId: payload.account.operatorId },
						claims: { permissions: payload.access.permissions },
						id: payload.account.id,
						roles: payload.access.roles,
						type: EApiAuthorizationPrincipalType.USER,
					};
				},
			},
		}),
	],
})
export class AppModule {}
```

The built-in `AuthorizationResolveDefaultPrincipal()` maps `request.user` into an `IApiAuthorizationPrincipal` using `id | uuid | email`, `roles | role`, `groups | group`, and `claims`. The principal intentionally does not contain permissions or policy attachments:

- hooks mode resolves permissions through `hookPermissionSources`
- IAM mode resolves attachments and documents through `iam.attachmentSources` and `iam.documentSources`

### Authorization resolver cache modes

`ApiAuthorizationModule` defaults to `EApiAuthorizationCacheMode.SOURCE_FIRST`. Every authorization evaluation reads hooks permissions, IAM attachments, and requested IAM documents from the configured sources. The resolver caches neither read nor write cross-request entries in this mode, including empty results, so a later source error is propagated instead of falling back to stale data. The explicit `SOURCE_FIRST` setting in the example is optional and documents the intended multi-instance behavior.

Use bounded `MEMORY` mode only as an explicit single-process optimization:

```typescript
ApiAuthorizationModule.forRoot({
	cache: {
		maxEntries: 1_000,
		mode: EApiAuthorizationCacheMode.MEMORY,
		ttlMs: 30_000,
	},
	// principalResolver and sources...
});
```

`ttlMs` and `maxEntries` must be positive safe integers or bootstrap fails. TTL starts when an entry is stored, and the oldest entry is evicted when that resolver cache reaches its limit. Each hooks permission, IAM attachment, and IAM document cache has its own limit. Memory is process-local and requires explicit invalidation when a backing change must become visible before TTL expiry; it does not provide multi-instance consistency.

Do not treat Redis Pub/Sub invalidation around independent process-local maps as a correctness boundary, and do not add an implicit memory fallback when a source fails. Multi-instance correctness requires every resolver to read an authoritative source in `SOURCE_FIRST` or a separately designed shared-cache contract outside Automator.

Hooks policy-rule caching is separate from these resolver modes. It remains disabled by default and is configured through `ApiAuthorizationPolicyRegistry.configureCache()` or a policy's `cache` option.

### `forRootAsync()` for DI-backed sources

Use `forRootAsync()` when your resolver or IAM sources depend on `Repository`, `DataSource`, or other Nest providers. The authorization module supports `imports`, `inject`, `useFactory`, `useClass`, and `useExisting`. The public API also exports `IApiAuthorizationModuleAsyncOptions` and `IApiAuthorizationModuleOptionsFactory` for typed Nest module wiring.

```typescript filename="authorization/authorization.module.ts" copy
import type { IApiAuthorizationPrincipal, IApiAuthorizationPrincipalResolver, IApiPolicyAttachmentSource, IApiPolicyDocumentRecord, IApiPolicyDocumentSource, IApiResolvedPolicyAttachments } from "@elsikora/nestjs-crud-automator";

import { Injectable, Module } from "@nestjs/common";
import { InjectRepository, TypeOrmModule } from "@nestjs/typeorm";
import { Repository } from "typeorm";

import { ApiAuthorizationModule, AuthorizationResolveDefaultPrincipal, EApiAuthorizationPrincipalType, EApiPolicySourceType } from "@elsikora/nestjs-crud-automator";

@Injectable()
class DbPrincipalResolver implements IApiAuthorizationPrincipalResolver {
	public resolve(user: unknown): IApiAuthorizationPrincipal {
		return AuthorizationResolveDefaultPrincipal(user);
	}
}

@Injectable()
class DbAttachmentSource implements IApiPolicyAttachmentSource {
	public constructor(
		@InjectRepository(PolicyAttachmentEntity)
		private readonly repository: Repository<PolicyAttachmentEntity>,
	) {}

	public async getAttachments(principal: IApiAuthorizationPrincipal): Promise<IApiResolvedPolicyAttachments> {
		const rows = await this.repository.find({
			where: { principalId: principal.id },
		});

		return {
			attachments: rows.map((row) => ({
				policyId: row.policyId,
				principalId: row.principalId,
				principalType: EApiAuthorizationPrincipalType.USER,
			})),
			boundaries: [],
		};
	}
}

@Injectable()
class DbDocumentSource implements IApiPolicyDocumentSource {
	public constructor(
		@InjectRepository(PolicyDocumentEntity)
		private readonly repository: Repository<PolicyDocumentEntity>,
	) {}

	public async getDocumentsByIds(ids: ReadonlyArray<string>): Promise<ReadonlyArray<IApiPolicyDocumentRecord>> {
		const rows = await this.repository.find();

		return rows
			.filter((row) => ids.includes(row.id))
			.map((row) => ({
				document: row.document,
				id: row.id,
				namespace: row.namespace,
				sourceType: EApiPolicySourceType.DATABASE,
				version: row.version,
			}));
	}
}

@Module({
	exports: [DbAttachmentSource, DbDocumentSource, DbPrincipalResolver],
	imports: [TypeOrmModule.forFeature([PolicyAttachmentEntity, PolicyDocumentEntity])],
	providers: [DbAttachmentSource, DbDocumentSource, DbPrincipalResolver],
})
class AuthorizationSourcesModule {}

@Module({
	imports: [
		AuthorizationSourcesModule,
		ApiAuthorizationModule.forRootAsync({
			imports: [AuthorizationSourcesModule],
			inject: [DbAttachmentSource, DbDocumentSource, DbPrincipalResolver],
			useFactory: (attachmentSource: DbAttachmentSource, documentSource: DbDocumentSource, principalResolver: DbPrincipalResolver) => ({
				iam: {
					attachmentSources: [attachmentSource],
					documentSources: [documentSource],
				},
				principalResolver,
			}),
		}),
	],
})
export class AppModule {}
```

If you prefer Nest factory classes, the same setup can be expressed with `useClass` or `useExisting`.

## Controller Opt-In and Mode Selection

Use both decorators together on any secured controller:

```typescript filename="controllers/user.controller.ts" copy
import { EApiRouteType } from "@elsikora/nestjs-crud-automator";

import { EApiAuthorizationMode, ApiController, ApiControllerSecurable } from "@elsikora/nestjs-crud-automator";

@ApiControllerSecurable()
@ApiController<UserEntity>({
	authorization: {
		defaultMode: EApiAuthorizationMode.HOOKS,
	},
	entity: UserEntity,
	path: "users",
	routes: {},
})
export class UserController {
	constructor(public service: UserService) {}
}
```

Bootstrap validation fails fast when:

- `@ApiControllerSecurable()` is present but the controller has no `authorization` block
- a controller declares `authorization` but is missing `@ApiControllerSecurable()`
- the selected mode is not `hooks` or `iam`
- a custom `@ApiMethod(...)` or `@ApiRouteCustom(...)` route of the controller, declared on the class or inherited from a base class, has no `resource.action` or has a `resource.entity` other than the controller entity
- a custom route resolves to `hooks` and no `@ApiAuthorizationPolicy(...)` is registered for the entity, or resolves to `iam` and the controller does not meet the IAM prerequisites, also when the controller default is the other mode
- the controller serves a route that skips authorization
- the application has a securable controller and does not import `ApiAuthorizationModule`
- the controller has a `@MessagePattern`, `@EventPattern` or `@SubscribeMessage` handler, with or without `@ApiMethod`
- a handler is replaced on the controller instance by a function that does not carry its authorization
- route metadata written by hand has no `route`

The closest definition of a method name is the one checked. An override with `@ApiMethod(...)` or `@ApiRouteCustom(...)` is checked in place of the route of the base class, and an override with no route decorator at all is not a route. A plain `@Post` override is served without authorization, so it fails startup, as described below. A custom route without a mode resolves to `defaultMode`, and the prerequisites of that mode apply.

### Every Served Route Goes Through Authorization

On a controller decorated with `@ApiControllerSecurable()`, every handler Nest serves goes through authorization, or the application does not start. Generated routes, `@ApiMethod` and `@ApiRouteCustom` qualify. A route declared only with Nest decorators, such as `@Get`, `@Post`, `@All`, `@Sse`, or `@Redirect` next to a route decorator, does not. The rule also covers a plain route inherited from a base class and a plain override of a generated or custom route.

```text
Controller "UserController" method "report" serves GET /users/report without authorization: declare it with @ApiRouteCustom or @ApiMethod, or move it to a controller that is not securable. Route metadata written by hand also needs ApiAuthorizationGuard or a subclass of it in @UseGuards on the method or the controller; a guard instance and APP_GUARD do not count
```

- There is no public or skip option. A health check or another open route moves to a controller without `@ApiControllerSecurable()`, where plain routes keep working.
- An override with no route decorator is not a route: Nest does not serve it, and the application starts. Helper methods and accessors are ignored.
- Route metadata written by hand counts only with `ApiAuthorizationGuard` or a subclass of it in `@UseGuards` on the method or the controller. A guard instance and `APP_GUARD` do not count. Metadata alone never runs the guard. `@UseGuards(ApiAuthorizationGuard)` on the class plus an `@ApiMethod` route evaluates the policy twice, because `@ApiMethod` attaches the guard as well.
- An application with a securable controller and no `ApiAuthorizationModule` does not start. With only plain routes `app.init()` fails, and the error names the controller and the module. This covers a bare `@Controller` and a request-scoped controller. With a generated, `@ApiMethod` or `@ApiRouteCustom` route Nest fails first, already on `compile()`, with its dependency error that names `ApiAuthorizationGuard` and `ApiAuthorizationRuntime`. The fix is the same: import the module. `Test.createTestingModule(...).compile()` of a controller with only plain routes runs no startup check.
- A microservice or WebSocket transport has no identity that authorization can trust, because the caller writes the payload the guard would read as the request, `user` included. A `@MessagePattern`, `@EventPattern` or `@SubscribeMessage` handler therefore fails startup, with or without `@ApiMethod`, in a microservice and in a hybrid application. Move it to a controller that is not securable, which leaves authenticating that transport to you. A gateway is a provider, so startup does not inspect it: a gateway with `@ApiControllerSecurable()` starts and every message is denied.
- Nest takes the route from the prototype and the guards from the function on the instance. `this.report = this.report.bind(this)` in a constructor therefore drops the guards, and startup refuses it, because Nest already calls a handler with `this` set to the controller. A function that carries all the metadata of the handler is accepted. A request-scoped instance does not exist at startup, so there the guard below decides.

`@ApiControllerSecurable()` also attaches a guard to the class. It applies the same rule per request and denies a handler that does not go through authorization, and everything on a transport other than HTTP: `403` over HTTP, `Forbidden resource` over a microservice or WebSocket transport. It evaluates no policy, so an authorized route is evaluated once. It covers what startup cannot see, such as a request-scoped handler, a gateway, or path metadata removed after the routes were registered. The guard runs for any execution context, so it also denies a GraphQL resolver on a securable class; that case is untested, because GraphQL is not a dependency of this package.

Code written to evade the check is out of scope, for example calling `ApiControllerSecurable()` inside a bootstrap hook or a constructor that returns an object of another class.

## Runtime authorization actions

`@ApiMethod(...)` uses one route action identity: `metadata.resource.action`. Generated CRUD routes also carry `metadata.route.type` for built-in CRUD/IAM mapping.

Auto-generated CRUD routes receive built-in runtime actions automatically:

- `create`
- `delete`
- `get`
- `getList`
- `partialUpdate`
- `update`

Custom secured routes should declare their own domain action strings:

```typescript filename="controllers/user.controller.ts" copy
@ApiMethod<UserEntity>({
	metadata: {
		resource: {
			action: "update.promote",
			entity: UserEntity,
		},
		route: {
			method: RequestMethod.POST,
			path: ":id/promote",
		},
		security: {
			authorization: { mode: EApiAuthorizationMode.HOOKS },
		},
		response: {
			status: HttpStatus.OK,
			type: UserResponseDto,
		},
	},
})
public promote(@Param("id") id: string) {
	return this.service.promote(id);
}
```

That same `metadata.resource.action` value is what hooks receive as `context.action` and what IAM turns into a namespaced action such as `admin:user:update.promote`.

## Hooks Mode

Hooks mode keeps the original policy authoring style, but now runs on `principal + permissions` rather than `subject + subject.permissions`. Policies are still auto-discovered by entity through `@ApiAuthorizationPolicy({ entity })`.

```typescript filename="policies/user-hooks.policy.ts" copy
import type { IApiAuthorizationRuleContext, IApiAuthorizationScope, TApiAuthorizationPolicyBeforeGetListContext, TApiAuthorizationPolicyBeforePartialUpdateContext } from "@elsikora/nestjs-crud-automator";

import { EApiAuthorizationPermissionMatch, ApiAuthorizationPolicy, ApiAuthorizationPolicyBase } from "@elsikora/nestjs-crud-automator";

@ApiAuthorizationPolicy<UserEntity>({
	entity: UserEntity,
	priority: 200,
})
export class UserHooksPolicy extends ApiAuthorizationPolicyBase<UserEntity> {
	private getOperatorId(principal: IApiAuthorizationRuleContext<UserEntity>["principal"]): string | undefined {
		return principal.attributes.operatorId as string | undefined;
	}

	private scopeToOperator(context: IApiAuthorizationRuleContext<UserEntity>): IApiAuthorizationScope<UserEntity> {
		return {
			where: {
				operatorId: this.getOperatorId(context.principal),
			},
		};
	}

	public onBeforeGetList(context: TApiAuthorizationPolicyBeforeGetListContext<UserEntity>) {
		const requestedOperatorId = context.query.operatorId as string | undefined;

		if (requestedOperatorId && requestedOperatorId !== this.getOperatorId(context.principal)) {
			return [];
		}

		return [
			...this.allowForRoles(["platform-admin"]),
			...this.allowForPermissions(["admin.user.read", "admin.user.list"], {
				match: EApiAuthorizationPermissionMatch.ALL,
				scope: (ruleContext: IApiAuthorizationRuleContext<UserEntity>): IApiAuthorizationScope<UserEntity> => this.scopeToOperator(ruleContext),
			}),
		];
	}

	public onBeforePartialUpdate(context: TApiAuthorizationPolicyBeforePartialUpdateContext<UserEntity>) {
		if (context.body.operatorId && context.body.operatorId !== this.getOperatorId(context.principal)) {
			return [];
		}

		return [
			...this.allowForPermissions(["admin.user.update"], {
				scope: (ruleContext: IApiAuthorizationRuleContext<UserEntity>): IApiAuthorizationScope<UserEntity> => this.scopeToOperator(ruleContext),
			}),
			...this.denyForPermissions(["admin.user.update"], {
				condition: ({ principal }: IApiAuthorizationRuleContext<UserEntity>) => Boolean(principal.attributes.isOperatorLocked),
				priority: 1000,
			}),
		];
	}
}
```

Generated CRUD routes dispatch to CRUD hooks such as `onBeforeGetList` or `onBeforeUpdate` by internal `routeType`. Custom `@ApiMethod(...)` and `@ApiRouteCustom(...)` routes without `metadata.route.type` do not use CRUD hook names; handle them in `getCustomActionRule(action, context)` instead:

```typescript filename="policies/user-hooks.policy.ts" copy
public getCustomActionRule(action: string) {
	if (action === "update.promote") {
		return this.allowForPermissions(["admin.user.promote"]);
	}

	return [];
}
```

Hook contexts expose:

- `principal` and resolved `permissions`
- `body`, `parameters`, `query`, `headers`, and `ip`
- `action`, `routeType`, `entity`, and `entityMetadata`
- the same data again under `context.DATA`

`routeType` is only populated for auto-generated CRUD handlers. For custom `@ApiMethod(...)` routes, branch on `action`.

For stronger typing, use the route-aware helper contexts:

- `TApiAuthorizationPolicyBeforeCreateContext<E>`
- `TApiAuthorizationPolicyBeforeGetContext<E>`
- `TApiAuthorizationPolicyBeforeGetListContext<E, M = PAGE>`
- `TApiAuthorizationPolicyBeforeUpdateContext<E>`
- `TApiAuthorizationPolicyBeforePartialUpdateContext<E>`

The GET_LIST policy action stays the same in CURSOR mode. Select `M = EApiControllerGetListQueryPaginationMode.CURSOR` when a policy needs typed `after`/`before` access or returns a transform for the flat cursor envelope.

Permission helpers compare required permissions against the permissions returned by your hook permission sources:

- `EApiAuthorizationPermissionMatch.ANY` is the default
- `EApiAuthorizationPermissionMatch.ALL` requires every listed permission
- wildcards are supported on granted permissions only, for example `admin.user.*`, `admin.*`, or `*`

If you need custom checks outside a policy class, use `AuthorizationPermissionMatches()` and `AuthorizationPermissionSetMatches()`.

Policy-rule caching remains available in hooks mode through `ApiAuthorizationPolicyRegistry.configureCache()` or per policy with the `cache` option. Leave it disabled when a policy depends on request-specific data.

Inject `ApiAuthorizationCacheInvalidationService` when an enabled policy-rule cache must be cleared, or when `MEMORY` resolver entries must reflect hook permission, IAM attachment, or IAM document changes before TTL expiry. It is the public facade for clearing automator-owned authorization caches, so application services do not need to inject IAM resolver internals:

```typescript
@Injectable()
export class PermissionAdminService {
	constructor(private readonly cacheInvalidation: ApiAuthorizationCacheInvalidationService) {}

	async revokeUserPermission(userId: string, permission: string): Promise<void> {
		await this.permissionRepository.delete({ userId, permission });
		this.cacheInvalidation.clearAll(UserEntity);
	}
}
```

Use the narrower methods when the backing change is scoped to one cache family: `clearPolicyCache(entity?)`, `clearHookPermissionCache()`, `clearIamAttachmentCache()`, `clearIamDocumentCache()`, or `clearIamCache()`. Resolver-cache clear methods are harmless in source-first mode because those maps remain empty.

## IAM Mode

IAM mode does not use `@ApiAuthorizationPolicy` classes. Instead, the runtime:

1. Resolves a principal
2. Loads policy attachments for that principal
3. Loads IAM documents by attachment policy IDs
4. Evaluates identity policies and optional boundaries
5. Compiles safe resource scopes into controller queries

Every IAM-enabled controller must declare:

- `defaultMode: EApiAuthorizationMode.IAM`
- `policyNamespace`
- `resourceDefinition`

```typescript filename="controllers/item.controller.ts" copy
import { ApiController, ApiControllerSecurable, EApiAuthorizationMode } from "@elsikora/nestjs-crud-automator";

@ApiControllerSecurable()
@ApiController<ItemEntity>({
	authorization: {
		defaultMode: EApiAuthorizationMode.IAM,
		policyNamespace: "admin:item",
		resourceDefinition: {
			entity: ItemEntity,
			fields: [
				{
					isFilterable: true,
					path: "resource.id",
					queryPath: "id",
				},
				{
					isFilterable: true,
					path: "resource.operatorId",
					queryPath: "operator.id",
				},
				{
					isFilterable: true,
					path: "resource.status",
					queryPath: "status",
				},
			],
			namespace: "admin:item",
			resourcePath: "gameport:admin:item/{id}",
			resourceType: "gameport:admin:item",
		},
	},
	entity: ItemEntity,
	path: "items",
	routes: {},
})
export class ItemController {
	constructor(public service: ItemService) {}
}
```

Generated CRUD actions are normalized to IAM-friendly names inside the configured namespace:

- `get` -> `<policyNamespace>:read`
- `getList` -> `<policyNamespace>:list`
- `create` -> `<policyNamespace>:create`
- `update` / `partialUpdate` -> `<policyNamespace>:update`
- `delete` -> `<policyNamespace>:delete`

Custom `@ApiMethod(...)` actions pass through unchanged after the namespace. For example, `resource.action: "update.promote"` becomes `admin:item:update.promote` when `policyNamespace` is `admin:item`.

`queryPath` may be nested, such as `operator.id`, when your repository filter shape uses relations. The query planner compiles both `resource.id` and relation-backed paths such as `resource.operatorId` into scopes for row and list routes.

Example IAM sources:

```typescript filename="authorization/iam-sources.ts" copy
import type { IApiPolicyAttachmentSource, IApiPolicyDocumentSource, IApiResolvedPolicyAttachments } from "@elsikora/nestjs-crud-automator";

import { EApiAuthorizationPrincipalType, EApiPolicySourceType } from "@elsikora/nestjs-crud-automator";

export const attachmentSource: IApiPolicyAttachmentSource = {
	async getAttachments(principal): Promise<IApiResolvedPolicyAttachments> {
		return {
			attachments: [
				{
					policyId: "allow-managed",
					principalId: principal.id,
					principalType: EApiAuthorizationPrincipalType.USER,
				},
			],
			boundaries: [
				{
					policyId: "boundary-db",
					principalId: principal.id,
					principalType: EApiAuthorizationPrincipalType.USER,
				},
			],
		};
	},
};

export const documentSource: IApiPolicyDocumentSource = {
	async getDocumentsByIds(ids) {
		return ids.map((id) => ({
			document: {
				Statement: [
					{
						Action: ["admin:item:list", "admin:item:read"],
						Condition: {
							StringEquals: {
								"resource.operatorId": "operator-1",
							},
						},
						Effect: EApiPolicyEffect.ALLOW,
						Resource: ["gameport:admin:item/*"],
						Sid: id,
					},
				],
				Version: "2012-10-17",
			},
			id,
			namespace: "admin:item",
			sourceType: EApiPolicySourceType.MANAGED,
			version: "2026-03-14",
		}));
	},
};
```

Relation-backed create and update rules can also work directly with raw UUID payloads. If the consumer sends `request.body.operator = "operator-1"` instead of `{ id: "operator-1" }`, IAM conditions can use that value without any hooks fallback:

```typescript filename="authorization/operator-managed-document.ts" copy
const document = {
	Statement: [
		{
			Action: ["admin:item:create", "admin:item:update"],
			Condition: {
				StringEquals: {
					"request.body.operator": "${principal.attributes.operatorId}",
				},
			},
			Effect: EApiPolicyEffect.ALLOW,
			Resource: ["gameport:admin:item/*"],
		},
		{
			Action: ["admin:item:read", "admin:item:list"],
			Condition: {
				StringEquals: {
					"resource.id": "${request.parameters.id}",
					"resource.operatorId": "${principal.attributes.operatorId}",
				},
			},
			Effect: EApiPolicyEffect.ALLOW,
			Resource: ["gameport:admin:item/*"],
		},
	],
	Version: "2012-10-17",
};
```

`request.parameters`, `${request.parameters.*}`, and `resourcePath` placeholders read the canonical text of the route's validated path values. `ApiAuthorizationGuard` validates each value by the rule of its described column before it evaluates anything, then writes it as text:

| Column type        | Text authorization sees         |
| ------------------ | ------------------------------- |
| integer `NUMBER`   | canonical decimal, such as `16` |
| `UUID`             | lower-case                      |
| `BOOLEAN`          | `true` or `false`               |
| `DATE` (date-time) | ISO 8601 UTC with milliseconds  |
| `DATE` (date)      | `YYYY-MM-DD`, as given          |
| `STRING`, `ENUM`   | the validated text              |

So `{id}` renders as `16`, `{at}` as `2024-03-10T12:00:00.000Z`, and `{active}` as `true`. A `DATE_TIME` path value must be sent in that one form: `2024-03-10T12:00:00Z` returns `400`. A malformed or non-canonical value such as `016`, `1e3`, or `1` for a boolean is rejected with `400` before evaluation, so it cannot name the same row as `16` and slip past a Deny on `item/16`. A `resource.*` value compares by the same text, so the recipe `"resource.at": "${request.parameters.at}"` matches a `DATE_TIME` column. Scope values from conditions and hooks, such as the literal `"16"` in `"resource.id": "16"`, are converted to the column type before they merge with the route's identity and `read.scope` values. Handlers, subscribers, and the service still receive the typed values.

On a securable `@ApiRouteCustom` route, IAM and a HOOKS policy see the value the route's PARAMETERS DTO produces. The guard runs that DTO on the path values: it converts them with class-transformer, validates them with class-validator, reads each value back through its `@Expose` name, and renders the canonical text above. An `@Expose({ name: "id" })` rename, a `PickType`, `OmitType`, `PartialType`, or `IntersectionType` of another DTO, a bare `@IsInt() @Type(() => Number)`, and a `@Transform` all count. With `@IsInt() @Type(() => Number)` a Deny on `"16"` returns `403` for `/16`, `/016`, and `/0x10`; with `ApiPropertyNumber` `/016` and `/1e1` return `400`, and any value the DTO rejects returns `400` before IAM. A `resourcePath` that names a path parameter also needs that value copied from a column with `ApiPropertyCopy`, or the application fails at startup, because a resource string must render by the column's rule. The application also fails at startup when the DTO makes a path value an object or a list, drops it, or declares a property with `isResponse`. These checks belong to each controller class: a custom route inherited from a base controller is checked for every securable subclass by that subclass's own `resourcePath`.

On a securable route, the handler and the policy read the path value authorization saw, or the application does not start. The path parameters of a route are those of the paths Nest serves it at: the global prefix, unless `setGlobalPrefix` excludes the route, the `RouterModule` path, nested modules included, the controller path, and the route path. Escaped text names no parameter, such as `\:x` on Express and `a::b` on Fastify. A securable route with a path parameter, in IAM and HOOKS mode alike, fails at startup with an error that names the controller, method, and parameter, and says what to change, when:

- any part of its path has a wildcard (`*`, `*name`, or `{*name}`), whose value has no name a PARAMETERS DTO can describe. Name each value as a path parameter, such as `:name`;
- it is an IAM `@ApiRouteCustom` or `@ApiMethod` route that does not list and its `resourcePath` names a placeholder that is not a path parameter of the route. The guard has no loaded row to fill it from, so it renders as `*`, which no Deny on a value matches. Serve the route under that path parameter, copied with `ApiPropertyCopy`, or authorize it in HOOKS mode. A list route, with `route.type` `GET_LIST` or the action `<policyNamespace>:list`, keeps such a placeholder, because it maps it to row exclusions;
- it is an `@ApiRouteCustom` or `@ApiMethod` route that declares no `dto[EApiDtoType.PARAMETERS]`, or whose PARAMETERS DTO does not describe a path parameter with a class-validator rule, an `ApiProperty*` decorator, `ApiPropertyCopy`, a `@Transform`, or a `@Type`. Declare the route with `@ApiRouteCustom` and describe each path value, preferably with `ApiPropertyCopy`;
- it is a HOOKS route whose PARAMETERS DTO holds a path parameter without a column type: only `ApiPropertyCopy` and the `ApiProperty*` decorators count, so a bare `@IsInt() @Type(() => Number)` or `@IsString()` fails. The type the PARAMETERS DTO declares decides the canonical text, and `ApiPropertyCopy` declares the column's own type, so prefer it: an `ApiPropertyString` on an integer column keeps `016` as text, which the handler and the policy then both read;
- it is a generated route and a `RouterModule` path or the global prefix adds a parameter its generated PARAMETERS DTO does not describe. `read.scope.parameters` maps only parameters of the controller path, so serve the route with `@ApiRouteCustom` and a PARAMETERS DTO that describes it;
- `@UsePipes` on the method or the controller holds a pipe other than `ValidationPipe`, as a class or an instance, or a `ValidationPipe` with `expectedType`, or a `ValidationPipe` that runs another class-transformer or class-validator, set by `transformerPackage` or `validatorPackage`. Nest shares those packages among every `ValidationPipe` of the process, so startup runs the pipe on two probe DTOs to see them. Remove the pipe or the option and let the PARAMETERS DTO convert the value. A global pipe of the host, from `app.useGlobalPipes()` or `APP_PIPE`, is the host's own choice and is not checked: keep it to `ValidationPipe` on securable routes;
- a `@Param` argument has a pipe, such as `@Param("id", ParseIntPipe)`, also for a parameter of the `RouterModule` path. Remove the pipe and let the PARAMETERS DTO convert the value;
- a `@Param("id")` argument has a type that compiles to neither `String` nor `Object`, such as `id: number`, which `ValidationPipe({ transform: true })` would convert by its own rule. `string`, `unknown`, `any`, and a union compile to `String` or `Object` and start;
- a `@Param()` argument is typed as another class than the PARAMETERS DTO. Type it as the PARAMETERS DTO.

So a handler reads the canonical text from `@Param("id") id: string`, or the converted value from `@Param() parameters: ItemReadParametersDto` under `ValidationPipe({ transform: true })`. The guard writes the canonical text to `request.params`, so a handler that reads it through `@Req()` or its own parameter decorator reads that text too. What startup cannot see is a conversion such a reader, or a pipe on its decorator, makes by itself: keep it out, or read the value with `@Param`.

The guard also compares each request with what startup checked: a request whose `request.params` holds a parameter startup did not record for the route, or a route startup did not check, answers `500` before the policy, the handler, and any query, and the log names the controller, method, and parameter. A test that replaces `ApiAuthorizationBootstrapValidationService` turns this comparison off with every other startup check.

The handler reads the value authorization saw, or the request is refused. The guard runs the DTO with and without implicit conversion, because it cannot see the options of a host pipe, and returns `400` when both accept a value and give different text. It writes the canonical text back to `request.params`, with no host pipe too, so a handler without a pipe and a validate-only `new ValidationPipe()` read that text, and a `ValidationPipe({ transform: true })` converts it. It then runs the DTO on that text and returns `400` when an accepting conversion gives other text. So a `@Transform` that adds a `p-` prefix on every call or decodes base64 cannot serve a securable route: without this, a Deny on `abc` would be checked on `p-abc` while a handler read `abc`. Keep the `@Transform` stable on its own output, or move the conversion into the handler. The same checks run at startup on sample values, `true` and `false` too for a `boolean` property, and name the controller, method, DTO, and what to change; a sample cannot show everything, so those values are checked on each request. A `@Transform` runs several times per request and must be pure. What the guard cannot run, it refuses at startup by reading the metadata: a `@Transform` limited to class-transformer `groups`, `since`, or `until`, and an `@Expose` limited to `since` or `until`, on a path value. A validator limited to class-validator `groups` on a path value is refused too: the guard runs every validator, while a host pipe with groups runs only those of its groups, so the two would check the value differently. Two properties that expose one path parameter's name are a startup error too. A guard that runs before `ApiAuthorizationGuard` still sees the raw text; see [Validation](/docs/nestjs-crud-automator/guides/validation#generated-route-path-parameters).

On a custom route's PARAMETERS DTO, an upper-case UUID returns `400` (`id must be a lower-case UUID`) under `ApiPropertyUUID`, a mapped type of it, and a bare `@IsUUID()` alike, so `/AAAAAAAA-...` never reaches a Deny on the lower-case UUID. A bare `@IsString()`, `@IsDateString()`, or `@IsNumberString()` only validates, so IAM compares the text as sent and a Deny misses another spelling that the database can still match, such as another letter case of a key in a case-insensitive column. Give a bare rule its canonical form with a pure `@Transform`:

```typescript
class ItemParametersDto {
	@IsString()
	@Transform(({ value }: { value: unknown }): unknown => (typeof value === "string" ? value.toLowerCase() : value), { toClassOnly: true })
	public slug!: string;
}
```

IAM behavior is intentionally strict:

- explicit deny wins over allow
- boundaries intersect the final allow scope
- typed client filters, static `USE_DEFAULT` predicates, and authorization scopes are merged once with logical `AND`, not overwrite semantics
- principal- or tenant-dependent restrictions belong in HOOKS/IAM scope; route query defaults never replace or satisfy authorization scope
- impossible conflicts collapse to a match-nothing branch instead of rewriting the requested filter
- conditions that cannot be planned into a query fail closed instead of being filtered in memory: an Allow statement is not matched, while a Deny statement denies the whole request (explicit deny)
- duplicate document IDs across sources and missing requested documents throw immediately

### Condition operators

IAM conditions support exactly these operators, exposed as `EApiPolicyConditionOperator`:

| Operator                  | Holds when                                     |
| ------------------------- | ---------------------------------------------- |
| `StringEquals`            | the value equals the expected value            |
| `StringEqualsIfExists`    | the value is absent or equals the expected one |
| `StringNotEquals`         | the value differs from the expected value      |
| `StringNotEqualsIfExists` | the value is absent or differs from it         |

Any other operator is a document validation error: `ApiAuthorizationIamDocumentValidator` rejects the document when it is loaded from a document source, so a typo can never silently turn a statement into a no-op. If an unknown operator still reaches evaluation, it fails closed: the key holds for a Deny and fails for an Allow. An operand that is a list, an object or `null` has no text to compare: the validator logs a warning and the key fails closed the same way: the key fails for an Allow and holds for a Deny, whose other keys still decide whether it matches. In a planned scope such a `resource.*` key cannot compile (see [Deny semantics](#deny-semantics)). None of these answers `500`.

Keys inside one statement are ANDed. `principal.*` and `request.*` keys are evaluated in memory; `resource.*` keys are evaluated in memory when the resource is already loaded (for example in `ApiAuthorizationSimulator` with `resource`) and are otherwise planned into a database scope.

### Allow scopes

The query planner compiles `StringEquals` and `StringEqualsIfExists` Allow conditions on `resource.*` fields marked `isFilterable` into the decision scope. Allow statements are ORed with each other and intersected with boundary scopes. An Allow statement whose `resource.*` keys use another operator, a non-filterable or unmapped field, an unresolved `${...}` variable, a value that is `""` or resolves to `null` or `""`, a `queryPath` TypeORM cannot resolve to a column, a list, object or `null` value, or on a boolean column a value other than `true`, `false` or that exact text is not matched.

The planner reads each `queryPath` through the TypeORM metadata of the resource entity, at every step: relations of any depth, embedded entities, and columns inherited from a parent class or a single-table-inheritance parent. A path that does not end on a column TypeORM maps, such as a misspelled property, a relation itself, or a step past a column, does not compile.

A boolean column is one TypeORM types as `boolean`, `bool` or `bit` (the SQL Server boolean), including a bare `@Column()` on a `boolean` property, or one described as `BOOLEAN`; it needs no `@ApiPropertyDescribe`. On it, `true`, `false` and the text `"true"` and `"false"` bind as booleans in Allow scopes, Deny exclusions and exact row-scoped Deny patterns, so each database compares them with its stored form, such as `1` and `0` on SQLite and MySQL. Any other value, such as `"1"`, `"TRUE"`, `"yes"` or the number `1`, equals no stored boolean in the in-memory evaluator, so it does not compile. A resource entity that no TypeORM decorator maps, such as one registered only through an `EntitySchema`, has no column types to read, so none of its `resource.*` keys compile.

### Deny semantics

Generated routes evaluate IAM once, before the resource is loaded. A matched Deny statement (its action, resource, and non-resource keys hold) then behaves as follows:

- **No `resource.*` keys** — the whole request is denied with `403`.
- **`resource.*` keys that all compile** — the Deny becomes a row exclusion: its condition is negated and ANDed with the Allow scope. Lists omit excluded rows, and `GET`, `UPDATE`, `PARTIAL_UPDATE`, and `DELETE` of an excluded row answer `404`, exactly like a row outside an Allow scope.
- **Any `resource.*` key that cannot compile** (another operator, a non-filterable or unmapped field, a `queryPath` TypeORM cannot resolve to a column, an unresolved `${...}` variable, a value that resolves to `null` or `""`, a list, object or `null` value, a value other than `true` or `false` on a boolean column) — the whole request is denied with `403`.
- **`CREATE`** — a Deny with `resource.*` keys denies the whole request, because there is no stored row to exclude. Custom routes whose action is `<policyNamespace>:create` follow the same rule. A Deny whose `Resource` names a concrete row, such as `gameport:admin:item/item-1`, is not applied on `CREATE`: the request is evaluated against the collection resource, so that pattern does not match and the row is created. To refuse a value on `CREATE`, use an Allow scope instead (see [Scoped CREATE](#scoped-create)).

By De Morgan, the keys of one Deny become top-level OR branches of the exclusion. The kept rows are exactly the rows the in-memory evaluator allows once the resource is loaded. That evaluator compares values as strings and treats a stored `NULL` as a present value that normalizes to an empty string, so `NULL` never equals a non-empty value and always differs from it. The `IfExists` operators only behave differently for paths that are missing entirely, which a stored row never has, so for stored rows they compile like their plain forms:

| Deny key                  | Rows kept                         |
| ------------------------- | --------------------------------- |
| `StringEquals`            | `field <> value OR field IS NULL` |
| `StringEqualsIfExists`    | `field <> value OR field IS NULL` |
| `StringNotEquals`         | `field = value`                   |
| `StringNotEqualsIfExists` | `field = value`                   |

Because `""` and `NULL` compare equal in memory but not in SQL, a condition value that is `""` or resolves to `null` or `""` is not compiled; it denies the whole request instead.

Several matched Deny statements, including boundary Deny statements, are ANDed. Nested `queryPath` values such as `operator.id` follow the same path rules as Allow scopes.

A Deny on `request.parameters.*` or on a `resourcePath` compares text, while the database reads the key by its column type and collation. Integer keys are refused unless canonical, an upper-case UUID is refused on a UUID key, and a decimal key fails at startup in IAM and HOOKS mode, as described in [Validation](/docs/nestjs-crud-automator/guides/validation#generated-route-path-parameters). Under a case-insensitive collation (common on MySQL, or `citext` on PostgreSQL) `/ABC` finds the row of `abc` and passes a Deny on `abc`, so give such a key one canonical case in its DTO, or use a Deny with `resource.*` keys, which the database compares by the same collation.

Equality follows the database collation, exactly as it does for Allow scopes. Under a case-insensitive collation (common on MySQL), the `field = value` branch of a `StringNotEquals` or `StringNotEqualsIfExists` Deny also keeps rows whose value differs from `value` only by letter case, although the case-sensitive in-memory evaluator would deny them. Use case-sensitive collations for columns that Deny statements compare.

A merged scope with a Deny exclusion may hold at most `AUTHORIZATION_IAM_SCOPE_CONSTANT.MAX_WHERE_BRANCHES` (128) OR branches; a larger one denies the whole request with `403` instead of sending an unbounded query. Branches are counted without pruning:

- within one Deny statement, branches add up: each `StringEquals` or `StringEqualsIfExists` key and each row-pattern placeholder constraint contributes 2 (`<> value` and `IS NULL`); each `StringNotEquals` or `StringNotEqualsIfExists` key contributes 1;
- Deny statements multiply with each other, and the result multiplies with the Allow scope branches (one per compiled Allow statement, times the boundary scope branches).

For example, three Deny statements with one `StringEquals` key each give 2 × 2 × 2 = 8 branches; under an Allow scope with 20 branches that is 160, so the request is denied.

```typescript filename="authorization/archived-deny-document.ts" copy
const document = {
	Statement: [
		{
			Action: ["admin:item:list", "admin:item:read", "admin:item:update", "admin:item:delete"],
			Condition: {
				StringEquals: {
					"resource.operatorId": "${principal.attributes.operatorId}",
				},
			},
			Effect: EApiPolicyEffect.ALLOW,
			Resource: ["gameport:admin:item/*"],
		},
		{
			Action: ["admin:item:list", "admin:item:read", "admin:item:update", "admin:item:delete"],
			Condition: {
				StringEquals: {
					"resource.status": "archived",
				},
			},
			Effect: EApiPolicyEffect.DENY,
			Resource: ["gameport:admin:item/*"],
		},
	],
	Version: "2012-10-17",
};

// GET_LIST scope: operatorId = principal operator AND (status <> 'archived' OR status IS NULL)
```

### Row-scoped Deny on lists

A list request (`GET_LIST`, or a custom route whose action is `<policyNamespace>:list`) uses the collection resource, for example `gameport:admin:item/*`. A Deny statement whose `Action` matches the list action and whose `Resource` is more specific than the collection resource is compiled into a row exclusion on the mapped fields:

- `gameport:admin:item/item-1` excludes `id = 'item-1'`
- `gameport:admin:item/abc*` excludes ids starting with `abc`; literal `%`, `_`, and `!` are escaped and the prefix is matched with `NOT LIKE ... ESCAPE '!'`
- with `resourcePath: "bool:item/{isFeatured}"` on a boolean column, `bool:item/true` excludes `isFeatured = true`; only `true` and `false` map, so `bool:item/1` or `bool:item/TRUE` denies the list with `403`

Rows whose placeholder field is `NULL` stay visible, because their resource string renders the placeholder as `*`, which no row-scoped pattern matches.

Unresolved `resourcePath` placeholders map to `resourceDefinition.fields` by name: `{id}` uses the `resource.id` field, which must be `isFilterable`. Prefix patterns additionally require a direct property described as `EApiPropertyDescribeType.STRING`, the same rule the typed `starts` filter uses, without the `BIGINT_STRING` and `UUID` string formats; UUID, numeric, and relation-backed fields cannot be prefix-matched. Placeholders already resolved from request parameters, such as an inherited parent id, must match literally. A prefix pattern only maps when it ends inside the first unresolved placeholder. When the pattern cannot be mapped unambiguously or a placeholder field is missing, not filterable, or not a string, the whole list request is denied with `403`. Patterns for other resource types are ignored.

`LIKE` is case-sensitive on PostgreSQL but case-insensitive by default on SQLite and on MySQL with case-insensitive collations. There, a prefix Deny also hides rows whose id differs only by letter case, so it over-excludes rather than revealing rows.

Actions are never widened: a Deny on `read` does not hide rows from `list`, and a row-scoped Deny on `list` does not affect `read`. On row routes the resource string is concrete, so an exact `Resource` Deny matches that row and denies the request with `403`.

### Custom routes

Custom `@ApiMethod(...)` routes receive the same contract through `decision.scope`: Allow scopes and Deny exclusions are already merged into `decision.scope.where`, so applying it to the route's own query enforces both. A Deny with `resource.*` keys that cannot compile denies the custom route with `403` before the handler runs.

Automator does not add a separate immutable `baseWhere` controller option. Put fixed, principal-dependent, and tenant-dependent restrictions in HOOKS or IAM scope so they participate in the same fail-closed AND merge.

## Scoped CREATE

A generated `CREATE` is scoped when its decision carries a non-empty `scope.where`, from a HOOKS `rule.scope` or an IAM Allow scope. A scope describes a stored row, and only the database knows that row: defaults, `onBeforeCreate` subscribers, and generated columns all shape it, and a scope may hold operators such as `Raw` or `ILike` that only the database evaluates. So the check does not run before the insert. The route writes the row, then reloads it by its primary key and the scope inside the same transaction, after the insert and before the commit, and commits only when the reload finds it:

- **Row inside the scope** — the transaction commits and the route answers `201`.
- **Row outside the scope** — the transaction rolls back and the route answers `403`. The row is never committed, except when an outer owner catches the refusal (see below). The response carries no value from the body or the scope.

Only the reload's own miss becomes `403`. A `404` from request relation hydration, `service.create`, or a subscriber stays as it is, and so does every other error. An `onBeforeGet` subscriber that narrows the reload causes such a miss, so an in-scope row is refused with `403` as well. The route identifies the created row before it applies the scope:

- **The key comes from the stored row.** The protected `create` reports the primary key TypeORM saved for the row its `save` inserted, generated columns included, before function subscribers run, so an `onAfterCreate` subscriber that returns another row does not change which row the scope checks. A non-scoped `CREATE` does the same. This is the key the response is read by as well (see [the relations guide](/docs/nestjs-crud-automator/guides/relations)).
- **Every primary column must hold a value TypeORM knows.** A part of the key that the saved row lacks, for example one a database trigger or a default added outside TypeORM fills, answers `500` and rolls back, with an error that says to declare the column as generated, so the reload never falls back to part of the key or to the scope alone.
- **A date and time column matches its whole millisecond**, also inside an embedded property, where the route finds the column and the body value by their property path. PostgreSQL can store microseconds, while the driver reads the value back with milliseconds, so the key matches the range `[t, t + 1 ms)`. A value a `create` function reports as text is parsed into a date first. Both bounds are bound the way every other read binds a temporal condition: on PostgreSQL and CockroachDB a `timestamptz` column binds them as canonical UTC text, because node-postgres binds a `Date` through the local offset cut to whole minutes, which moves a historical value such as 1800 in `Asia/Kolkata` by seconds. A `timestamp` or `datetime` column, and every column on MariaDB, binds the `Date`, whose local wall-clock text is what the column stores. A `date` column matches by equality. A column with a `transformer` matches its stored value by equality instead of a range: the transformer runs once on the key, and both the condition and its operands are bound so TypeORM does not run the transformer again. A range would send each bound through the transformer on its own, and a transformer that cuts the value, for example to whole seconds, would collapse it. A key that a default or a trigger fills on a `timestamp` column inside a daylight saving transition, such as a `CreateDateColumn` primary key in the skipped or repeated hour, reads back as another instant, so it can answer `500` and roll back. Use `timestamptz` for such a key.
- **An instant key is written exactly.** On PostgreSQL and CockroachDB a `timestamptz` primary key from the body is written as its exact UTC instant, whether the column is declared as `timestamptz` or as `timestamp with time zone`, including a historical value whose zone offset holds seconds. Its column transformer and your subscribers receive a `Date` that reports its UTC fields as local ones, so its `getTime()` and `toISOString()` are the instant while `getHours()` returns the UTC hour. Read such a key through `getTime()` or `toISOString()`, never text. A transformer that returns a new `Date` for such a historical value writes the shifted value node-postgres produces, so the key misses, and the route answers `500` and rolls back. A `Date` that application code writes into a `timestamptz` column on its own write is moved by the same truncation.
- **A date and time primary key from the body is checked and parsed once, before the transaction.** Behind a transforming `ValidationPipe` or without one, the route answers `400` with the validation body when the value cannot be stored exactly: it is not a date and time, it names a day or an hour the calendar does not hold (such as `2026-02-30` or `24:00`, which a JavaScript `Date` would roll over into the next day), it holds more fraction digits than the column stores or than the three a JavaScript `Date` holds, or it has no zone or offset with minutes on a `timestamptz` column, because an instant must name its zone. The zone rule is the one date and time filters use. On `timestamp` and `datetime` columns a value without a zone is parsed in the process time zone. Such a column stores the local wall clock, so on every driver outside the SQLite family, which stores UTC, the route also answers `400` for the second occurrence of an hour that a daylight saving change repeats in the process time zone: it shares its wall clock with the first occurrence, so one value would otherwise name the row of the other. The row and the key then use that one parsed value. Other columns of the body are not affected.
- **A date and time primary key the database fills needs a driver that reads it back.** A controller that generates `CREATE` fails at startup, naming the controller, the column, and the driver, when the database fills such a key through a column default, a `CreateDateColumn` or `UpdateDateColumn`, or a generated value, unless the driver is `postgres`, `cockroachdb`, or `mariadb`. MySQL and SQLite have no `INSERT RETURNING`, so the route could not tell which row it stored; MariaDB needs version 10.5 or later for the same reason. A request-scoped controller reaches no startup hook, so it answers `500` with the same named error at request time and persists nothing. A key the body supplies is known without reading it back, so it works on every driver, alone or in a composite key.
- **A securable `CREATE` refuses a date and time primary key finer than a millisecond.** TypeORM reads such a column with milliseconds, so two rows of one millisecond look like one, and the scope could be checked against another row. A controller with `@ApiControllerSecurable` fails at startup, naming the controller, the entity, and the column, whether the database fills the key or the body sends it. Declare the column with `precision: 3`. A column without a precision passes only where the driver's default holds no more: MySQL and MariaDB default to `0`, and the SQLite family, `datetime`, and `smalldatetime` hold no finer value, while PostgreSQL, CockroachDB, Oracle, and MSSQL `datetime2` are refused. A controller that is not securable keeps such a key, and when another row commits into the millisecond of the created key its `CREATE` answers `500` and rolls back, never with the other row.
- **The key must match exactly one row.** The database counts the rows the key matches, before the reload and again after it: one row is the created row, while no row or more rows answer `500` and roll back. The count after the reload catches a row another request commits meanwhile, which can only add to it. This check runs on non-scoped `CREATE` as well.

A database trigger that overwrites a primary value the body supplied is not covered: the stored row still holds the body value, no row matches, and the route answers `500` and rolls back. Let such a column be filled by a default TypeORM knows, such as `@PrimaryGeneratedColumn` or `@PrimaryColumn({ generated: ... })`, instead of a trigger.

Inside this transaction, everything a generated `CREATE` does follows a few rules:

- **A custom repository stays.** `create` and `get` bind the service repository to the transaction without running its constructor again: the bound repository inherits from the service repository and only replaces its manager and query runner. So a `save` override runs once and custom methods stay on `DATA.repository`, for a subclass of `Repository`, for `.extend()`, and for a NestJS repository whose constructor takes the `DataSource` or other providers. A plain object that only delegates to a repository is no `Repository`: it cannot be bound, so the transaction uses the plain repository of the entity. Write custom repository code as methods. An arrow function stored in a field, such as `save = async (entity) => …`, keeps the `this` of the service repository, so it writes through the service repository's manager, outside the transaction. No binding can change that. On a driver with a connection pool, such as PostgreSQL or MySQL, that write runs on another connection and commits on its own, so a scoped `CREATE` answers `403` and rolls back its own transaction while the row that field wrote stays. On the SQLite family the write shares the one connection, so it lands inside the open transaction and the `403` rolls it back with the rest; do not rely on that either, since the field still skips the transaction manager.
- **Another `DataSource` works on its own.** A service or an `ApiFunctionTransactionScope` of another `DataSource` runs on its own connection, in its own transaction when it opens one, and does not roll back with the `CREATE`. `MANDATORY` does not count the `CREATE`'s transaction for it. A call back into the first `DataSource` joins the `CREATE` again, also when the call on the other `DataSource` runs without a transaction, as `SUPPORTS` does.
- **A scope on the same `DataSource` joins.** `ApiFunctionTransactionScope.runWithDataSource` joins the transaction of the `CREATE` and rolls back with it. It refuses an `observation`, because the owner of the transaction settles it.
- **`onAfterErrorCreate` runs after the rollback.** A failed statement aborts a PostgreSQL transaction, so in a transaction a route or a function owns the hook runs once the transaction has ended: `DATA.eventManager` is `undefined` and `DATA.repository` is the service repository. An error it throws replaces the answer of the `CREATE`. If the transaction committed anyway, because a subscriber caught a nested failure, the error is only logged. A subscriber that declares transaction expectation `REQUIRED` or `MANDATORY` gets no manager here, so its `onAfterErrorCreate` fails: use `onBeforeErrorCreate`, which still runs inside. In your own `ApiFunctionTransactionScope` the hook stays inside the scope.
- **A lost race answers `409`.** The database can end one of two racing requests with a deadlock or a snapshot error, as MySQL and MariaDB do on one primary key. The transaction rolls back, no row is left over, and the client can send the request again.
- **A `DataSource` that starts later is checked later.** With `manualInitialization`, the startup checks that read entity metadata wait, and the date and time key rules run on each request once the `DataSource` is up. The check of the service functions and their transaction modes needs no metadata, so it still runs at startup.

| Route `transaction.mode` | Generated `CREATE`                                              |
| ------------------------ | --------------------------------------------------------------- |
| omitted, `SUPPORTS`      | Opens a `ROUTE` transaction, or joins an active Automator owner |
| `REQUIRED`               | Opens a `ROUTE` transaction, or joins an active Automator owner |
| `MANDATORY`              | Joins the required active owner                                 |
| `NONE`                   | Fails at startup, because nothing could roll the write back     |

Every service function the route calls runs inside that transaction, including the functions that request relation hydration uses, so function `SUPPORTS` and `REQUIRED` join it, and `MANDATORY` runs under every route mode in the table. A `CREATE` or `GET` function configured as `NONE` would reject the transaction, so the controller fails at startup under every route mode, naming the function and the mode to set. Any other function configured as `NONE` on that path, such as one that request relation hydration uses, rejects the active transaction at request time: the route answers `500` and persists nothing. A request-scoped controller reaches no startup hook, so a `NONE` route answers `500` before the write as well.

A generated `CREATE` calls only the exact `create` function produced by `@ApiService` or a built-in `@ApiFunction*` decorator, because a refusal rolls back only what was written through the transaction manager. A controller with an undecorated `create` or `get` override, which may write through `this.repository`, fails at startup, naming the controller and the reason; on a request-scoped controller it answers `500` before the transaction and the write. The startup checks need a real repository: a controller whose service holds a mocked repository, or that has no service, skips them, as the relation load check does.

A non-scoped `CREATE`, including an IAM Allow without conditions and a scope of `{}`, runs the same way: the insert, the identity read, and the reload share one transaction under every mode in the table, for the cost of `START TRANSACTION` and `COMMIT`, so a failure after the insert leaves no row and a retry creates no duplicate. A deny-all scope such as `{ id: In([]) }` is a scope: the write is rolled back and the route answers `403`. A scope of `[]` is rejected with `500` before the transaction and the write, as is any predicate that cannot restrict the query, such as a null value or an empty branch. These are mistakes in the policy, so the error names the path that holds no predicate: use `IsNull()` to match null.

Keep these limits in mind:

- **The guarantee needs a transactional engine.** On a non-transactional engine such as MySQL MyISAM, the rollback does nothing and the row stays after the `403`.
- **A single-connection driver runs Automator transactions one at a time.** TypeORM runs all queries of the SQLite family (`better-sqlite3`, `sqljs`, and the mobile drivers) on one shared connection, so two open transactions would be one, and the rollback of one request would remove the rows of another. The Automator therefore runs every transaction it opens one after another per `DataSource`, so concurrent `CREATE` requests wait for their turn. A transaction that joins an open one takes no turn. This does not cover work outside those transactions on that connection: a read can see an uncommitted row, and a write, including a raw `dataSource.transaction`, can land inside the open transaction and be rolled back with it.
- **A scope does not stop an overwrite.** The route checks the row after the write, and `save` updates a row whose key already exists. Do not rely on a scope to protect a row another tenant owns from a body that names its key or reaches it through a cascade.
- **A historical `timestamptz` column outside the key can miss its scope.** On PostgreSQL and CockroachDB only the primary key is written as its exact instant. Another `timestamptz` column of the body goes through node-postgres, which moves a value whose zone offset holds seconds, such as 1800 in `Asia/Kolkata`. A scope on that column compares the exact instant with the moved value, so an in-scope row answers `403` and rolls back. This fails closed.
- **A joined outer owner decides the commit.** Under an active `ApiFunctionTransactionScope` or another outer owner, the `403` propagates and the outer owner rolls back when the error reaches it. If the outer callback catches the refusal and completes, the outer owner commits and the out-of-scope row stays. Do not swallow this error unless the outer work must not commit it.
- **A generated `CREATE` holds its connection for the whole request.** The route transaction keeps one pool connection from the write until the commit. A subscriber that reads through an injected `Repository` instead of `DATA.repository` asks the pool for a second connection. When concurrent `CREATE` requests hold every connection, those reads wait for each other. node-postgres waits for a connection without limit by default (`connectionTimeoutMillis: 0`), so the requests hang forever. Read through `DATA.repository`, which uses the transaction's connection; otherwise make the pool larger than the number of concurrent `CREATE` requests, and set `extra.connectionTimeoutMillis` on PostgreSQL so that a wait fails with `500` instead of hanging.
- **Function subscribers run before the decision.** Function `onAfterCreate` subscribers run before the reload, on the same manager, so on a `403` they have already finished. They may observe through `DATA.repository` a row that is rolled back. The rollback undoes only what they wrote through that repository. A write through an injected `Repository` uses another connection and stays committed, and an email, a queue message, or a call to another service stays done. Side effects outside the transaction belong in `onAfterCommit`, which runs only after the row is committed, while `onAfterRollback` reports the refusal. Route `onAfterCreate` subscribers do not run on a refusal. When the route owns the transaction, they run after the commit; when it joins an outer owner, they run before that owner commits, so the outer work can still roll the row back.

## Decision Trace, Audit, and Simulator

Both modes produce the same `IApiAuthorizationDecision` shape:

- `decision.principal`
- `decision.effect`
- `decision.mode`
- `decision.scope`
- `decision.permissions`
- `decision.trace`

Hooks mode populates `decision.trace.rules` and `decision.trace.permissions`. IAM mode populates `decision.trace.attachments`, `decision.trace.boundaries`, `decision.trace.documents`, and `decision.trace.statements`.

Use `ApiAuthorizationSimulator` to evaluate authorization outside HTTP requests:

```typescript filename="authorization/simulator.ts" copy
import { EApiRouteType } from "@elsikora/nestjs-crud-automator";

import { ApiAuthorizationSimulator, EApiPolicyEffect, ErrorException } from "@elsikora/nestjs-crud-automator";

const decision = await simulator.evaluate({
	action: EApiRouteType.GET_LIST,
	authorization: itemAuthorization,
	entity: ItemEntity,
	principal,
	routeType: EApiRouteType.GET_LIST,
	requestMetadata: {
		query: {
			limit: 20,
			page: 1,
		},
	},
});

if (decision.effect !== EApiPolicyEffect.ALLOW) {
	throw ErrorException("Access denied");
}
```

The simulator applies the same IAM rules as generated routes: pass `routeType` to select list, create, or row semantics, and pass `resource` to evaluate `resource.*` keys in memory instead of planning them into `decision.scope`.

If you need audit logging, provide `AUTHORIZATION_AUDIT_SINK_TOKEN` with an `IApiAuthorizationAuditSink` implementation. The runtime records every final decision through that sink.

The built-in permission, attachment, and document resolvers follow the module's cache mode. Source-first mode reads the sources on every evaluation; bounded memory mode uses the configured process-local TTL and entry limit.

## Bootstrap Validation

The authorization module validates configuration during bootstrap. Common failures include:

- securable controllers without an `authorization` block
- controllers with an `authorization` block but no `@ApiControllerSecurable()`
- a custom route, declared or inherited, without `resource.action` or with a `resource.entity` other than the controller entity
- a securable controller that has a pattern handler, or that serves a route or a handler replaced on the instance that skips authorization; see [Every Served Route Goes Through Authorization](#every-served-route-goes-through-authorization)
- hooks mode enabled for an entity with no discovered `@ApiAuthorizationPolicy(...)`, for routes that resolve to that mode
- IAM mode without `policyNamespace`, `resourceDefinition`, or registered `documentSources`, for routes that resolve to that mode
- an unknown authorization cache mode or `MEMORY` without positive safe-integer `ttlMs` and `maxEntries`
- `resourceDefinition.namespace` not matching `policyNamespace`
- `resourceDefinition.entity` not matching the controller entity
- invalid `resourceDefinition.fields` entries or duplicate `path` / `queryPath` mappings

IAM policy documents are validated whenever a document source returns them: invalid `Action`, `Resource`, or `Effect` entries, malformed `Condition` maps, and condition operators outside `EApiPolicyConditionOperator` throw instead of being evaluated.

This keeps misconfiguration explicit and prevents silent fallback behavior.

## Test Harness

A test that should not evaluate real policies imports `ApiAuthorizationModule` and replaces two of its providers: `ApiAuthorizationBootstrapValidationService` with `{}`, and `ApiAuthorizationRuntime` with an object whose `evaluate` returns a complete `IApiAuthorizationDecision`:

```typescript
import type { IApiAuthorizationDecision } from "@elsikora/nestjs-crud-automator";

import { ApiAuthorizationBootstrapValidationService, ApiAuthorizationModule, ApiAuthorizationRuntime, ApiSubscriberModule, EApiAuthorizationDecisionType, EApiAuthorizationMode, EApiAuthorizationPrincipalType, EApiPolicyEffect } from "@elsikora/nestjs-crud-automator";
import { Test } from "@nestjs/testing";

const allowDecision = (): IApiAuthorizationDecision<UserEntity> => ({
	action: "test",
	appliedRules: [],
	effect: EApiPolicyEffect.ALLOW,
	mode: EApiAuthorizationMode.HOOKS,
	permissions: [],
	policyId: "test",
	policyIds: [],
	principal: { attributes: {}, id: "test", roles: [], type: EApiAuthorizationPrincipalType.USER },
	resourceType: "UserEntity",
	trace: { decisionType: EApiAuthorizationDecisionType.EXPLICIT_ALLOW, mode: EApiAuthorizationMode.HOOKS },
	transforms: [],
});

const moduleReference = await Test.createTestingModule({
	controllers: [UserController],
	imports: [ApiAuthorizationModule.forRoot(), ApiSubscriberModule],
	providers: [UserService],
})
	.overrideProvider(ApiAuthorizationBootstrapValidationService)
	.useValue({})
	.overrideProvider(ApiAuthorizationRuntime)
	.useValue({ evaluate: async () => allowDecision() })
	.compile();
```

- Build the decision with the enums, not string literals: `EApiPolicyEffect.ALLOW` is `"Allow"`.
- Keep `transforms: []`. A generated route runs the `transforms` of the decision on the response, so a decision without them answers `500`.
- To test a `403`, return `EApiPolicyEffect.DENY` with `EApiAuthorizationDecisionType.EXPLICIT_DENY` in the trace. The guard denies only that effect.
- Keep the module import. A runtime stubbed as a provider without the module fails `app.init()` with the error that names the controller and `ApiAuthorizationModule`, and leaving the import out of the recipe above fails `compile()` with the Nest dependency error that names `ApiAuthorizationGuard`.
- Replacing the validation service turns off every startup check, the one for plain routes and the path parameter comparison of each request included, so keep the recipe in tests. A plain route on a securable controller still answers `403`, because the class guard of `@ApiControllerSecurable()` stays on.

## Migration Notes

When moving from the older authorization API:

1. Replace `subject` with `principal`.
2. Move granted permissions out of the principal and into `hookPermissionSources`.
3. Keep `@ApiControllerSecurable()`, but move mode selection into `@ApiController({ authorization })`.
4. Use `@ApiAuthorizationPolicy(...)` only for hooks mode.
5. Use IAM attachment/document sources for declarative IAM evaluation.
6. Treat source-first resolver reads as the new default. Applications that intentionally need process-local resolver reuse must opt into bounded `MEMORY`, choose finite TTL and entry limits, and own invalidation; the old unbounded, indefinitely retained resolver maps are not preserved.

Startup now checks custom routes on securable controllers, including inherited ones. 4.x read the wrapper class that `@ApiController` returns, which holds no route, so a route of another entity started without an error.

IAM Deny statements are compiled into row exclusions instead of being applied to the whole request or ignored:

- A Deny with `resource.*` keys that compile now hides the matching rows: row routes (`GET`, `UPDATE`, `PARTIAL_UPDATE`, `DELETE`) answer `404` instead of `403`, and lists omit the rows instead of failing. A Deny whose `resource.*` keys cannot compile, which was ignored before, now denies the whole request with `403`.
- Custom routes that run their own queries must apply `decision.scope.where`; it carries both Allow scopes and Deny exclusions.
- Condition operators outside `EApiPolicyConditionOperator` now throw when a document source returns the document, instead of evaluating to false. A list, object or `null` operand is logged as a warning and fails closed: the key fails for an Allow and holds for a Deny, whose other keys still decide whether it matches. It no longer answers `500`. To check that a `principal.*` or `request.*` value is absent, compare it with `""`, which the evaluator treats the same as a missing value.
- An Allow statement whose `resource.*` value is `""` or resolves to `null` or `""` is no longer compiled into an equality scope; the statement is unmatched, so without another matching Allow the request is an implicit deny.
- Row-scoped list Deny patterns that cannot be mapped, such as a prefix pattern that crosses a placeholder or runs over several of them, deny the list with `403`.

From 5.0.0 a securable controller with a plain Nest route, a `@MessagePattern`, `@EventPattern` or `@SubscribeMessage` handler or a handler replaced on the instance without its guards does not start, and neither does an application with a securable controller and no `ApiAuthorizationModule`. Before 5.0.0 such a handler was served with no authorization, or took the identity from the message when it also had `@ApiMethod`, and startup said nothing. Declare an HTTP route with `@ApiRouteCustom` or `@ApiMethod`, move a route or a pattern handler to a controller that is not securable, remove the replacement, and import the module. See [Every Served Route Goes Through Authorization](#every-served-route-goes-through-authorization).

Path values reach authorization validated, as canonical text:

- `ApiAuthorizationGuard` validates path values by the rule of their described columns before evaluation. A malformed value returns `400` with the `ValidationPipe` body instead of being evaluated as a string.
- `request.parameters.*` holds canonical text: decimal integers, lower-case UUIDs, `true` or `false`, ISO 8601 UTC with milliseconds for date-time values, and `YYYY-MM-DD` for date values. `resourcePath` renders the same text, and a `resource.*` condition compares a loaded or planned column value by it. Before 5.0.0 the recipe `"resource.id": "${request.parameters.id}"` returned `404` on a `NUMBER` key, a `DATE_TIME` Deny on `request.parameters` missed other spellings, and a `BOOLEAN` placeholder rendered as `*`.
- Integer path values are accepted only in canonical form, so `016`, `16.0`, or `1.6e1` can no longer address a row that a Deny names as `16`. Boolean path values are only `true` or `false`.
- `request.params` holds the canonical text after `ApiAuthorizationGuard`. A guard that runs before it sees the raw text.
- A securable custom route inherited by several controllers is checked at startup and validated for each of them by its own `resourcePath`; before, the first controller decided for all of them.
- A securable custom route whose `resourcePath` names one of its path parameters must copy it with `ApiPropertyCopy` in its PARAMETERS DTO, or the application fails at startup. The guard runs the route's PARAMETERS DTO before authorization, so IAM sees the values the DTO produces, under any `@Expose` name and through mapped types; a route whose DTO rejects a value now returns `400` even without a host pipe. On a route that declares this DTO, a handler reads the value IAM saw or the request is refused, so a `@Transform` that changes its own output fails at startup or returns `400`: make it stable on its own output or move the conversion into the handler. A DTO that makes a path value an object or a list, drops it, exposes its name from two properties, limits a `@Transform` of it to `groups`, `since`, or `until`, limits its `@Expose` to `since` or `until`, limits a validator of it to `groups`, copies it from a decimal column, or declares a property with `isResponse` fails at startup. Before 5.0.0 `/016`, `/1.6e1`, or an upper-case UUID passed a Deny or a `request.parameters` condition on the canonical value.
- A generated or copied path value on an integer column must be canonical text: `/016` and `/-0` return `400` on a `bigint` or `int` key described as a string, and the default `BIGINT_STRING` pattern refuses `-0` in every request. A UUID path value must be lower-case: an upper-case one returns `400` on a `uuid` column or a column described as `UUID`. A decimal, numeric, float, double, or money column as a path value on a securable route fails at startup, in HOOKS mode as in IAM mode, because a HOOKS policy compares `context.parameters` as text too; use an integer, UUID, or text key.
- `requestMetadata.parameters` and the `parameters` of a hooks policy context are typed `Record<string, string>`, because they hold text; before they were typed as entity values. On a generated route and on a securable custom route, IAM or HOOKS, it is the canonical text the PARAMETERS DTO produces, and a decimal key fails at startup in both modes. Before, a HOOKS custom route ran no DTO in the guard, so its policy read `016` or an upper-case UUID as sent and could miss the row it denies.
- A securable `@ApiRouteCustom` or `@ApiMethod` route with a path parameter, IAM or HOOKS, fails at startup when it declares no PARAMETERS DTO, when the DTO does not describe a path parameter, when a HOOKS DTO holds one without `ApiPropertyCopy` or an `ApiProperty*` decorator, when `@UsePipes` on the method or the controller holds a pipe other than `ValidationPipe`, when a `@Param` argument has a pipe such as `ParseIntPipe`, when a `@Param("id")` argument has a type that compiles to neither `String` nor `Object`, or when a `@Param()` argument is typed as another class than the PARAMETERS DTO. The path parameters are those of the served paths, the global prefix, unless `setGlobalPrefix` excludes the route, and the `RouterModule` path included, and a wildcard in any part of a securable route's path fails at startup. A `ValidationPipe` in `@UsePipes` with `expectedType`, `transformerPackage`, or `validatorPackage` fails at startup too. Before, such a handler could read another value than the policy saw. Declare the PARAMETERS DTO with `ApiPropertyCopy` or `ApiProperty*`, describe the parameters of the prefix and the module path in it, name wildcard values as path parameters, type `@Param("id")` as `string`, and read converted values from `@Param()` typed as that DTO.
- An IAM `@ApiRouteCustom` or `@ApiMethod` route that does not list fails at startup when its `resourcePath` names a placeholder that is not a path parameter of the route. Before, the placeholder rendered as `*`, so a Deny on a value of it never matched. Serve the placeholder as a path parameter copied with `ApiPropertyCopy`, or authorize the route in HOOKS mode; a list keeps mapping such a placeholder to row exclusions.
- A request whose `request.params` holds a path parameter startup did not record for its route answers `500` before the policy, the handler, and any query, and the log names the controller, method, and parameter. Before, a parameter added by an earlier guard or middleware reached the policy unchecked. Do not add path parameters to `request.params` before `ApiAuthorizationGuard`.
- A custom route that describes a path value without a column, and names it in its `resourcePath`, fails at startup. Copy the column of an entity you own that holds the same value:

```typescript
// Before: `resourcePath: "config-data/{id}"` fails at startup
class ConfigDataGetParametersDto {
	@ApiPropertyUUID({ entity: { name: "ConfigData" }, isRequired: true })
	id!: string;
}

// After
class ConfigDataGetParametersDto {
	@ApiPropertyCopy({ dtoType: EApiDtoType.PARAMETERS, entity: () => ConfigDataHistoryEntity, method: EApiRouteType.GET, propertyName: "configDataId" })
	id!: string;
}
```

- Scope values merged against a column, from conditions or hooks, are converted to the column type; a value the column cannot hold becomes a match-nothing condition.
- `ApiAuthorizationGuard` and `ApiAuthorizationBootstrapValidationService` inject `ApiAuthorizationParametersRuleRegistry`, which `ApiAuthorizationModule` provides and exports. A class that extends either one passes it to `super(...)`, and a manual `new`, such as `app.useGlobalGuards(new ApiAuthorizationGuard(app.get(ApiAuthorizationRuntime), app.get(ApiAuthorizationParametersRuleRegistry)))`, passes it as the second argument. A guard built without the registry refuses every request to a securable controller with an error that names `ApiAuthorizationParametersRuleRegistry`, instead of running without custom route rules, and an application that serves a securable controller without `ApiAuthorizationModule` fails at startup with a message that names the module.

In 5.0.0, generated `CREATE` refuses a row outside the decision scope instead of hiding it after the write (see [Scoped CREATE](#scoped-create)):

- A row outside the scope now answers `403` and is not committed, unless an outer owner catches the refusal. It used to answer `404`, and under omitted config or `SUPPORTS` the row stayed in the database. Clients that handled `404` on `CREATE` must handle `403`.
- A scoped `CREATE` under omitted config or `SUPPORTS` now runs in a `ROUTE` transaction. Its function subscribers receive `eventManager`, `onAfterCommit` and `onAfterRollback` now run, and a function configured as `REQUIRED` joins this transaction instead of committing before the reload.
- A non-scoped `CREATE` now runs the same way, in one transaction with its identity read and reload. A failure after the insert no longer leaves a committed row, and each `CREATE` costs `START TRANSACTION` and `COMMIT` on top of its queries. A `CREATE` or `GET` function in mode `NONE` now fails startup under every route mode, and another `NONE` function on its path answers `500` and persists nothing. A `CREATE` or `GET` function in mode `MANDATORY` now starts under omitted config and `SUPPORTS`.
- A date and time primary key in the body now answers `400` when it names a day or an hour the calendar does not hold, such as `2026-02-30T00:00:00Z` or `2026-01-01T24:00:00+01:00`, instead of being stored as the day it rolls over into; when it is more precise than its column or a `Date`; or when it has no zone or offset on a `timestamptz` column. Send an ISO 8601 value with `Z` or an offset with minutes, such as `+05:30`. Microseconds on a `timestamptz(6)` or other microsecond primary key also answer `400`, even though the column can store them, because a `Date` cannot hold them. On `timestamp` and `datetime` columns a value without a zone is parsed in the process time zone, and the second occurrence of an hour that a daylight saving change repeats answers `400`, except on the SQLite family, which stores UTC.
- A controller that generates `CREATE` now fails at startup when the database fills a date and time primary key (a column default, a `CreateDateColumn` or `UpdateDateColumn`, a generated value) on a driver other than `postgres`, `cockroachdb`, or `mariadb`, including `mysql` and `better-sqlite3`. Such a route answered `500` before. Send the key in the body, or use a supported driver or a non-temporal key. A request-scoped controller answers `500` with the same error. A key from the body keeps working on every driver.
- A controller that generates `CREATE` on a route configured as `NONE` now fails at startup. Use `SUPPORTS` or `REQUIRED`. So does one whose `CREATE` or `GET` function runs in mode `NONE`: set that function to `SUPPORTS` or `REQUIRED`.
- A generated `CREATE` now accepts only a `create` and a `get` produced by `@ApiService` or a built-in `@ApiFunction*` decorator. A controller with an undecorated override now fails at startup, even when nobody calls `POST`: decorate it, remove it, or disable the generated `CREATE`. A request-scoped controller answers `500` before the write.
- The `CREATE` reload now matches the whole primary key TypeORM saved for the created row, so a composite key no longer returns or accepts a sibling row. A date and time column matches its whole millisecond, bound like every other temporal read: UTC text for `timestamptz` on PostgreSQL and CockroachDB, a `Date` for `timestamp` and `datetime`, equality for `date`. A column with a `transformer` matches its stored value by equality, and the transformer runs once on the key. On PostgreSQL and CockroachDB an instant key is written as its exact UTC instant, so a historical value no longer answers `500` under the long `timestamp with time zone` alias. A saved row without a value TypeORM knows for every primary column, or a key that matches no row or more than one row, answers `500` and rolls back on every generated `CREATE`, scoped or not.
- A database trigger that overwrites a primary value the body supplied now answers `500`, because the created row no longer matches, and the row is rolled back. Fill such a column through a default TypeORM knows instead.
- A generated `CREATE` takes the key from the row the protected `create` stored, before its function subscribers run. A value an `onAfterCreate` subscriber returns no longer decides which row the scope checks.
- A deferred constraint, such as a deferred foreign key, that fails on the commit of a scoped `CREATE` now answers `500`. Under omitted config or `SUPPORTS` the failure used to come from the insert itself and answered `400`.
- A generated `CREATE` now holds a pool connection for the whole request. Subscribers that read through an injected `Repository` need a second connection and, with a small pool and the default `connectionTimeoutMillis: 0`, hang forever: read through `DATA.repository`, or size the pool and set `extra.connectionTimeoutMillis`.
- `DATA.repository` of `CREATE` function subscribers is now bound to the active transaction, as it is on `GET` and `DELETE`. Reads through it see the uncommitted row and take no second connection. A subclass of `Repository` and `.extend()` keep their methods; a plain object that delegates to a repository is replaced by the plain repository of the entity.
- A controller with `@ApiControllerSecurable` that generates `CREATE` now fails at startup on a date and time primary key finer than a millisecond, on every driver, filled by the database or sent in the body. Declare the column with `precision: 3`, and migrate the column in the database with it.
- A service or a transaction scope of another `DataSource`, called from a subscriber of a `CREATE`, does not roll back with the `CREATE`: compensate for it yourself. A transaction scope on the `DataSource` of the `CREATE` now joins it, rolls back with it, and refuses an `observation`: settle an observation in a scope outside the `CREATE`.
- In a transaction a route or a function owns, `onAfterErrorCreate` now runs after the rollback, with no `DATA.eventManager` and with the service repository as `DATA.repository`. Move work that needs the transaction to `onBeforeErrorCreate`. A subscriber with transaction expectation `REQUIRED` or `MANDATORY` cannot have this hook here.
- A `CREATE` that loses a race with a deadlock or a snapshot error now answers `409` and leaves no row. Clients can send the request again.
- On the SQLite family, every transaction the Automator opens now waits for the previous one per `DataSource`, because all queries share one connection and a rollback would otherwise remove the rows of concurrent requests. Reads and writes outside those transactions can still land inside an open one.

See the [API Reference](/docs/nestjs-crud-automator/api-reference/decorators#apiauthorizationpolicy) for the hooks policy contract and the [controller decorator docs](/docs/nestjs-crud-automator/api-reference/decorators/api-controller/api-controller-securable) for marker behavior.
