# Pagination

Generated GET_LIST routes support page and cursor pagination. Page mode remains the default, so existing controllers and request/response types keep their current contract.

## Page Mode

Omit `pagination` or select it explicitly:

```typescript filename="user.controller.ts" copy
[EApiRouteType.GET_LIST]: {
	request: {
		[EApiControllerRequestTarget.QUERY]: {
			pagination: {
				mode: EApiControllerGetListQueryPaginationMode.PAGE,
			},
		},
	},
}
```

Both `limit` and the 1-based `page` are required integers from 1 through 100:

```http
GET /users?limit=20&page=2
```

The response includes the ordinary count envelope. For example, the exported generic resolves to a concrete user response as follows:

```typescript
type UserPageResponse = IApiGetListResponseResult<UserEntity>;
```

It contains `count`, `currentPage`, `items: Array<UserEntity>`, `totalCount`, and `totalPages`.

Page mode calls the existing decorated `service.getList(...)` with `take = limit` and `skip = limit * (page - 1)`. It is the right choice when a client must jump directly to an arbitrary numbered page or display totals.

## Cursor Mode

Select cursor pagination on the generated GET_LIST query target and provide an explicit stable order:

```typescript filename="game.controller.ts" copy
@ApiController<GameEntity>({
	entity: GameEntity,
	path: "brands/:brandId/games",
	routes: {
		[EApiRouteType.GET_LIST]: {
			read: {
				scope: {
					parameters: [{ parameter: "brandId", field: "brandId" }],
				},
			},
			request: {
				[EApiControllerRequestTarget.QUERY]: {
					order: {
						defaultOrder: [{ direction: EFilterOrderDirection.DESC, field: "position" }],
						fields: {
							isFeatured: { isEnabled: true },
							position: { isEnabled: true },
						},
						tieBreakers: [{ direction: EFilterOrderDirection.ASC, field: "id" }],
						unlistedFields: EApiControllerGetListQueryUnlistedFields.REJECT,
					},
					pagination: {
						mode: EApiControllerGetListQueryPaginationMode.CURSOR,
					},
				},
			},
		},
	},
})
export class BrandGameController {
	constructor(public service: GameService) {}
}
```

Every possible default or client-selected order field must be a described, non-null, direct scalar. The complete primary key, single or composite, must form the final explicit tie-breakers: each component appears exactly once, in any order among them, after every other order entry. No component may appear in `defaultOrder`, earlier in `tieBreakers`, or in the client `fields` map.

A composite primary key lists every component:

```typescript
@Entity("wallet_transactions")
export class WalletTransactionEntity {
	@PrimaryColumn({ precision: 3, type: "timestamptz" })
	@ApiPropertyDescribe({
		format: EApiPropertyDateType.DATE_TIME,
		identifier: EApiPropertyDateIdentifier.CREATED_AT,
		type: EApiPropertyDescribeType.DATE,
	})
	createdAt!: Date;

	@PrimaryColumn({ type: "uuid" })
	@ApiPropertyDescribe({ description: "transaction", type: EApiPropertyDescribeType.UUID })
	id!: string;
}

// Route configuration
order: {
	fields: {},
	tieBreakers: [
		{ direction: EFilterOrderDirection.DESC, field: "createdAt" },
		{ direction: EFilterOrderDirection.ASC, field: "id" },
	],
	unlistedFields: EApiControllerGetListQueryUnlistedFields.REJECT,
},
pagination: { mode: EApiControllerGetListQueryPaginationMode.CURSOR },
```

The token carries one value per effective order entry, including each key component, and the context hash covers that whole order.

### First Window

`limit` is required; `page` is not part of this mode:

```http
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=1
```

The generated response is always the flat cursor envelope. It has no `pageInfo`, booleans, counts, or totals:

```typescript
type GameCursorResponse = IApiGetListCursorResponseResult<GameEntity>;
```

```json
{
	"items": [
		{
			"id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
			"name": "Example Game",
			"position": 42
		}
	],
	"nextCursor": "eyJ2IjoxLCJjIjoiMDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWYwMTIzNDU2Nzg5YWJjZGVmMDEyMzQ1Njc4OWFiY2RlZiIsInZhbHVlcyI6WzQyLCJhYWFhYWFhYS1hYWFhLTRhYWEtOGFhYS1hYWFhYWFhYWFhYWEiXX0",
	"previousCursor": null
}
```

### Forward And Backward Windows

Use the returned cursors without decoding or modifying them:

```http
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=1&after=<nextCursor>
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=1&before=<previousCursor>
```

`after` and `before` are optional but mutually exclusive. Sending both, an empty cursor, a non-canonical cursor, or `page` returns `400 INVALID_CURSOR`. A client may change `limit` between windows.

The first window performs one `service.getMany(...)` query with `take = limit + 1`. A request containing a cursor performs that window query and exactly one opposite-direction `take: 1` probe. No cursor rows, read model, provider, extra service, or signing keys are required.

The HTTP route remains a generated GET_LIST route, so route authorization still uses the existing GET_LIST action and `onBeforeGetList` policy hook. Only the service/function lifecycle uses GET_MANY for each window or probe.

For one CURSOR HTTP request, Automator runs the GET_MANY BEFORE subscriber chain exactly once against a detached copy of the base options. It captures only the candidate `where` and `withDeleted` decision and reuses that same snapshot for the main window and the opposite probe. Candidate predicates are AND-merged with the mandatory query/path/IAM scope and the framework's cursor-window predicate; executable or unstable candidates such as `Raw(...)` and function-backed values fail before either query.

The framework owns each generated window predicate, `order`, and `take`. It also forces an own `cache: false`, shadows `select` and `skip`, and does not permit subscriber `join` or `lock` options. GET_MANY AFTER subscribers still run for each actual query and may redact unrelated fields, but changing item cardinality, sequence, or the raw primary/order tuple fails closed. Later route, authorization, relation, DTO, and serialization work must also preserve the exact flat envelope, both cursors, and protected tuples. Direct `service.getMany(...)` calls do not use this generated-route contract: their BEFORE subscribers run per call and retain the ordinary option/result replacement behavior.

Generated mandatory reads set `cache: false` even when cache configuration is inherited, supplied by a subscriber, or globally enabled. One TypeORM combination cannot honor that guarantee: requested `relations` with an effective `relationLoadStrategy: "query"` while the data source query cache has `alwaysEnabled: true`. Automator rejects that combination before repository I/O; use join relation loading or disable the global always-on query cache.

### Token Context And Authorization

Cursor tokens are strict canonical, unsigned Base64URL values. They contain a version, a context hash, and the typed effective-order values. The context binds:

- generated route;
- inherited path values such as `brandId`;
- normalized query-plan signature;
- normalized actual filter AST, including applied static defaults;
- effective default or client order plus tie-breakers.

The query-plan signature includes each filter field's allowed operations, so widening what a field accepts (for example, UUID fields gained `in`/`notin`) changes the generated query schema name and makes cursor tokens minted before that upgrade fail once with `400 INVALID_CURSOR`; clients simply restart from the first window.

It intentionally excludes `limit` and HOOKS/IAM scope. Path scope, filters, and current HOOKS/IAM authorization are recalculated and AND-merged on every request, including the opposite probe. A token is a navigation position, not an authorization credential.

The token is reversible and contains the typed effective-order values. Automator therefore accepts only potential order/tie fields that are already selected and unconditionally raw-exposed in the GET_LIST response; do not treat cursor contents as secret.

### Protected Order Values

Every potential default, client-selected, or tie-breaker field must survive the database, entity, and response pipelines as the same exact raw scalar value. CURSOR therefore requires a selected, persisted, non-null direct column with compatible `ApiPropertyDescribe` metadata and rejects TypeORM value transformers, array values, and accessor-backed fields. It also rejects entity `@AfterLoad` listeners at bootstrap and fails before query I/O when an active TypeORM subscriber with `afterLoad` can apply to the cursor entity. These hooks could otherwise rewrite a protected tuple after the database comparison. Automator snapshots each active subscriber's `listenTo()` target once; subscriber implementations are trusted TypeORM extension code, so `listenTo()` must be deterministic.

CURSOR v1 deliberately supports only PostgreSQL with the standard text result parsers. The complete supported order-storage matrix is:

- PostgreSQL `boolean` exposed as JavaScript `boolean`;
- signed PostgreSQL `smallint` and `integer` TypeORM declarations exposed as safe JavaScript integers, including increment-generated columns whose DDL uses `SMALLSERIAL` or `SERIAL`;
- numeric TypeScript enums backed by PostgreSQL `smallint` or `integer`;
- signed PostgreSQL `bigint` TypeORM declarations exposed as canonical decimal `BIGINT_STRING` without conversion through `Number`, including increment-generated columns whose DDL uses `BIGSERIAL`;
- native PostgreSQL `uuid` exposed as a canonical UUID string;
- PostgreSQL `timestamptz` TypeORM declarations with a declared integer `precision` from 0 to 3, described as `EApiPropertyDateType.DATE_TIME` and hydrated as a JavaScript `Date`.

`smallserial`, `serial`, and `bigserial` are PostgreSQL DDL forms, not TypeORM column type literals. Declare increment generation over the corresponding supported `smallint`, `integer`, or `bigint` type.

A temporal order field must declare its precision because a JavaScript `Date` holds whole milliseconds only. An unset precision (PostgreSQL defaults to 6), or any precision other than an integer from 0 to 3, fails at bootstrap with an error naming the field. The declared precision must match the physical column. Each seek binds the canonical UTC string to the `timestamptz` comparison, so the boundary is exact in every process time zone and rows sharing one timestamp page without duplicates or gaps through the following order entries.

PostgreSQL `timestamp` has no offset, so a stored wall-clock value does not identify one instant. It fails at bootstrap with an error naming the field and the `timestamptz` rule, as do `Date`-constructor columns, which TypeORM stores as `timestamp`.

`@CreateDateColumn` and `@UpdateDateColumn` take the type the driver gives them, `timestamp` on PostgreSQL, so `@CreateDateColumn({ precision: 3 })` fails at bootstrap with the `timestamptz` storage error. Declare it explicitly as `@CreateDateColumn({ precision: 3, type: "timestamptz" })`. The storage check reads the column type the active driver reports, so it runs at bootstrap, when the DataSource exists.

In a token, a temporal value is a canonical ISO-8601 UTC string with millisecond precision, such as `2026-01-31T12:00:00.000Z`. A non-canonical, impossible, or out-of-range value is `INVALID_CURSOR` before database access. The token form covers years 0001 through 9999.

A stored value outside those years, BC values included, is served normally while it stays inside a window, so the outcome depends on `limit`. The request fails closed only when such a value lands on a row that must become a cursor: the last item of a window with a next page, or the first or last item of a window reached through a cursor. A value a JavaScript `Date` cannot hold, such as year 280000, and PostgreSQL `infinity` and `-infinity` fail closed on every window that reads them, including the extra row read to detect a next page.

A `timestamptz` field can be client-sortable through `fields`, and it is also available through `defaultOrder` and `tieBreakers`.

PostgreSQL binary mode, custom `extra.types` parser configuration, every other PostgreSQL storage type, and every other database driver fail closed before CURSOR query I/O. This restriction applies only to protected CURSOR order/tie-breaker fields. It does not change PAGE behavior or PAGE's existing driver support.

Sub-millisecond temporal, general text, floating-point, and string-enum storage domains are deferred rather than transitionally supported. Any future expansion must be a separate slice rewritten from the current source, choose an exact database/type/parser matrix, and prove the public endpoint against real PostgreSQL E2E. Recovery object `202e2eab` contains superseded design evidence only and must not be restored wholesale.

A cursor is an opaque seek boundary, not ordinary request-field input. `ApiPropertyDescribe` still proves the primitive wire category and raw response exposure, but request-only minimum/maximum, length, pattern, and `multipleOf` constraints do not restrict the boundary. Generated tokens and incoming tokens are capped at 8,192 Base64URL characters, and bootstrap rejects a physical order tuple whose worst-case encoding cannot fit that bound.

Custom item DTOs must declare protected fields under the same names with compatible Automator response decorators. Accessor aliases, `toPlainOnly` transforms, response transformers, authorization transforms, or subscribers may change unrelated fields but cannot conceal or rewrite the protected tuple.

## Filters And Client Sorting

Both modes use the same generated filters and optional paired `orderBy`/`orderDirection` input. In cursor mode, changing filters or effective order invalidates an earlier token:

```http
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=20&orderBy=position&orderDirection=desc
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=20&after=<cursor>&orderBy=position&orderDirection=desc
```

If the client supplies the pair, it replaces `defaultOrder`; server `tieBreakers` are still appended. Duplicate fields retain the earlier occurrence.

When `order.fields` enables no client fields, the generated CURSOR query DTO and OpenAPI schema omit `orderBy` and `orderDirection`, requests containing either control are rejected, and the server default/tie-breaker order remains fixed. The broad TypeScript query helper remains entity-shaped like its PAGE counterpart; generated route metadata is the exact per-route request contract.

## Table Inheritance Roots

Cursor mode works over a [table inheritance](/docs/nestjs-crud-automator/core-concepts/entities#table-inheritance) root. Its `items` are polymorphic, and the envelope stays `items`, `nextCursor`, and `previousCursor`.

Order fields must be root columns; a child column fails at bootstrap. The cursor proof must hold for every variant as well as for the root: a variant with an `@AfterLoad` listener, an accessor over an order field, or a response DTO that hides an order field fails at bootstrap.

## Choosing A Mode

Use PAGE when the UI needs page numbers, random access, or totals. Use CURSOR for next/previous navigation, feeds, and large ordered collections where avoiding large offsets is useful. Cursor mode cannot jump to an arbitrary page because it navigates from a known order position.

For either mode, add a database index matching the common effective order and scope/filter prefix. For example:

```typescript
@Entity("games")
@Index(["brandId", "position", "id"])
export class GameEntity {
	@PrimaryColumn("uuid")
	@ApiPropertyDescribe({ type: EApiPropertyDescribeType.UUID })
	id!: string;

	@Column({ type: "uuid" })
	@ApiPropertyDescribe({ type: EApiPropertyDescribeType.UUID })
	brandId!: string;

	@Column({ nullable: false, type: "varchar" })
	@ApiPropertyDescribe({
		description: "Game name",
		exampleValue: "Example Game",
		format: EApiPropertyStringType.STRING,
		maxLength: 200,
		minLength: 1,
		pattern: "/^.+$/",
		type: EApiPropertyDescribeType.STRING,
	})
	name!: string;

	@Column({ nullable: false, type: "integer" })
	@ApiPropertyDescribe({
		format: EApiPropertyNumberType.INTEGER,
		type: EApiPropertyDescribeType.NUMBER,
	})
	position!: number;

	@Column({ default: false, nullable: false, type: "boolean" })
	@ApiPropertyDescribe({ type: EApiPropertyDescribeType.BOOLEAN })
	isFeatured!: boolean;
}
```

## Empty Results

Page mode returns its ordinary zero-count envelope. Cursor mode keeps all three fields present:

```json
{
	"items": [],
	"nextCursor": null,
	"previousCursor": null
}
```

At an empty cursor edge, the cursor pointing back toward an existing window remains available while the exhausted direction is `null`.

## Temporal Keys, Relations, And Filters

pg serializes a JavaScript `Date` parameter through the process's local offset truncated to whole minutes. Where that offset has seconds, as local mean time does before a zone adopted standard time, the bound value is a different instant. Automator therefore binds no `Date` into a `timestamptz` condition on PostgreSQL and CockroachDB, and no parsed `Date` of a temporal primary key on PostgreSQL, in PAGE, CURSOR, GET_MANY, and GET reads alike:

- On PostgreSQL and CockroachDB, every `Date` that a read compares with a column whose driver-normalized type is `timestamptz` binds as canonical UTC text: filter values and defaults, authorization scopes, primary keys, and the where clause a service caller passes. The column type comes from the driver, so a CockroachDB `@CreateDateColumn()` counts as well. Every operand of such a condition, a `Date` or not, passes through the column transformers once, in order, also inside `And`, `Not`, `In`, and `Between`, and a `Date` they return binds as canonical UTC text; TypeORM does not run them again. An invalid `Date` fails before query I/O. Find options and subscribers keep seeing the `Date` values. Conditions on `timestamp` and `date` columns keep binding a `Date`, whose local wall-clock text is what those columns store. Other drivers bind what the transformers return, as TypeORM does. On every driver, a condition that composes operators, such as `And` or `Not`, on a `timestamptz`, `timestamp`, `datetime`, or `date` column with a transformer runs the transformers once on each operand the same way, because TypeORM would hand them the inner operators instead.
- A client date-time filter value is a UTC instant in the published `YYYY-MM-DDTHH:mm:ss.sssZ` form on every GET_LIST route, a route with default query settings included, and on every column: a value without `Z` or milliseconds, or with an offset such as `+05:30`, answers `400 INVALID_FILTER`, because the process zone would otherwise pick the instant. The check covers relation paths and every value of `in` and `between`; the value of `isnull` and `notnull` is not checked. A calendar `date` field takes `YYYY-MM-DD` text instead. On every date and time column, a value must also name a day of a year from 0001 to 9999 that exists in the calendar: `2024-02-30T10:00:00.000Z`, `2024-03-01T25:00:00.000Z`, and `0000-01-01T00:00:00.000Z` answer `400 INVALID_FILTER`. The [filtering guide](/guides/filtering-and-sorting) lists the date, time, and date-time forms.
- On PostgreSQL and CockroachDB, a paged read of an entity whose primary key includes a `timestamptz`, `timestamp`, or `date` column, with joined relations from `include`, eager relations, or relation filters, loads in two queries: the distinct page keys first, read as PostgreSQL text, then the entities of exactly those keys, bound as that text. Both queries and the count run on one query runner, the transaction's when there is one, so a replicated DataSource answers them from the same replica. Such a page orders only by the entity's own columns; a relation order path fails with an error naming the path.
- Every relation loaded with `relationLoadStrategy: "query"` from an entity whose primary key includes a `timestamptz`, `timestamp`, or `date` column fails, because the relation query binds the parsed keys of the loaded entities. A `"query"` relation whose join columns on either side include such a column fails as well. The check applies at every level of a nested relation path, also when the DataSource supplies `"query"` as the default. An entity that a `"query"` relation loads also joins its eager relations, whatever the read sets for `loadEagerRelations`, so the checks below cover those eager relations too.
- A to-many `@RelationId` property, or a to-many relation named by `loadRelationIds`, fails under the same conditions on every strategy, because TypeORM loads those ids by the same kind of query. The check covers the read entity and every entity its eager or requested relations reach. Ids of a many-to-one or owning one-to-one relation come from the loaded row and stay supported.
- These errors name the relation load, the bound column with its entity, and the recipe: `relationLoadStrategy: "join"`, or loading the relation itself instead of its ids. Every generated route that is not disabled, listed in `routes` or not, fails at application bootstrap, and so does a request relation load from `relations.request.load`, checked against the related entity; any other read fails before query I/O. A reader answers such a read with its generic server error and writes the exact error text to the log at error level.

Other drivers keep TypeORM's own loading. On MySQL, mysql2 writes a `Date` as local wall-clock text without an offset and reads it back through the same local fields, so no truncated offset enters the value. Two limits remain there. A JavaScript `Date` holds milliseconds, so mysql2 truncates a `DATETIME(4)` to `DATETIME(6)` or `TIMESTAMP(4)` to `TIMESTAMP(6)` value to milliseconds when it reads the value, and that value binds back as a different instant. A stored local time that falls into a daylight-saving gap of the process zone does not exist there, so the `Date` shifts it by the gap and it binds back as a different value. Keep such columns at precision 0 to 3 and run the process in UTC, or another zone without daylight-saving gaps, when their values serve as keys or filters.

## Migration Notes

In 5.0.0, cursor mode accepts composite primary keys and `timestamptz` order fields. Existing single-key cursor routes and their tokens keep working without configuration changes.

- A composite primary key must appear in full, each component once, as the final explicit tie-breakers. The components may appear in any order among themselves, and no component may appear in `defaultOrder`, ahead of a non-key tie-breaker, or in client ordering.
- A `timestamptz` order field needs a declared integer `precision` from 0 to 3 that matches the physical column, plus `EApiPropertyDateType.DATE_TIME` metadata. A date column counts by the type the active driver stores it as, so `@CreateDateColumn` needs an explicit `type: "timestamptz"`. `timestamp` and `Date`-constructor columns are not cursor storage.

Bootstrap error texts changed. Update any assertion that matches them:

| Previous text                                                              | Current text                                                                    |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `requires exactly one primary column`                                      | `requires a primary key`                                                        |
| `requires the sole primary field "id" as the final explicit tie-breaker`   | `requires the complete primary key "id" as the final explicit tie-breakers`     |
| `primary field "id" may appear only as the final tie-breaker`              | `primary key "id" may appear only as the final tie-breakers`                    |
| `active repository must use the final order field as its sole primary key` | `active repository must use the final order fields as its complete primary key` |

New temporal bootstrap errors name the field:

- `date order field "createdAt" supports only DATE_TIME metadata in PostgreSQL v1`
- `date order field "createdAt" requires PostgreSQL timestamptz storage because other date column types have no exact instant; the active driver stores it as "timestamp without time zone", so declare the column type "timestamptz"`
- `date order field "createdAt" requires a declared integer column precision from 0 to 3 so a JS Date round-trips exactly`

In 5.0.0, PostgreSQL and CockroachDB reads of temporal keys and `timestamptz` filters change shape:

- A paged read of an entity with a `timestamptz`, `timestamp`, or `date` primary key and joined relations runs a distinct key query and an entity query instead of TypeORM's two-step load. Ordering such a page by a relation path now fails: `Paged read of entity "LedgerEntity" cannot order by relation path "account": an entity with a temporal primary key and joined relations pages only by its own columns`.
- A relation loaded with `relationLoadStrategy: "query"` from an entity with a temporal primary key, or over a temporal join column, now fails at bootstrap for every generated route that is not disabled, listed in `routes` or not, and for each request relation load, and before query I/O for any other read: `Controller "LedgerController" route "getList": relation "account" of entity "LedgerEntity" with relationLoadStrategy "query" cannot load because its query filters by the PostgreSQL date or timestamp column "postedAt" of entity "LedgerEntity", which pg binds through a local offset truncated to whole minutes; use relationLoadStrategy: "join"`. Set `relationLoadStrategy: "join"` on the route's `relations.response.load`, or on the DataSource when it supplies the default.
- A to-many `@RelationId` property or `loadRelationIds` relation of such an entity now fails the same way on every strategy: `@RelationId property "watcherIds" of entity "LedgerEntity" cannot load because its query filters by the PostgreSQL date or timestamp column "postedAt" of entity "LedgerEntity", which pg binds through a local offset truncated to whole minutes; load the relation with relationLoadStrategy: "join" instead`. Remove the property, or the `loadRelationIds` option, and load the relation itself with `relationLoadStrategy: "join"`.
- On PostgreSQL and CockroachDB, a `Date` condition on a `timestamptz` column binds as canonical UTC text when the read runs, after the column transformers ran once on every operand of it. A client filter and an authorization scope on the same `timestamptz` column with a transformer now combine instead of failing with a server error, on `timestamp`, `datetime`, and `date` columns with a transformer as well, and an invalid `Date` in such a condition fails before query I/O.
- A client date-time filter value other than the UTC instant `YYYY-MM-DDTHH:mm:ss.sssZ`, such as `2024-03-01T10:00:00` or `2024-03-01T15:30:00+05:30`, now answers `400 INVALID_FILTER` on every column. Send `2024-03-01T10:00:00.000Z`.
- A client filter value on a date or time column that is not a calendar date or a date-time of a year from 0001 to 9999, such as `2024-02-30T10:00:00Z`, `2024-03-01T25:00:00Z`, or `0000-01-01T00:00:00Z`, now answers `400 INVALID_FILTER` on every GET_LIST route instead of a server error or a shifted date.
- `timestamptz`, `timestamp with time zone`, and `uuid` columns are orderable: generated PAGE `orderBy` values now include those fields, and a CURSOR route can enable a `timestamptz` field that meets the cursor storage rules as a client order field. Exclude a field from ordering with `useAsOrderByFilter: false` in its `ApiPropertyDescribe` GET_LIST query properties. A CURSOR route that enables a primary key component as a client order field now fails with `CURSOR GET_LIST primary key "id" may appear only as the final tie-breakers` instead of `GET_LIST order field "id" is not an enabled direct scalar path`.

From 5.0.0, an `@ApiController` whose `service.repository` is not a TypeORM repository fails at application bootstrap with `Controller "UserController": service has no TypeORM repository`, also when every generated route is disabled. A repository from a second installed copy of TypeORM counts. Inject the entity repository as `public repository` in the service constructor.
