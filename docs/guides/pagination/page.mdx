# Pagination

Generated GET_LIST routes support page and cursor pagination. Page mode remains the default, so existing controllers and request/response types keep their current contract.

## Page Mode

Omit `pagination` or select it explicitly:

```typescript filename="user.controller.ts" copy
[EApiRouteType.GET_LIST]: {
	request: {
		[EApiControllerRequestTarget.QUERY]: {
			pagination: {
				mode: EApiControllerGetListQueryPaginationMode.PAGE,
			},
		},
	},
}
```

Both `limit` and the 1-based `page` are required integers from 1 through 100:

```http
GET /users?limit=20&page=2
```

The response includes the ordinary count envelope. For example, the exported generic resolves to a concrete user response as follows:

```typescript
type UserPageResponse = IApiGetListResponseResult<UserEntity>;
```

It contains `count`, `currentPage`, `items: Array<UserEntity>`, `totalCount`, and `totalPages`.

Page mode calls the existing decorated `service.getList(...)` with `take = limit` and `skip = limit * (page - 1)`. It is the right choice when a client must jump directly to an arbitrary numbered page or display totals.

## Cursor Mode

Select cursor pagination on the generated GET_LIST query target and provide an explicit stable order:

```typescript filename="game.controller.ts" copy
@ApiController<GameEntity>({
	entity: GameEntity,
	path: "brands/:brandId/games",
	routes: {
		[EApiRouteType.GET_LIST]: {
			read: {
				scope: {
					parameters: [{ parameter: "brandId", field: "brandId" }],
				},
			},
			request: {
				[EApiControllerRequestTarget.QUERY]: {
					order: {
						defaultOrder: [{ direction: EFilterOrderDirection.DESC, field: "position" }],
						fields: {
							isFeatured: { isEnabled: true },
							position: { isEnabled: true },
						},
						tieBreakers: [{ direction: EFilterOrderDirection.ASC, field: "id" }],
						unlistedFields: EApiControllerGetListQueryUnlistedFields.REJECT,
					},
					pagination: {
						mode: EApiControllerGetListQueryPaginationMode.CURSOR,
					},
				},
			},
		},
	},
})
export class BrandGameController {
	constructor(public service: GameService) {}
}
```

Every possible default or client-selected order field must be a described, non-null, direct scalar. The complete primary key, single or composite, must form the final explicit tie-breakers: each component appears exactly once, in any order among them, after every other order entry. No component may appear in `defaultOrder`, earlier in `tieBreakers`, or in the client `fields` map.

A composite primary key lists every component:

```typescript
@Entity("wallet_transactions")
export class WalletTransactionEntity {
	@PrimaryColumn({ precision: 3, type: "timestamptz" })
	@ApiPropertyDescribe({
		format: EApiPropertyDateType.DATE_TIME,
		identifier: EApiPropertyDateIdentifier.CREATED_AT,
		type: EApiPropertyDescribeType.DATE,
	})
	createdAt!: Date;

	@PrimaryColumn({ type: "uuid" })
	@ApiPropertyDescribe({ description: "transaction", type: EApiPropertyDescribeType.UUID })
	id!: string;
}

// Route configuration
order: {
	fields: {},
	tieBreakers: [
		{ direction: EFilterOrderDirection.DESC, field: "createdAt" },
		{ direction: EFilterOrderDirection.ASC, field: "id" },
	],
	unlistedFields: EApiControllerGetListQueryUnlistedFields.REJECT,
},
pagination: { mode: EApiControllerGetListQueryPaginationMode.CURSOR },
```

The token carries one value per effective order entry, including each key component, and the context hash covers that whole order.

### First Window

`limit` is required; `page` is not part of this mode:

```http
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=1
```

The generated response is always the flat cursor envelope. It has no `pageInfo`, booleans, counts, or totals:

```typescript
type GameCursorResponse = IApiGetListCursorResponseResult<GameEntity>;
```

```json
{
	"items": [
		{
			"id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
			"name": "Example Game",
			"position": 42
		}
	],
	"nextCursor": "eyJ2IjoxLCJjIjoiMDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWYwMTIzNDU2Nzg5YWJjZGVmMDEyMzQ1Njc4OWFiY2RlZiIsInZhbHVlcyI6WzQyLCJhYWFhYWFhYS1hYWFhLTRhYWEtOGFhYS1hYWFhYWFhYWFhYWEiXX0",
	"previousCursor": null
}
```

### Forward And Backward Windows

Use the returned cursors without decoding or modifying them:

```http
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=1&after=<nextCursor>
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=1&before=<previousCursor>
```

`after` and `before` are optional but mutually exclusive. Sending both, an empty cursor, a non-canonical cursor, or `page` returns `400 INVALID_CURSOR`. A client may change `limit` between windows.

The first window performs one `service.getMany(...)` query with `take = limit + 1`. A request containing a cursor performs that window query and exactly one opposite-direction `take: 1` probe. No cursor rows, read model, provider, extra service, or signing keys are required.

The HTTP route remains a generated GET_LIST route, so route authorization still uses the existing GET_LIST action and `onBeforeGetList` policy hook. Only the service/function lifecycle uses GET_MANY for each window or probe.

For one CURSOR HTTP request, Automator runs the GET_MANY BEFORE subscriber chain exactly once against a detached copy of the base options. It captures only the candidate `where` and `withDeleted` decision and reuses that same snapshot for the main window and the opposite probe. Candidate predicates are AND-merged with the mandatory query/path/IAM scope and the framework's cursor-window predicate; executable or unstable candidates such as `Raw(...)` and function-backed values fail before either query.

The framework owns each generated window predicate, `order`, and `take`. It also forces an own `cache: false`, shadows `select` and `skip`, and does not permit subscriber `join` or `lock` options. GET_MANY AFTER subscribers still run for each actual query and may redact unrelated fields, but changing item cardinality, sequence, or the raw primary/order tuple fails closed. Later route, authorization, relation, DTO, and serialization work must also preserve the exact flat envelope, both cursors, and protected tuples. Direct `service.getMany(...)` calls do not use this generated-route contract: their BEFORE subscribers run per call and retain the ordinary option/result replacement behavior.

Generated mandatory reads set `cache: false` even when cache configuration is inherited, supplied by a subscriber, or globally enabled. One TypeORM combination cannot honor that guarantee: requested `relations` with an effective `relationLoadStrategy: "query"` while the data source query cache has `alwaysEnabled: true`. Automator rejects that combination before repository I/O; use join relation loading or disable the global always-on query cache.

### Token Context And Authorization

Cursor tokens are strict canonical, unsigned Base64URL values. They contain a version, a context hash, and the typed effective-order values. The context binds:

- generated route;
- inherited path values such as `brandId`;
- normalized query-plan signature;
- normalized actual filter AST, including applied static defaults;
- effective default or client order plus tie-breakers.

The query-plan signature includes each filter field's allowed operations, so widening what a field accepts (for example, UUID fields gained `in`/`notin`) changes the generated query schema name and makes cursor tokens minted before that upgrade fail once with `400 INVALID_CURSOR`; clients simply restart from the first window.

It intentionally excludes `limit` and HOOKS/IAM scope. Path scope, filters, and current HOOKS/IAM authorization are recalculated and AND-merged on every request, including the opposite probe. A token is a navigation position, not an authorization credential.

The token is reversible and contains the typed effective-order values. Automator therefore accepts only potential order/tie fields that are already selected and unconditionally raw-exposed in the GET_LIST response; do not treat cursor contents as secret.

### Protected Order Values

Every potential default, client-selected, or tie-breaker field must survive the database, entity, and response pipelines as the same exact raw scalar value. CURSOR therefore requires a selected, persisted, non-null direct column with compatible `ApiPropertyDescribe` metadata and rejects TypeORM value transformers, array values, and accessor-backed fields. It also rejects entity `@AfterLoad` listeners at bootstrap and fails before query I/O when an active TypeORM subscriber with `afterLoad` can apply to the cursor entity. These hooks could otherwise rewrite a protected tuple after the database comparison. Automator snapshots each active subscriber's `listenTo()` target once; subscriber implementations are trusted TypeORM extension code, so `listenTo()` must be deterministic.

CURSOR v1 deliberately supports only PostgreSQL with the standard text result parsers. The complete supported order-storage matrix is:

- PostgreSQL `boolean` exposed as JavaScript `boolean`;
- signed PostgreSQL `smallint` and `integer` TypeORM declarations exposed as safe JavaScript integers, including increment-generated columns whose DDL uses `SMALLSERIAL` or `SERIAL`;
- numeric TypeScript enums backed by PostgreSQL `smallint` or `integer`;
- signed PostgreSQL `bigint` TypeORM declarations exposed as canonical decimal `BIGINT_STRING` without conversion through `Number`, including increment-generated columns whose DDL uses `BIGSERIAL`;
- native PostgreSQL `uuid` exposed as a canonical UUID string;
- PostgreSQL `timestamp` and `timestamptz` TypeORM declarations with a declared `precision` of at most 3, described as `EApiPropertyDateType.DATE_TIME` and hydrated as a JavaScript `Date`.

`smallserial`, `serial`, and `bigserial` are PostgreSQL DDL forms, not TypeORM column type literals. Declare increment generation over the corresponding supported `smallint`, `integer`, or `bigint` type.

A temporal order field must declare its precision because a JavaScript `Date` holds whole milliseconds only. An unset precision (PostgreSQL defaults to 6) or a precision above 3 fails at bootstrap with an error naming the field. The declared precision must match the physical column. Each seek compares `Date` values equal to the stored milliseconds, so rows sharing one timestamp page without duplicates or gaps through the following order entries.

In a token, a temporal value is a canonical ISO-8601 UTC string with millisecond precision, such as `2026-01-31T12:00:00.000Z`. A non-canonical, impossible, or out-of-range value is `INVALID_CURSOR` before database access. The token form covers years 0000 through 9999; a stored value outside that range, including PostgreSQL `infinity`, fails closed when a window containing it is read.

`timestamp` stores no offset, so the standard parser and parameter binding both use process-local wall-clock time. Every process serving one route must therefore run in the same time zone. A stored wall-clock value inside that zone's daylight-saving gap has no exact `Date`, so prefer `timestamptz`, or run in UTC, wherever other writers can produce such values. The `pg` `parseInputDatesAsUTC` default breaks this symmetry and fails closed for `timestamp` order fields.

Client order selection follows the GET_LIST order baseline, which includes `timestamp` and `Date` columns but not `timestamptz`. A `timestamptz` field is available through `defaultOrder` and `tieBreakers`.

PostgreSQL binary mode, custom `extra.types` parser configuration, every other PostgreSQL storage type, and every other database driver fail closed before CURSOR query I/O. This restriction applies only to protected CURSOR order/tie-breaker fields. It does not change PAGE behavior or PAGE's existing driver support.

Sub-millisecond temporal, general text, floating-point, and string-enum storage domains are deferred rather than transitionally supported. Any future expansion must be a separate slice rewritten from the current source, choose an exact database/type/parser matrix, and prove the public endpoint against real PostgreSQL E2E. Recovery object `202e2eab` contains superseded design evidence only and must not be restored wholesale.

A cursor is an opaque seek boundary, not ordinary request-field input. `ApiPropertyDescribe` still proves the primitive wire category and raw response exposure, but request-only minimum/maximum, length, pattern, and `multipleOf` constraints do not restrict the boundary. Generated tokens and incoming tokens are capped at 8,192 Base64URL characters, and bootstrap rejects a physical order tuple whose worst-case encoding cannot fit that bound.

Custom item DTOs must declare protected fields under the same names with compatible Automator response decorators. Accessor aliases, `toPlainOnly` transforms, response transformers, authorization transforms, or subscribers may change unrelated fields but cannot conceal or rewrite the protected tuple.

## Filters And Client Sorting

Both modes use the same generated filters and optional paired `orderBy`/`orderDirection` input. In cursor mode, changing filters or effective order invalidates an earlier token:

```http
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=20&orderBy=position&orderDirection=desc
GET /brands/bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb/games?limit=20&after=<cursor>&orderBy=position&orderDirection=desc
```

If the client supplies the pair, it replaces `defaultOrder`; server `tieBreakers` are still appended. Duplicate fields retain the earlier occurrence.

When `order.fields` enables no client fields, the generated CURSOR query DTO and OpenAPI schema omit `orderBy` and `orderDirection`, requests containing either control are rejected, and the server default/tie-breaker order remains fixed. The broad TypeScript query helper remains entity-shaped like its PAGE counterpart; generated route metadata is the exact per-route request contract.

## Table Inheritance Roots

Cursor mode works over a [table inheritance](/docs/nestjs-crud-automator/core-concepts/entities#table-inheritance) root. Its `items` are polymorphic, and the envelope stays `items`, `nextCursor`, and `previousCursor`.

Order fields must be root columns; a child column fails at bootstrap. The cursor proof must hold for every variant as well as for the root: a variant with an `@AfterLoad` listener, an accessor over an order field, or a response DTO that hides an order field fails at bootstrap.

## Choosing A Mode

Use PAGE when the UI needs page numbers, random access, or totals. Use CURSOR for next/previous navigation, feeds, and large ordered collections where avoiding large offsets is useful. Cursor mode cannot jump to an arbitrary page because it navigates from a known order position.

For either mode, add a database index matching the common effective order and scope/filter prefix. For example:

```typescript
@Entity("games")
@Index(["brandId", "position", "id"])
export class GameEntity {
	@PrimaryColumn("uuid")
	@ApiPropertyDescribe({ type: EApiPropertyDescribeType.UUID })
	id!: string;

	@Column({ type: "uuid" })
	@ApiPropertyDescribe({ type: EApiPropertyDescribeType.UUID })
	brandId!: string;

	@Column({ nullable: false, type: "varchar" })
	@ApiPropertyDescribe({
		description: "Game name",
		exampleValue: "Example Game",
		format: EApiPropertyStringType.STRING,
		maxLength: 200,
		minLength: 1,
		pattern: "/^.+$/",
		type: EApiPropertyDescribeType.STRING,
	})
	name!: string;

	@Column({ nullable: false, type: "integer" })
	@ApiPropertyDescribe({
		format: EApiPropertyNumberType.INTEGER,
		type: EApiPropertyDescribeType.NUMBER,
	})
	position!: number;

	@Column({ default: false, nullable: false, type: "boolean" })
	@ApiPropertyDescribe({ type: EApiPropertyDescribeType.BOOLEAN })
	isFeatured!: boolean;
}
```

## Empty Results

Page mode returns its ordinary zero-count envelope. Cursor mode keeps all three fields present:

```json
{
	"items": [],
	"nextCursor": null,
	"previousCursor": null
}
```

At an empty cursor edge, the cursor pointing back toward an existing window remains available while the exhausted direction is `null`.
