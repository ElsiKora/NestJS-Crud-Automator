# DTOs

Data Transfer Objects (DTOs) in NestJS CRUD Automator are automatically generated based on entity metadata. The library creates appropriate DTOs for request bodies, query parameters, and responses with built-in validation and transformation.

## Automatic DTO Generation

DTOs are generated automatically from entity properties decorated with `@ApiPropertyDescribe`:

```typescript filename="user.entity.ts" copy
@Entity("users")
export class UserEntity {
	@PrimaryGeneratedColumn("uuid")
	@ApiPropertyDescribe({
		type: EApiPropertyDescribeType.UUID,
		description: "User ID",
	})
	id: string;

	@Column()
	@ApiPropertyDescribe({
		type: EApiPropertyDescribeType.STRING,
		description: "Username",
		format: EApiPropertyStringType.STRING,
		minLength: 3,
		maxLength: 20,
		pattern: "/^[a-zA-Z0-9_-]+$/",
		exampleValue: "john_doe",
	})
	username: string;
}
```

This automatically generates:

- **CreateUserDto** - For POST requests
- **UpdateUserDto** - For PUT update/replace requests where enabled fields keep their requiredness
- **PartialUpdateUserDto** - For PATCH partial-update requests where enabled body fields are optional-friendly
- **UserResponseDto** - For responses
- **GetListQueryDto** - For GET /users query parameters

### Property-wide exclusion

Set `isAutoDtoEnabled: false` on `@ApiPropertyDescribe` when the entity still needs complete metadata but the property must not appear in any generated DTO:

```typescript
@Column({ default: false, type: "boolean" })
@ApiPropertyDescribe({
	description: "Internal eligibility flag",
	isAutoDtoEnabled: false,
	type: EApiPropertyDescribeType.BOOLEAN,
})
internalEligibility!: boolean;
```

Omitted or `true` keeps normal generation. `false` preserves `MetadataStorage`, TypeORM mapping, and manual DTO behavior while excluding the property from generated BODY, PARAMETERS, QUERY, and RESPONSE DTOs, generated Swagger relation components, and metadata-driven or typed client filter/order fields. Route- or DTO-level `isEnabled: true`, generated GET identity, `read.scope.parameters`, and query allowlists cannot reopen it.

An explicit `@ApiPropertyCopy` can deliberately place the source property in a manual DTO; only the global exclusion is bypassed, so the remaining route/DTO, guard, and validation rules still apply. PAGE server-only defaults and tie-breakers may use a hidden described scalar. CURSOR cannot, because every cursor order field must remain exposed in the generated response.

## DTO Types

### Body DTOs

Used for request bodies in CREATE and UPDATE operations.

**Create DTO** includes:

- Properties enabled for `[EApiRouteType.CREATE][EApiDtoType.BODY]`
- Validation rules from property configuration
- Required fields based on `isRequired`

**Update DTO** includes:

- Properties enabled for `[EApiRouteType.UPDATE][EApiDtoType.BODY]` or `[EApiRouteType.PARTIAL_UPDATE][EApiDtoType.BODY]`
- `UPDATE` bodies keep required fields required; `PARTIAL_UPDATE` bodies are optional-friendly
- Validation rules still apply when provided

Generated CREATE, UPDATE, and PARTIAL_UPDATE bodies always omit server-owned date properties identified by `EApiPropertyDateIdentifier.CREATED_AT`, `RECEIVED_AT`, or `UPDATED_AT`. This rule is semantic and independent of the property name. Response DTOs retain these timestamps, while `DATE` and other business/range identifiers remain eligible for write bodies.

### Query DTOs

Used for filtering, sorting, and PAGE/CURSOR pagination in GET_LIST operations. PAGE remains the default:

```typescript
// Generated GetListQueryDto structure
interface GetListQueryDto {
	limit: number;
	page: number;
	orderBy?: string;
	orderDirection?: "asc" | "desc";
	"username[operator]"?: EFilterOperation;
	"username[value]"?: string;
	"username[values]"?: string[];
}
```

Example usage:

```
GET /users?limit=10&page=1&username[operator]=cont&username[value]=john&orderBy=createdAt&orderDirection=desc
```

CURSOR mode replaces `page` with optional mutually exclusive `after`/`before` while keeping `limit` and filters. The optional paired `orderBy`/`orderDirection` controls are present only when `order.fields` enables at least one client-order field.

GET_LIST query DTOs remain dynamically generated from entity metadata. Optional route `request[EApiControllerRequestTarget.QUERY].filter`, `order`, and `pagination` configuration narrows or overlays that metadata and selects the envelope; it does not replace generation with a hand-written DTO. Automator compiles a normalized immutable plan and uses it for:

- The runtime query DTO and strict query parser.
- Controller- and plan-scoped DTO cache identity.
- OpenAPI deep-object `oneOf` filter branches.
- Typed TypeORM filter values and the direct-scalar order allowlist.

Omitting `filter` or `order` preserves that section's legacy metadata-driven behavior in PAGE mode; omitting `pagination` selects PAGE. A route plan cannot re-enable a field disabled by entity query metadata, and response visibility does not grant query exposure.

PAGE requires `limit` and `page` integers from 1 through 100 and maps them to TypeORM `take` and `skip`. CURSOR requires `limit`, rejects `page`, and generates the flat `{ items, nextCursor, previousCursor }` response. Its explicit order must end with the complete primary key, single or composite, as server-only tie-breakers, and all possible order fields must be described non-null direct scalars from the PostgreSQL-only v1 storage matrix in [Pagination](/docs/nestjs-crud-automator/guides/pagination). A client order pair replaces the defaults in either mode, then tie-breakers are appended and duplicate fields are removed. PAGE is unchanged.

### Read PARAMETERS DTOs

Generated GET and GET_LIST routes can create path-parameter DTOs for nested owner scopes:

```typescript
@ApiController<GameEntity>({
	entity: GameEntity,
	path: "providers/:providerKey/games",
	routes: {
		[EApiRouteType.GET]: {
			identity: { parameter: "gameId" },
			read: {
				scope: {
					parameters: [{ parameter: "providerKey", field: "providerId" }],
				},
			},
		},
		[EApiRouteType.GET_LIST]: {
			read: {
				scope: {
					parameters: [{ parameter: "providerKey", field: "providerId" }],
				},
			},
		},
	},
})
export class ProviderGameController {}
```

Automator copies validation/transformation and Swagger metadata from the primary or mapped described direct scalar field to each external parameter name. In the example, the GET PARAMETERS DTO contains `gameId` and `providerKey`; the TypeORM identity predicate still targets the actual primary column. GET_LIST contains only the inherited mapping. Omit `identity` to keep the primary-column name, and use identity without scope only when the controller path has no inherited parameters. DTO/schema identity is route- and mapping-scoped, so controllers over the same entity can use different external names safely.

All inherited `:parameters` must be mapped exactly once. A manual `dto[EApiDtoType.PARAMETERS]` is mutually exclusive with configured read identity or scope; `autoDto[EApiDtoType.PARAMETERS]` validators can still decorate the generated DTO.

Identity aliases do not rename response fields. A manual response DTO can use the standard `class-transformer` alias when its wire contract needs `gameId` for an entity value named `id`:

```typescript
import { Expose } from "class-transformer";

export class PublicGameResponseDto {
	@Expose({ name: "id" })
	@ApiPropertyString({
		description: "Public game identifier",
		entity: () => PublicGameResponseDto,
		exampleValue: "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
		format: EApiPropertyStringType.UUID,
		isRequired: true,
		isResponse: true,
		maxLength: 36,
		minLength: 36,
		pattern: "/^[0-9a-f-]{36}$/",
	})
	gameId!: string;
}
```

The order of `@Expose` and the Automator property decorator does not matter, and neither does when a lazy `entity` resolves. An explicit `@Expose` keeps its name, groups and versions, also one inherited from a parent class; the property decorator exposes a property under its own name only when no `@Expose` covers it. `isExpose: false` and `@Exclude` win over an `@Expose` without a name in either order.

A named `@Expose`, own or inherited, next to `isExpose: false` or an `@Exclude` that applies to plain objects fails at startup whatever the decorator order: class-transformer would still read the exposed name from a plain object into the excluded property, on a request body and on a custom route response. `@Exclude({ toPlainOnly: true })` stays legal next to a name.

#### `@Expose` Migration Notes

Before 5.0.0 an `@ApiProperty*` decorator that ran after an explicit `@Expose` erased it, so only `@Expose` above the property decorator with an `entity` that resolves at once kept its name. A property that lost its name that way now follows its `@Expose`. A request body is read from the exposed name, while validation errors name the declared property. `ClassSerializerInterceptor` and `instanceToPlain` write the exposed name. `@ApiRouteCustom` without the interceptor reads the exposed name from what the handler returns and sends the property key, so a handler that returns the property key now gets `{}` where it got `{"value":"declaredKey"}`. Remove the `@Expose` to keep the property name.

A named `@Expose` next to `isExpose: false` or `@Exclude` used to read the exposed name into the excluded property, and now fails at startup. Remove one of them, or limit the exclude with `@Exclude({ toPlainOnly: true })`.

An application bundled so that `class-transformer` resolves to another entry than its CommonJS one loads two copies, and fails at decoration with `Cannot read class-transformer metadata`. Alias exactly `class-transformer` to `class-transformer/cjs/index.js`, set `main` before `module` in the bundler's `mainFields`, or mark both `class-transformer` and `class-transformer/cjs/storage.js` external. The alias must not touch subpaths: webpack needs `class-transformer$`, and esbuild needs a second alias of `class-transformer/cjs/storage.js` to itself. The peer range stays on `0.5.1`, the release whose `cjs/storage.js` this reads.

### Response DTOs

Control which properties are included in responses:

```typescript
@Column()
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.STRING,
  description: "Password hash",
  format: EApiPropertyStringType.PASSWORD,
  minLength: 1,
  maxLength: 128,
  pattern: "/^[\\s\\S]{1,128}$/",
  exampleValue: "hashed-password",
  properties: {
    [EApiRouteType.GET]: {
      [EApiDtoType.RESPONSE]: { isEnabled: false, isResponse: true },
    },
    [EApiRouteType.GET_LIST]: {
      [EApiDtoType.RESPONSE]: { isEnabled: false, isResponse: true },
    },
  },
})
password: string;
```

## Generated Schema Names

Every DTO that Automator generates for a controller route is named after that controller, and the class name is also the OpenAPI component name. The name starts with the controller's schema prefix: the controller class name without a trailing `Controller`. When nothing is left after removing it, the prefix is the full class name. `AdminUserController` has the prefix `AdminUser`, and `UserController` has `User`. The entity name is not part of generated names.

| Generated DTO                                             | Name                                                                                                                                                                                                                                                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Body, query, parameters, response                         | `<Prefix><Route><DtoType>DTO`, for example `UserGetResponseDTO`, `UserCreateBodyDTO`, `UserPartialUpdateBodyDTO`                                                                                                                                                                  |
| GET_LIST page and cursor wrapper                          | `<Prefix>GetListPageDTO`, or `<Prefix>GetListCursorPageDTO` in CURSOR mode                                                                                                                                                                                                        |
| GET_LIST wrapper around a `{ itemType }` response DTO     | `<Prefix>GetListResponse<ItemType>`, or `<Prefix>GetListResponse<ItemType>Cursor` in CURSOR mode, where `<ItemType>` is the item class name: `UserController` with `PublicUserResponseDto` gives `UserGetListResponsePublicUserResponseDto`                                       |
| Nested DTO at any depth                                   | `<Parent><Property>DTO`, or `<Parent><Property><Variant>DTO` for a variant, where `<Parent>` is the name of the DTO that holds the property without `DTO`                                                                                                                         |
| Table inheritance variant response                        | `<Prefix><Route>Response<Value>DTO`, see [Table Inheritance](/docs/nestjs-crud-automator/core-concepts/entities#table-inheritance). A root without a `@ChildEntity` value uses its discriminator value, which is the root class name: `<Prefix><Route>Response<RootClassName>DTO` |
| Typed GET_LIST query, GET identity, read scope parameters | `<Prefix>GetListQuery<signature>DTO`, `<Prefix>GetIdentity<signature>DTO`, `<Prefix>GetParameters<signature>DTO`, `<Prefix>GetListParameters<signature>DTO`                                                                                                                       |
| Body, query, parameters of a custom route                 | `<Prefix><Method><DtoType>DTO`, where `<Method>` is the handler method name in PascalCase: `PublicUserController.getMe` gives `PublicUserGetMeParametersDTO`                                                                                                                      |

Nested names follow one recursive rule: a relation, a dynamic object variant, or a manual DTO copied into a generated DTO is named after the DTO that holds it plus the property name in PascalCase, and the variant name for a variant. A relation `owner` of `UserGetResponseDTO` is `UserGetResponseOwnerDTO`. The same relation inside variant `V1` of property `details` is `UserGetResponseDetailsV1OwnerDTO`, because its parent is `UserGetResponseDetailsV1DTO`. A relation or dynamic object that `@ApiPropertyCopy` copies into a hand-written DTO follows the same rule with that DTO as the parent: `currency` copied into `DepositResponseDTO` gives `DepositResponseCurrencyDTO`, and variant `V1` of a copied `details` gives `DepositResponseDetailsV1DTO`. The property is the one of the host DTO that `@ApiPropertyCopy` decorates, not the entity property it copies, so one relation copied into `currency` and `previousCurrency` gives `DepositResponseCurrencyDTO` and `DepositResponsePreviousCurrencyDTO`. A trailing `DTO` is removed from the parent name in any case, so the host classes `DepositResponseDTO` and `DepositResponseDto` both give `DepositResponseCurrencyDTO`. A class named only `DTO` keeps its name.

The PascalCase segment of a property or variant name uppercases its first letter, removes the separators `_`, `-`, `.` and spaces, and uppercases the letter after each of them. Every other letter is kept as written. One trailing `DTO` in any case is removed, because the name adds its own, unless nothing else is left: a property named `dto` is a legal name and keeps it, so it gives `…DtoDTO`. A name made only of separators, such as `_`, fails startup naming the DTO and the property, because the nested DTO would get the name of its host. The same goes for the handler of a custom route that generates DTOs, because its name replaces the route type:

| Property or variant | Segment       |
| ------------------- | ------------- |
| `owner`             | `Owner`       |
| `v2Item`            | `V2Item`      |
| `HTMLContent`       | `HTMLContent` |
| `userID`            | `UserID`      |
| `ID`                | `ID`          |
| `created_by`        | `CreatedBy`   |
| `x-id`              | `XId`         |
| `v2-beta`           | `V2Beta`      |
| `pageDTO`           | `Page`        |
| `page_dto`          | `Page`        |
| `pageDtoDto`        | `PageDto`     |
| `dto`               | `Dto`         |
| `DTO`               | `DTO`         |

A name does not depend on which other controllers exist, so adding a controller never renames another controller's schemas.

No property name, variant name or table inheritance value can produce a name with a fixed suffix. Every generated DTO that holds nested DTOs is named `<Prefix><Route or Method><DtoType>…`, where `<DtoType>` is `Body`, `Parameters`, `Query` or `Response`, so a nested name always contains that route and DTO type followed by a segment that is not empty. That is why it never equals `<Prefix><Route or Method><DtoType>DTO`. The GET_LIST wrappers `<Prefix>GetListPageDTO` and `<Prefix>GetListCursorPageDTO` and the `Exception*DTO` names have no DTO type after the route, the typed query, identity and read scope parameter DTOs never hold nested DTOs, and the generated enum names do not end in `DTO`. The `{ itemType }` wrapper `<Prefix>GetListResponse<ItemType>` does contain `Response`, and its last part is a class name you choose. A relation named `items`, `page`, `cursor`, `query`, `parameters`, `body` or `response` therefore gets its own component, for example `UserGetListResponseItemsDTO` for a relation `items` next to the wrapper `UserGetListPageDTO`. Two generated names can still meet when one of them comes from a name you choose: a dynamic object variant or a table inheritance value that equals another property name plus a suffix, two property names that differ only by separators or a trailing `DTO`, such as `dto` and `_dto`, a custom route handler name, an `itemType` class name, or a hand-written DTO class name. The [startup checks](#startup-checks) report these.

A custom route declared with `@ApiRouteCustom` uses its handler method name in place of the route type, so its generated DTOs stay apart from the generated route of the same type on its controller, also when the two routes have different guards. The response DTO of a custom route is the one you configure.

A custom route that a decorated controller inherits from a base class or a mixin gets its DTOs from that controller, and keeps its guards and interceptors: `UserController extends BaseController` with a custom route `getMe` declared in `BaseController` generates `UserGetMeParametersDTO`, and every other controller that extends `BaseController` generates its own. `@ApiController` gives the controller its own copy of the inherited handler, which calls the handler of the base class, so Nest and Swagger read the route from the controller.

Exception DTOs such as `ExceptionNotFoundDTO` are shared by all routes and keep their names. A name you set yourself, such as `dto.response.name` for a GET_LIST item wrapper, is used as written.

### Startup Checks

Because the entity name is no longer part of generated names, the controller class name must be unique within an application. A decorated controller class without a name, for example `ApiController({ ... })(class {})`, fails when it is decorated. Declare a named class.

Everything else is checked once per application at bootstrap, over the controllers that this application contains. `@ApiController` attaches the check to the controller class, so it runs in every application that has a library controller, also when a test overrides `ApiAuthorizationGuard` or a controller is REQUEST-scoped. `app.init()` and `app.listen()` fail, naming what to fix, when:

- two different decorated controller classes have the same schema prefix, for example two classes named `UserController` in two modules mounted under `admin/` and `public/` with `RouterModule`, or `User` and `UserController`. The error names both controllers with their modules and paths. A subclass or mixin of a decorated controller has the prefix of the decorated class and is not a second owner.
- two different classes get the same OpenAPI component name. Every class that a route's schema reaches is checked at any depth, for generated routes, `@ApiRouteCustom` routes and the routes of plain `@Controller` classes alike, because Swagger puts all of them into one document: responses, body, query and parameters, generated DTOs, DTOs you configure with `dto`, and plain Swagger classes nested in them. Examples are a GET_LIST item wrapper name set with `dto.response.name` that matches another generated name, a hand-written `UserGetResponseDTO` used on another controller, on a custom route or in `@ApiOkResponse` of a plain controller, a dynamic object variant name that equals a relation name, or two table inheritance children that each nest a different class named `AddressDTO`. The error names the component and where each class comes from, such as `property address in AdminUserGetResponseHomeDTO` or `the 200 response of route getMe in controller PublicUserController`. Rename the hand-written class, or the controller class, property or variant that the generated name is built from.
- a custom route declared on a class without a name is served without `@ApiController`, for example by a plain `@Controller` class that inherits it from a mixin. Such a class has no schema prefix, so the route would have no generated DTOs and no request validation. Name the class, or inherit the route in a class decorated with `@ApiController`. A provider that inherits such a class serves no route and does not fail.
- a lazy type such as `type: () => AddressDTO` cannot be resolved. Lazy types are resolved at bootstrap, when every module has loaded. A lazy type that throws, as a class in its temporal dead zone does, or returns `undefined`, as an unfinished CommonJS circular import does, fails with the DTO and property, for example `Cannot resolve the lazy type of property address in UserGetResponseDTO`.

Only the classes of one application are compared, so a module that is evaluated again in one process, as with webpack HMR or `vi.resetModules`, needs no special case: the old classes are not in the new application. Two applications in one process are checked separately. One hand-written DTO class used by several routes is not a conflict.

Plain controllers have no schema prefix, so only their route schemas are checked. An application without any `@ApiController` class is not checked.

`@ApiController` attaches the check as an exception filter, `ApiControllerSchemaNameCheck`, with `@UseFilters` on the controller class. It catches no exception that a route can throw and does not change error responses, but `Reflect.getMetadata(EXCEPTION_FILTERS_METADATA, controller)` now lists it next to your own `@UseFilters` filters.

The check runs in `app.init()`, which `app.listen()` calls. A script that exports the document with `SwaggerModule.createDocument` without starting the application is not checked, so call `await app.init()` before `createDocument`.

A generated route on a subclass or mixin of a decorated controller, such as `class LoggedUserController extends UserController {}`, uses the DTOs of the decorated class at runtime, which are the ones the document shows.

### Two controllers on one entity

A typical case is an admin and a public controller with different guards on the same entity. A property exposed only to `AdminGuard` appears in the admin response and not in the public one:

```typescript
@ApiController<UserEntity>({ entity: UserEntity, path: "admin/users", routes: { [EApiRouteType.GET]: { security: { authentication: { guard: AdminGuard, type: EApiAuthenticationType.ADMIN } } } } })
export class AdminUserController {}

@ApiController<UserEntity>({ entity: UserEntity, path: "users", routes: { [EApiRouteType.GET]: { security: { authentication: { guard: UserGuard, type: EApiAuthenticationType.USER } } } } })
export class UserController {}
```

`GET /admin/users/{id}` is documented by `AdminUserGetResponseDTO` and `GET /users/{id}` by `UserGetResponseDTO`, and each schema matches what its route sends.

### Migration Notes

Before 5.0.0, generated body, response, GET_LIST items, relation, and nested object DTOs were named `<Entity><Route><DtoType>…DTO` without the controller. When two controllers on one entity generated different DTOs, for example because of different guards, both used the same component name and the OpenAPI document kept only one of them. The other route was documented with a schema it does not send. Responses on the wire were already correct. Typed GET_LIST query, GET identity, and read scope parameter DTOs were named `<Controller><Entity>…DTO`.

From 5.0.0, every generated name starts with the controller's schema prefix, and the entity name is removed:

- Component names change, and every `$ref` follows. The [name patterns](#old-and-new-name-patterns) below list each change, including the 4.x names that already contained the controller. Paths, operations, and schema contents of an application with one controller per entity stay the same. Regenerate API clients, and update code that refers to generated component names, such as hand-written `$ref` strings or type names from a generated client.
- Every controller gets the prefix, including the only controller of an entity. A prefix added only when a second controller appeared would rename an existing controller's schemas whenever someone added another controller.
- An application with several controllers on one entity gets one set of components per controller. Routes that were documented with another controller's schema now show their own.
- Generated DTOs of a custom route use the handler method name in place of the route type. A `@ApiRouteCustom` handler `getMe` of type GET on `PublicUserController` generates `PublicUserGetMeParametersDTO`, where 4.x generated `<Entity>GetParametersDTO`.
- Nested generated names follow one recursive rule, `<Parent><Property>DTO`, with the property in PascalCase as [defined above](#generated-schema-names): separators are removed and every other letter is kept as written. A relation property such as `createdBy`, `userID` or `created_by` gives `…CreatedByDTO`, `…UserIDDTO` or `…CreatedByDTO` where 4.x gave `…CreatedbyDTO`, `…UseridDTO` or `…Created_byDTO`. A relation or dynamic object copied with `@ApiPropertyCopy` is named after the DTO it is copied into and the host property it decorates, `<Host><Property>[<Variant>]DTO`, where 4.x used `<Entity><Route><DtoType><Property>[<Variant>]DTO` with the entity property.
- A custom route inherited from a base class or a mixin generates its DTOs with the prefix of each decorated controller that inherits it, not the name of the class that declares it.
- The GET_LIST wrappers are `<Prefix>GetListPageDTO` and `<Prefix>GetListCursorPageDTO`. The 4.x names ended like the relation DTO of a property `items` of the list item DTO, so an entity with an `items` relation would have had one component name for two schemas.
- The [startup checks](#startup-checks) above are new. An application that has two controller classes with the same prefix, an anonymous controller class, two different classes with one component name, including hand-written DTOs, or a lazy type that cannot be resolved now fails at bootstrap instead of producing a document with a missing schema.
- Low-level helpers take the prefix as a required `schemaPrefix` argument: `DtoGenerate` and `DtoGetGetListQueryBaseClass` after `dtoType`, `ApiControllerGetDto` after `routeConfig`, `ApiControllerApplyDecorators` after `decorators`, and `DtoGenerateTableInheritanceResponse` after `method`. `DtoGenerateTableInheritanceResponse` first shipped in 5.0.0-dev.2, so callers of that pre-release need the change too. `DtoGenerateGetListResponse` and `DtoGenerateGetListCursorResponse` take an optional trailing `origin` that the component name check reports. `DtoGenerate` also takes an optional trailing `routeName`. `ApiControllerGetSchemaPrefix(controllerClass)` returns the prefix Automator uses. Code that only uses `@ApiController` and `@ApiRouteCustom` needs no change.

#### Old and New Name Patterns

`<Prefix>` is the controller class name without a trailing `Controller`. `<Controller>` is the full class name, and `<Entity>` is the entity class name.

| Generated name                                     | 4.x                                                     | 5.0.0                                                                                                                                                 |
| -------------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Body, query, parameters, response                  | `<Entity><Route><DtoType>DTO`                           | `<Prefix><Route><DtoType>DTO`                                                                                                                         |
| GET_LIST page wrapper                              | `<Entity>GetListResponseItemsDTO`                       | `<Prefix>GetListPageDTO`                                                                                                                              |
| CURSOR wrapper                                     | `<Entity>GetListCursorResponseItemsDTO`                 | `<Prefix>GetListCursorPageDTO`                                                                                                                        |
| Relation in a response                             | `<Entity><Route>Response<Property>DTO`                  | `<Prefix><Route>Response<Property>DTO`                                                                                                                |
| Dynamic or nested object                           | `<Entity><Route><DtoType><Property><Variant>DTO`        | `<Prefix><Route><DtoType><Property><Variant>DTO`                                                                                                      |
| Relation inside a dynamic variant                  | `<Entity><Route><DtoType><Property>DTO`                 | `<Parent><Property>DTO`                                                                                                                               |
| Relation or variant copied with `@ApiPropertyCopy` | `<Entity><Route><DtoType><Property>[<Variant>]DTO`      | `<Host><Property>[<Variant>]DTO`, where `<Host>` is the hand-written DTO name without a trailing `DTO` in any case and `<Property>` the host property |
| Typed GET_LIST query                               | `<Controller><Entity>GetListQuery<signature>DTO`        | `<Prefix>GetListQuery<signature>DTO`                                                                                                                  |
| GET identity                                       | `<Controller><Entity>GetIdentity<signature>DTO`         | `<Prefix>GetIdentity<signature>DTO`                                                                                                                   |
| Read scope parameters                              | `<Controller><Entity>Get[List]Parameters<signature>DTO` | `<Prefix>Get[List]Parameters<signature>DTO`                                                                                                           |
| Custom route body, query, parameters               | `<Entity><Route><DtoType>DTO`                           | `<Prefix><Method><DtoType>DTO`                                                                                                                        |
| GET_LIST wrapper around a `{ itemType }` DTO       | `<Entity>GetListResponse<ItemType>`                     | `<Prefix>GetListResponse<ItemType>`                                                                                                                   |

`Exception*DTO` names and a name you set yourself do not change. In 5.0.0-dev.2 table inheritance variants were named `<Entity><Route>Response<Value>DTO`; they are now `<Prefix><Route>Response<Value>DTO`.

#### Renaming References

The package ships a dependency-free script that compares the OpenAPI document of your application before and after the upgrade and prints a JSON map of old component names to new ones. It pairs components by where operations use them, not by how they are named, so it also covers custom routes and any controller name:

```bash
node node_modules/@elsikora/nestjs-crud-automator/scripts/openapi-rename-map.mjs openapi-4.json openapi-5.json > rename-map.json
```

The map holds each old name with exactly one new name. Names that did not change are left out. Stderr has two more sections, and neither is in the map:

- **Ambiguous old names.** Two controllers on one entity shared one 4.x component, such as `BonusCampaignEntityGetResponseDTO`, so that old name has two new ones. The report lists each new name with a route that uses it. Pick the new name per call site. An old `oneOf` or `anyOf` member is here too when the script cannot pair it safely: members pair by `discriminator.mapping` key, and without a discriminator by position only when the two members have the same property names and no other member of either list has them. The reason says when a member only moved to another position, when another member has the same property names, and when the member at that position changed.
- **Old components that no operation pairs with a new component.** A removed route leaves its components here. So do query and parameters DTOs, because Swagger writes them inline in the operation and no `$ref` points to them. Use the [name patterns](#old-and-new-name-patterns) for those.

The script reads JSON only, follows `$ref`s to `components/parameters`, `requestBodies` and `responses`, and exits with code 1 and a message when an argument is missing or a document cannot be read or has an invalid shape. To apply the map to files, such as hand-written `$ref` strings, tests, or code that imports types from a generated client:

```bash
node -e 'const fs=require("fs");const map=JSON.parse(fs.readFileSync("rename-map.json","utf8"));const pattern=new RegExp(`\\b(?:${Object.keys(map).join("|")})\\b`,"g");if(Object.keys(map).length)for(const file of process.argv.slice(1))fs.writeFileSync(file,fs.readFileSync(file,"utf8").replace(pattern,(name)=>map[name]));' src/client.ts test/api.test.ts
```

## Controlling DTO Generation

### Exclude from DTOs

Prevent a property from appearing in specific DTOs:

```typescript
@Column()
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.STRING,
  description: "Internal notes",
  format: EApiPropertyStringType.STRING,
  minLength: 0,
  maxLength: 500,
  pattern: "/^[\\s\\S]{0,500}$/",
  exampleValue: "Visible to staff only",
  properties: {
    [EApiRouteType.CREATE]: {
      [EApiDtoType.BODY]: { isEnabled: false },
    },
    [EApiRouteType.UPDATE]: {
      [EApiDtoType.BODY]: { isEnabled: false },
      [EApiDtoType.RESPONSE]: { isExpose: true, isResponse: true },
    },
  },
})
internalNotes: string;
```

### Required vs Optional

Control field requirements:

```typescript
@Column()
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.STRING,
  description: "Email",
  format: EApiPropertyStringType.EMAIL,
  minLength: 5,
  maxLength: 255,
  pattern: "/^[\\w.-]+@([\\w-]+\\.)+[\\w-]{2,}$/",
  exampleValue: "user@example.com",
  properties: {
    [EApiRouteType.CREATE]: {
      [EApiDtoType.BODY]: { isRequired: true },
    },
    [EApiRouteType.PARTIAL_UPDATE]: {
      [EApiDtoType.BODY]: { isRequired: false },
    },
  },
})
email: string;
```

### Default Values

Specify default values for DTO properties:

```typescript
@Column({ default: false })
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.BOOLEAN,
  description: "Is active",
})
isActive: boolean;
```

## Custom DTOs

Replace auto-generated DTOs with custom ones:

```typescript filename="dto/create-user.dto.ts" copy
import { IsString, IsEmail, MinLength, MaxLength } from "class-validator";
import { ApiProperty } from "@nestjs/swagger";

export class CreateUserDto {
	@ApiProperty()
	@IsString()
	@MinLength(3)
	@MaxLength(20)
	username: string;

	@ApiProperty()
	@IsEmail()
	email: string;

	@ApiProperty()
	@IsString()
	@MinLength(8)
	password: string;
}
```

Use in controller:

```typescript
@ApiController<UserEntity>({
  entity: UserEntity,
  routes: {
    [EApiRouteType.CREATE]: {
      dto: {
        [EApiDtoType.BODY]: CreateUserDto,
        [EApiDtoType.RESPONSE]: UserResponseDto,
      },
    },
  },
})
```

Manual DTOs can also be nested inside auto-generated DTOs through `@ApiPropertyObject`. When this happens, NestJS CRUD Automator creates context-specific wrapper schemas for each generated path, so the same manual DTO can be reused safely in create body DTOs, update body DTOs, and response DTOs without sharing conflicting Swagger or serialization metadata.

For GET_LIST, a manual `dto[EApiDtoType.QUERY]` and generated `request[QUERY].filter`, `order`, or `pagination` configuration are mutually exclusive. For generated GET/GET_LIST read scope, a manual `dto[EApiDtoType.PARAMETERS]` and `read.scope.parameters` are likewise mutually exclusive. Manual response DTOs remain compatible with both generated plans.

### Custom GET_LIST item DTOs

`GET_LIST` response DTOs support two explicit modes:

- Full wrapper mode: `dto[EApiDtoType.RESPONSE]` is a class that describes the whole list response.
- Item DTO mode: `dto[EApiDtoType.RESPONSE]` is `{ itemType }`, and the framework generates the PAGE count wrapper or CURSOR flat wrapper selected by the route plan.

Use item DTO mode when a route only needs custom serialization for each item:

```typescript
class PublicUserResponseDto {
	@Expose()
	id!: string;

	@Expose()
	username!: string;
}

@ApiController<UserEntity>({
	entity: UserEntity,
	routes: {
		[EApiRouteType.GET_LIST]: {
			dto: {
				[EApiDtoType.RESPONSE]: {
					itemType: PublicUserResponseDto,
					name: "PublicUserListResponseDto",
				},
			},
		},
	},
})
export class UserController {}
```

The wrapper follows the route pagination plan. PAGE uses `count`, `currentPage`, `items`, `totalCount`, and `totalPages`; CURSOR uses exactly `items`, `nextCursor`, and `previousCursor`.

The example above is PAGE because it omits pagination configuration. In CURSOR mode, a custom item DTO must use compatible Automator response metadata to prove every protected order/primary field under the same name; a custom full wrapper must additionally prove the exact three-field flat envelope. A class-transformer-only item such as the abbreviated PAGE example is not sufficient proof for CURSOR.

## DTO Validation

### Built-in Validators

Validation rules are automatically applied based on property configuration:

```typescript
@Column()
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.STRING,
  description: "Username",
  format: EApiPropertyStringType.STRING,
  minLength: 3, // Adds @MinLength(3)
  maxLength: 20, // Adds @MaxLength(20)
  pattern: "/^[a-zA-Z0-9_-]+$/", // Adds @Matches(/^[a-zA-Z0-9_-]+$/)
})
username: string;
```

### Custom Validators

Add custom validators to auto-generated DTOs:

```typescript
import {
  AllOrNoneOfListedPropertiesValidator
} from "@elsikora/nestjs-crud-automator";

@ApiController<UserEntity>({
  entity: UserEntity,
  routes: {
    [EApiRouteType.CREATE]: {
      autoDto: {
        [EApiDtoType.BODY]: {
          validators: [
            {
              constraintClass: AllOrNoneOfListedPropertiesValidator,
              options: ["firstName", "lastName"],
            },
          ],
        },
      },
    },
  },
})
```

Available built-in validators:

- `AllOrNoneOfListedPropertiesValidator` - All or none must be provided
- `OnlyOneOfListedPropertiesValidator` - Exactly one must be provided
- `HasAtLeastOneOfListedPropertiesValidator` - At least one required
- `HasAtLeastOneAndOnlyOneOfListedPropertiesValidator` - Only one required
- `MustMatchOneOfSchemasValidator` - Must match a schema
- `HasPairedCustomSuffixesFieldsValidator` - Paired fields validation

## Polymorphic DTOs

Support for discriminated unions:

```typescript
// Base interface
interface Payment {
  type: string;
}

// Specific implementations
interface CardPayment extends Payment {
  type: "card";
  cardNumber: string;
  cvv: string;
}

interface PayPalPayment extends Payment {
  type: "paypal";
  email: string;
}

@Column({ type: "jsonb" })
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.OBJECT,
  description: "Payment method",
  discriminator: {
    propertyName: "type",
    mapping: {
      card: CardPaymentDto,
      paypal: PayPalPaymentDto,
    },
  },
  dataType: [CardPaymentDto, PayPalPaymentDto],
  shouldValidateNested: true,
})
paymentMethod: CardPayment | PayPalPayment;
```

## DTO Transformation

Transform DTO values during processing:

```typescript
import { Transform } from "class-transformer";

@Column()
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.STRING,
  description: "Email",
  format: EApiPropertyStringType.EMAIL,
  minLength: 5,
  maxLength: 255,
  pattern: "/^[\\w.-]+@([\\w-]+\\.)+[\\w-]{2,}$/",
  exampleValue: "user@example.com",
})
@Transform(({ value }) => value.toLowerCase())
email: string;
```

## Guard-Based DTO Properties

Generate separate DTO property variants for a guard class:

```typescript
@Column()
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.STRING,
  description: "Admin notes",
  format: EApiPropertyStringType.STRING,
  minLength: 0,
  maxLength: 500,
  pattern: "/^[\\s\\S]{0,500}$/",
  exampleValue: "Admin-only note",
  properties: {
    [EApiRouteType.GET]: {
      [EApiDtoType.RESPONSE]: {
        isExpose: true,
        isResponse: true,
        guard: { guards: [AdminGuard] },
      },
    },
  },
})
adminNotes: string;
```

This metadata tags the generated response DTO variant for routes protected by `AdminGuard`. It is not a per-request authorization check; use authentication guards or authorization policies to decide whether a request may use that route.

## Relation DTOs

Control how relations appear in DTOs:

```typescript
@ManyToOne(() => UserEntity)
@ApiPropertyDescribe({
  type: EApiPropertyDescribeType.RELATION,
  description: "Post author",
  properties: {
    [EApiRouteType.GET]: {
      [EApiDtoType.RESPONSE]: { isExpose: true, isResponse: true },
    },
  },
})
author: UserEntity;
```

Load relation data from the route config with `relations.response.load.include`, not from the property metadata.

@Column({ type: "jsonb" })
@ApiPropertyDescribe({

  description: "User profile",
  dataType: UserProfileDto,
  shouldValidateNested: true,
