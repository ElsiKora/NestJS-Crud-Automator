# Services

Services in NestJS CRUD Automator handle the business logic and database operations. The `@ApiService` decorator automatically adds CRUD methods to your service class, which must extend `ApiServiceBase`.

## Basic Service Setup

A minimal service requires the `@ApiService` decorator, extension of `ApiServiceBase`, and a TypeORM repository:

```typescript filename="user.service.ts" copy
import { Injectable } from "@nestjs/common";
import { InjectRepository } from "@nestjs/typeorm";
import { Repository } from "typeorm";
import { ApiService, ApiServiceBase } from "@elsikora/nestjs-crud-automator";
import { UserEntity } from "./user.entity";

@Injectable()
@ApiService<UserEntity>({
	entity: UserEntity,
})
export class UserService extends ApiServiceBase<UserEntity> {
	constructor(
		@InjectRepository(UserEntity)
		public repository: Repository<UserEntity>,
	) {
		super();
	}
}
```

Each singleton `@ApiController` checks at application bootstrap that its `service.repository` is a TypeORM repository and fails with an error that names the controller, the entity, and the missing part otherwise. The check reads TypeORM's own type markers instead of `instanceof`, so a repository built by a second installed copy of TypeORM, as a pnpm workspace or monorepo can resolve, still counts, as does a Proxy-wrapped repository. Nest runs no bootstrap hook on a request-scoped controller, whose GET_LIST route makes the check when a request arrives. For tests, see [Testing](/docs/nestjs-crud-automator/guides/testing).

## Auto-Generated CRUD Methods

The `@ApiService` decorator automatically adds the following methods to your service:

### `create(properties): Promise<E>`

Creates a new entity:

```typescript
const user = await userService.create({
	username: "john_doe",
	email: "john@example.com",
});
```

### `get(properties): Promise<E>`

Retrieves a single entity by criteria:

```typescript
const user = await userService.get({
	where: { id: "uuid-here" },
});
```

### `getList(properties): Promise<IApiGetListResponseResult<E>>`

Retrieves a paginated list with filtering and sorting:

```typescript
const result = await userService.getList({
	where: {
		username: ILike("%john%"),
	},
	order: {
		createdAt: "DESC",
	},
	take: 10,
	skip: 0,
});

// Result contains:
// {
//   items: UserEntity[],
//   count: number,
//   currentPage: number,
//   totalCount: number,
//   totalPages: number
// }
```

### `getMany(properties): Promise<E[]>`

Retrieves multiple entities:

- Returns `[]` when no records match the criteria.
- Generated CURSOR GET_LIST routes use this existing decorated method for their `limit + 1` window and opposite-direction `take: 1` probe; PAGE routes continue to use `getList`.

```typescript
const users = await userService.getMany({
	where: {
		isActive: true,
	},
});
```

### `update(criteria, properties): Promise<E>`

Updates an existing entity:

```typescript
const updatedUser = await userService.update(
	{ id: "uuid-here" },
	{
		username: "new_username",
	},
);
```

### `delete(criteria): Promise<void>`

Deletes an entity:

```typescript
await userService.delete({
	id: "uuid-here",
});
```

### Query Criteria

Generated methods refuse a `where` that TypeORM would widen. A condition set to `undefined` or `null`, an empty relation object such as `{ owner: {} }`, an empty OR array and an empty OR branch fail before the query runs. Match SQL `NULL` with `IsNull()` and drop a condition you do not need instead of setting it to `undefined`.

`get`, `update` and `delete` target one row, so they also refuse a missing or empty `where`. Without this check TypeORM returns or changes the first row it finds. `getList` and `getMany` still accept a missing `where` and read every row.

The refusal surfaces as `InternalServerErrorException`, because it is a programming error in the calling code, not bad client input.

## Custom Methods

Use names other than `create`, `get`, `getList`, `getMany`, `update`, and `delete` for ordinary domain methods. A [generated `CREATE`](/docs/nestjs-crud-automator/guides/authorization#scoped-create) treats `create` like the others, and its controller fails at startup when `create` or `get` is not protected. Starting with the 4.0 capability boundary, generated controller routes invoke those reserved operations only when the exact function was produced for the same entity and function type by `@ApiService` or the matching built-in `@ApiFunction*` decorator. Undecorated overrides can still be called directly, but generated routes reject them before the Automator-managed route transaction or repository I/O. Prefer subscribers for generated CRUD lifecycle changes and `@ApiFunctionCustom` or a custom route for a distinct operation. See [Migrating to 4.0](/docs/nestjs-crud-automator/guides/migrating-to-4-0).

Add custom business logic beyond CRUD operations:

```typescript filename="user.service.ts" copy
@Injectable()
@ApiService<UserEntity>({
	entity: UserEntity,
})
export class UserService extends ApiServiceBase<UserEntity> {
	constructor(
		@InjectRepository(UserEntity)
		public repository: Repository<UserEntity>,
	) {
		super();
	}

	// Custom method
	async findByEmail(email: string): Promise<UserEntity | null> {
		return this.repository.findOne({ where: { email } });
	}

	// Custom method with complex logic
	async activateUser(id: string): Promise<UserEntity> {
		const user = await this.get({ where: { id } });
		return this.update(
			{ id },
			{
				isActive: true,
				activatedAt: new Date(),
			},
		);
	}

	// Custom bulk operation
	async bulkUpdateStatus(userIds: string[], isActive: boolean): Promise<void> {
		await this.repository.update({ id: In(userIds) }, { isActive });
	}
}
```

## Transaction Support

Do not pass `EntityManager` as a public service method argument. Use function `transaction.mode` and nested decorated calls so the framework propagates the active transaction through `ApiFunctionContextStorage`.

Generated CRUD functions can be configured directly on `@ApiService`:

```typescript filename="post.service.ts" copy
import { ApiService, ApiServiceBase, EApiFunctionTransactionMode, EApiFunctionType } from "@elsikora/nestjs-crud-automator";

@Injectable()
@ApiService<PostEntity>({
	entity: PostEntity,
	functions: {
		[EApiFunctionType.CREATE]: {
			transaction: { mode: EApiFunctionTransactionMode.REQUIRED },
		},
	},
})
export class PostService extends ApiServiceBase<PostEntity> {
	constructor(
		@InjectRepository(PostEntity)
		public repository: Repository<PostEntity>,
	) {
		super();
	}
}
```

The `functions` map accepts generated function types (`CREATE`, `UPDATE`, `DELETE`, `GET`, `GET_LIST`, `GET_MANY`). Omitted entries keep the default `SUPPORTS` mode, and `CUSTOM` is configured with `@ApiFunctionCustom` instead.

Custom commands can use `@ApiFunctionCustom` when the operation needs domain-specific method bodies:

```typescript filename="post.service.ts" copy
import { ApiFunctionCustom, EApiFunctionTransactionMode } from "@elsikora/nestjs-crud-automator";

@Injectable()
export class PostService extends ApiServiceBase<PostEntity> {
	constructor(
		@InjectRepository(PostEntity)
		public repository: Repository<PostEntity>,
		private dataSource: DataSource,
	) {
		super();
	}

	@ApiFunctionCustom<PostEntity>({
		action: "createWithComments",
		entity: PostEntity,
		transaction: { mode: EApiFunctionTransactionMode.REQUIRED },
	})
	async createPostWithComments(postData: DeepPartial<PostEntity>, commentsData: DeepPartial<CommentEntity>[]): Promise<PostEntity> {
		const context = this.getApiFunctionContext<PostEntity>();
		const post = await context.operations.create(postData);

		for (const commentData of commentsData) {
			await context.getRepository(CommentEntity).save({
				...commentData,
				postId: post.id,
			});
		}

		return post;
	}
}
```

Use `@ApiFunctionStep` for internal helper methods inside custom commands, generated or decorated service flows, or direct helper calls when the selected transaction mode permits. A step is useful when the helper needs ApiFunction transaction semantics and context but should not become a standalone custom action:

```typescript filename="withdrawal.service.ts" copy
import { ApiFunctionCustom, ApiFunctionStep, EApiFunctionTransactionMode } from "@elsikora/nestjs-crud-automator";

@Injectable()
export class WithdrawalService extends ApiServiceBase<WithdrawalEntity> {
	@ApiFunctionCustom<WithdrawalEntity>({
		action: "approve",
		entity: WithdrawalEntity,
		transaction: { mode: EApiFunctionTransactionMode.REQUIRED },
	})
	async approve(properties: IWithdrawalApproveProperties): Promise<WithdrawalEntity> {
		return await this.releaseReservedWithdrawalAmount(properties);
	}

	@ApiFunctionStep<WithdrawalEntity>({
		entity: WithdrawalEntity,
		transaction: { mode: EApiFunctionTransactionMode.MANDATORY },
	})
	private async releaseReservedWithdrawalAmount(properties: IWithdrawalApproveProperties): Promise<WithdrawalEntity> {
		const context = this.getApiFunctionStepContext<WithdrawalEntity>();

		return await context.repository.save({
			...properties.withdrawal,
			state: "released",
		});
	}
}
```

`@ApiFunctionStep` keeps normal method calls and does not require a context argument. It only provides transaction/context handling; it does not register a custom action, dispatch function subscribers, create route metadata, or expose Swagger/authorization metadata. Step context intentionally exposes only `eventManager`, `repository`, and `getRepository`; use `@ApiFunctionCustom` plus `getApiFunctionContext()` when you need `operations`.

### Transaction-Bound Values

A value that belongs to one command, such as its authority scope, can be bound to the Automator transaction the command runs in, so domain services read it without an `EntityManager` argument:

```typescript filename="authority.ts" copy
import { ApiFunctionTransactionScope } from "@elsikora/nestjs-crud-automator";

export const AUTHORITY: unique symbol = Symbol("authority");

await ApiFunctionTransactionScope.runWithDataSource(dataSource, { name: "settle-round" }, async () => {
	ApiFunctionTransactionScope.setValue<IAuthority>(AUTHORITY, authority);
	await roundService.settle(round);
});

// Inside roundService.settle, a REQUIRED or MANDATORY function or step it calls, or a function subscriber of its writes:
const authority: IAuthority | undefined = ApiFunctionTransactionScope.getValue<IAuthority>(AUTHORITY);
```

- `setValue(key, value)` binds the value to the current Automator transaction and throws when none is active. Keys are symbols.
- `getValue(key)` returns it to everything that runs in that same transaction: the owner, every `REQUIRED` or `MANDATORY` function and step that joined it (with `context.eventManager`, the service repository bound to it, and its function subscribers), and a `runWithDataSource` on the same `DataSource`, which joins it. It returns `undefined` outside any transaction, in a different transaction, and after the transaction committed or rolled back.
- `runWithValue(key, value, callback)` binds the value for the callback and puts back the previous value, or its absence, when the callback settles, also when it throws. The value belongs to the transaction, not to the callback's async context, so other work running in parallel in the same transaction sees it too.

The current transaction is the one the async context of the call runs in, the same one `runWithDataSource` joins. A transaction that a call opens on another `DataSource` inside it is a different transaction with values of its own, and a call back into the first `DataSource` joins the first transaction and sees its values again; a call on another `DataSource` that opens no transaction sees no value and cannot bind one. Values are released when the transaction ends, before `onAfterCommit` and `onAfterRollback` run, and are never shared between transactions: two transactions running in parallel each see only their own value under the same key. Route subscribers of a generated route run outside the transaction the route owns, so they see no value bound inside it.

## Observable Services

Enable function-level subscribers by marking the service as observable:

```typescript filename="post.service.ts" copy
import { ApiService, ApiServiceBase, ApiServiceObservable } from "@elsikora/nestjs-crud-automator";

@Injectable()
@ApiService<PostEntity>({
	entity: PostEntity,
})
@ApiServiceObservable()
export class PostService extends ApiServiceBase<PostEntity> {
	constructor(
		@InjectRepository(PostEntity)
		public repository: Repository<PostEntity>,
	) {
		super();
	}
}
```

This allows function-level subscribers to intercept service operations at the repository level.

## Service Dependencies

Inject other services for complex operations:

```typescript filename="order.service.ts" copy
@Injectable()
@ApiService<OrderEntity>({
	entity: OrderEntity,
})
export class OrderService extends ApiServiceBase<OrderEntity> {
	constructor(
		@InjectRepository(OrderEntity)
		public repository: Repository<OrderEntity>,
		private readonly productService: ProductService,
		private readonly userService: UserService,
		private readonly paymentService: PaymentService,
	) {
		super();
	}

	async createOrder(userId: string, productIds: string[]): Promise<OrderEntity> {
		// Validate user
		const user = await this.userService.get({ where: { id: userId } });

		// Validate products
		const products = await this.productService.getMany({
			where: { id: In(productIds) },
		});

		// Calculate total
		const total = products.reduce((sum, p) => sum + p.price, 0);

		// Create order
		return this.create({
			userId,
			total,
			status: OrderStatus.PENDING,
		});
	}
}
```

## Repository Access

Access the underlying TypeORM repository for advanced queries:

```typescript
@Injectable()
@ApiService<UserEntity>({
	entity: UserEntity,
})
export class UserService extends ApiServiceBase<UserEntity> {
	constructor(
		@InjectRepository(UserEntity)
		public repository: Repository<UserEntity>,
	) {
		super();
	}

	async getUsersWithPostCount(): Promise<Array<{ user: UserEntity; postCount: number }>> {
		return this.repository
			.createQueryBuilder("user")
			.leftJoin("user.posts", "post")
			.select("user")
			.addSelect("COUNT(post.id)", "postCount")
			.groupBy("user.id")
			.getRawAndEntities()
			.then((result) =>
				result.entities.map((user, index) => ({
					user,
					postCount: parseInt(result.raw[index].postCount || "0", 10),
				})),
			);
	}
}
```

## Error Handling

Throw meaningful errors from service methods:

```typescript
import { NotFoundException, BadRequestException } from "@nestjs/common";

async activateUser(id: string): Promise<UserEntity> {
  const user = await this.repository.findOne({ where: { id } });

  if (!user) {
    throw new NotFoundException(`User with ID ${id} not found`);
  }

  if (user.isActive) {
    throw new BadRequestException("User is already active");
  }

  return this.update(
    { id },
    {
      isActive: true,
      activatedAt: new Date(),
    }
  );
}
```

## Migration Notes

Before 5.0.0, a generated method passed its `where` to TypeORM unchecked. TypeORM 0.3 dropped `undefined` conditions and empty relation objects, so `get({ where: { id: undefined } })` returned the first row and `update({ id: undefined }, patch)` changed it. From 5.0.0 these calls fail with `InternalServerErrorException`, and so does any `where` with a `null` value, an empty relation object, an empty OR array or an empty OR branch.

Check the places where your code builds a `where` from optional values:

1. Remove a condition instead of setting it to `undefined`.
2. Replace `null` with `IsNull()`.
3. Stop passing `{}` or `[]` to `get`, `update` or `delete`.

See [Query Criteria](#query-criteria) for the full rules.
