# `@ApiRouteCustom`

`@ApiRouteCustom` is the high-level custom route decorator. It keeps the same strict route metadata contract as `@ApiMethod`, then adds runtime configuration for request/response transformers, DTOs, relation handling, custom route subscribers, authorization result transforms, and response serialization.

Use it when a controller method is not standard CRUD but should still behave like generated CRUD routes at the framework boundary.

## Signature

```typescript
@ApiRouteCustom<E extends IApiBaseEntity>(
	properties: IApiRouteCustomProperties<E>
): MethodDecorator
```

## Contract split

`@ApiRouteCustom` separates route metadata from runtime properties:

- Metadata fields (`resource`, `route`, `documentation`, `security`, `throttling`, and response `status`, `type`, `headers`, `errors`, `serialization`) are stored as `IApiRouteMetadata`.
- Runtime fields (`request`, target-first response transformers, `relations`, `dto`, and `autoDto`) are stored as `IApiRouteRuntimeProperties`.
- `execution.guards` and `execution.interceptors` are applied by the same `@ApiMethod` composition path used by generated routes. Custom interceptors run before the internal route-runtime interceptor.
- Response target keys such as `[EApiControllerResponseTarget.RESPONSE]` belong only to runtime properties, not method metadata.

`documentation.request` accepts required OpenAPI headers and request media types. `documentation.response` accepts response media types and additional responses with an explicit `status`. A configured ordinary body DTO always emits `ApiBody`, including handlers that read the physical request through `@Req()` rather than declaring `@Body()`. `@ApiRouteCustom` also preserves existing own method metadata when it wraps the handler, so Nest and third-party decorators do not depend on decorator ordering.

## Runtime behavior

Custom routes can use the same target-first request and response configuration as generated routes:

```typescript
@ApiRouteCustom<PostEntity>({
	resource: {
		action: "publish",
		entity: PostEntity,
	},
	route: {
		method: RequestMethod.POST,
		path: ":id/publish",
	},
	security: {
		authentication: {
			type: EApiAuthenticationType.USER,
			guard: JwtAuthGuard,
			securityRequirements: [
				{
					bearerStrategies: ["jwt"],
				},
			],
		},
		authorization: {
			mode: EApiAuthorizationMode.HOOKS,
		},
	},
	request: {
		[EApiControllerRequestTarget.BODY]: {
			transformers: [
				{
					key: "publisher",
					type: EApiControllerRequestTransformerType.DYNAMIC,
					value: TRANSFORMER_VALUE_DTO_CONSTANT.AUTHORIZED_ENTITY,
					shouldSetValueEvenIfMissing: true,
				},
			],
		},
	},
	response: {
		headers: {
			"X-Request-Id": {
				description: "Request correlation id.",
				schema: { type: "string" },
			},
		},
		status: HttpStatus.OK,
		type: PublishPostResponseDto,
		serialization: { isEnabled: true },
		[EApiControllerResponseTarget.RESPONSE]: {
			transformers: [
				{
					key: "requestSignature",
					type: EApiControllerRequestTransformerType.DYNAMIC,
					value: TRANSFORMER_VALUE_DTO_CONSTANT.REQUEST_SIGNATURE,
					shouldSetValueEvenIfMissing: true,
				},
			],
		},
	},
})
async publish(@Param("id") id: string, @Body() body: Partial<PostEntity>): Promise<PostEntity> {
	return await this.service.publish(id, body);
}
```

## Root-level discriminated DTOs

Use root-level discriminators when the whole custom route request body or response is polymorphic. Use `@ApiPropertyObject` when only a nested property inside a DTO is polymorphic.

```typescript
@ApiRouteCustom<UserEntity>({
	resource: { action: "registration.create", entity: UserEntity },
	route: { method: RequestMethod.POST, path: "registrations" },
	dto: {
		body: {
			type: [EmailRegistrationBodyDto, UsernameRegistrationBodyDto],
			validatorOptions: {
				skipMissingProperties: true,
			},
			discriminator: {
				propertyName: "channel",
				shouldKeepDiscriminatorProperty: true,
				mapping: {
					email: EmailRegistrationBodyDto,
					username: UsernameRegistrationBodyDto,
				},
			},
		},
	},
	response: {
		status: HttpStatus.CREATED,
		type: [VerificationResponseDto, SessionResponseDto],
		discriminator: {
			propertyName: "mode",
			shouldKeepDiscriminatorProperty: true,
			mapping: {
				verification: VerificationResponseDto,
				session: SessionResponseDto,
			},
		},
		serialization: { isEnabled: true },
	},
})
async register(@Body() body: EmailRegistrationBodyDto | UsernameRegistrationBodyDto): Promise<VerificationResponseDto | SessionResponseDto> {
	return await this.service.register(body);
}
```

For request bodies, Crud Automator selects the variant DTO from `discriminator.mapping`, transforms the plain body into that DTO class, runs `class-validator` on the selected variant, and passes the transformed instance to the controller method. Missing or unknown discriminator values fail request validation. Declare the discriminator property on every variant DTO with the usual property decorators, such as `ApiPropertyEnum`; make it optional on the DTO when `shouldKeepDiscriminatorProperty: false` should remove it from the transformed instance.

Root-level discriminator selection happens before Nest can validate a concrete DTO class, so global `ValidationPipe` options are not applied automatically to the selected variant. Use `validatorOptions` and `transformOptions` on the discriminated body config when the route must mirror specific validation or transformation settings.

For responses, Swagger emits `oneOf` with an OpenAPI discriminator. When serialization is enabled, Crud Automator selects the response DTO from the returned value's discriminator, then applies the same `excludeExtraneousValues` response serialization used by single DTO responses. Returning a value without a valid discriminator is treated as a route contract error.

Single DTO configs remain unchanged: `dto.body: SomeDto`, `response.type: SomeDto`, and `response.type: undefined` keep their existing behavior. Generated CRUD routes are not changed by root-level custom route discriminators.

## Relations

Custom route relations live under `relations.request` and `relations.response`, just like generated route config:

```typescript
@ApiRouteCustom<PostEntity>({
	resource: { action: "assignAuthor", entity: PostEntity },
	route: { method: RequestMethod.POST, path: ":id/author" },
	relations: {
		request: {
			load: { include: { author: true } },
			reference: {
				key: "id",
				shape: EApiControllerRelationReferenceShape.OBJECT,
			},
		},
		response: {
			load: { include: { author: true } },
			reference: {
				key: "id",
				shape: EApiControllerRelationReferenceShape.SCALAR,
			},
		},
	},
	response: {
		status: HttpStatus.OK,
		type: PostEntity,
	},
})
async assignAuthor(@Body() body: Partial<PostEntity>): Promise<PostEntity> {
	// body.author is hydrated before the handler when request relation loading is enabled.
	return await this.service.assignAuthor(body);
}
```

For response relation loading, the route response must identify the entity so the runtime can reload configured relations before projecting them to the configured reference shape. The controller must expose `service` extending `ApiServiceBase`; response items without an `id` are returned unchanged.

Custom route request relation hydration reads only the method body payload. `relations.request.load.include` selects direct body relations, nested include objects are passed to the direct relation service as TypeORM `relations`, and nested request references are not recursively hydrated. Omitted service mappings infer `${relationName}Service`; `relations.request.load.services` only overrides those controller property names. `relationLoadStrategy` is available on both request and response `load` configs.

## Subscribers

`@ApiRouteCustom` emits custom route subscriber hooks with the configured `resource.action`. The controller must still be marked with `@ApiControllerObservable()` for route subscribers to run:

```typescript
@ApiRouteSubscriber({
	entity: PostEntity,
	actions: ["publish"],
})
export class PublishRouteSubscriber extends ApiRouteSubscriberBase<PostEntity> {
	async onBeforeCustom(context: IApiSubscriberRouteExecutionContext<PostEntity>): Promise<unknown> {
		return context.result;
	}
}
```

Use custom actions for non-CRUD policy rules and route subscriber filters. Generated CRUD hooks remain tied to their `EApiRouteType`. Custom route before hooks receive `{ body?, parameters?, query? }` in `context.result`; read headers, IP, authentication request, route metadata, and runtime properties from `context.DATA`.
