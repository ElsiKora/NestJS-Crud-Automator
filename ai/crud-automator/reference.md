# Crud Automator Reference

## Native Primitive Map

| Need                                            | Use first                                               |
| ----------------------------------------------- | ------------------------------------------------------- |
| Standard CRUD                                   | `@ApiService()` + `ApiServiceBase` + `@ApiController()` |
| Custom service command                          | `@ApiFunctionCustom()`                                  |
| Internal transaction-aware service step         | `@ApiFunctionStep()`                                    |
| Custom controller command with runtime pipeline | `@ApiRouteCustom()`                                     |
| Low-level custom method metadata                | `@ApiMethod({ metadata })`                              |
| Generated DTO field controls                    | `ApiPropertyDescribe({ properties })`                   |
| Property-wide generated DTO opt-out             | `ApiPropertyDescribe({ isAutoDtoEnabled: false })`      |
| Route-local generated DTO validators            | `autoDto`                                               |
| Manual route DTOs                               | `dto: { [EApiDtoType.*]: DTO }`                         |
| GET_LIST custom item shape                      | `dto: { [EApiDtoType.RESPONSE]: { itemType, name? } }`  |
| Typed GET_LIST filter/order overlay             | `request[EApiControllerRequestTarget.QUERY]`            |
| Generated GET_LIST pagination mode              | `request[QUERY].pagination.mode`                        |
| External GET primary path name                  | `routes[GET].identity`                                  |
| Inherited owner path scope for GET/GET_LIST     | `read.scope.parameters`                                 |
| Stable server list order                        | `order.defaultOrder` + `order.tieBreakers`              |
| Relation hydration                              | `relations.request`                                     |
| Generated route transaction                     | `routes[route].transaction`                             |
| Direct request relation lock                    | `relations.request.load.locks`                          |
| Relation response loading                       | `relations.response.load.include`                       |
| HTTP-aware lifecycle logic                      | `ApiRouteSubscriberBase`                                |
| Persistence-aware lifecycle logic               | `ApiFunctionSubscriberBase`                             |
| Code-first auth rules                           | `ApiAuthorizationPolicyBase` in HOOKS mode              |
| Policy-document auth                            | IAM mode with sources/resolvers                         |
| External transaction scope                      | `ApiFunctionTransactionScope`                           |

Generated controller routes accept GET, GET_LIST, GET_MANY, UPDATE, and DELETE only from the exact same-entity matching built-in capability installed by `@ApiService` or `@ApiFunction*`. Generated CREATE also requires its `create` and its protected post-create GET, a controller fails at startup when either one is not protected, and UPDATE preflights a protected reload GET when configured. An undecorated same-named override remains directly callable but is not a generated-route implementation. Use subscribers or custom functions/routes for domain-specific behavior; see the 4.0 migration guide.

A singleton `@ApiController` with an enabled generated route fails at application bootstrap unless `service.repository` is a TypeORM repository, also when the decorator's return value is discarded: `Controller "<Name>" of entity "<Entity>": service.repository is not a usable TypeORM repository because <missing part>` (`the controller has no service`, `the service has no repository`, `it is a <type>, not an object`, `its metadata is not TypeORM entity metadata`, `its manager is not a TypeORM entity manager bound to a data source`, or `reading it failed, usually because its data source is not initialized yet (<cause>)`). A controller whose generated routes are all disabled is not refused. Nest runs no bootstrap hook on a request-scoped controller, so its GET_LIST route makes the repository and CURSOR database checks on the request and its other routes are unchecked. The check reads TypeORM's type markers through the properties instead of `instanceof` or `in`, so a repository from a second installed TypeORM copy and a Proxy-wrapped repository count. Testing recipe: a real repository of an in-memory `better-sqlite3` DataSource, provided under `getRepositoryToken(E)`, with single methods stubbed by `vi.spyOn`, plus `ApiAuthorizationModule.forRoot()`; a plain-object repository mock or a mocked service with no repository fails at bootstrap. A repository of a PostgreSQL DataSource whose subclass calls the protected `buildMetadatas()`, with no connection, or an object with its `metadata` and `manager`, passes every bootstrap check, the CURSOR check included. A column type SQLite rejects, such as `timestamp`, fails `initialize()` with `DataTypeNotSupportedError`; a CURSOR controller needs a real PostgreSQL DataSource with `vi.spyOn(repository, "find")`.

## Route Config Shape

Generated route config is nested by responsibility:

```ts
routes: {
	[EApiRouteType.CREATE]: {
			transaction: {
				mode: EApiFunctionTransactionMode.REQUIRED,
			},
		generation: {
			isEnabled: true,
			shouldWriteToController: true,
			decorators: [],
		},
		security: {
			authentication: {
				type: EApiAuthenticationType.USER,
				guard: JwtAuthGuard,
				securityRequirements: [
					{
						bearerStrategies: ["jwt"],
					},
				],
			},
			authorization: {
				mode: EApiAuthorizationMode.HOOKS,
			},
		},
		request: {
			[EApiControllerRequestTarget.BODY]: {
				transformers: [],
				validators: [],
			},
		},
		response: {
			headers: {
				"X-Request-Id": {
					description: "Request correlation id.",
					schema: { type: "string" },
				},
			},
			[EApiControllerResponseTarget.RESPONSE]: {
				transformers: [],
			},
		},
		relations: {
			request: {
				reference: { shape: EApiControllerRelationReferenceShape.SCALAR },
				load: {
					include: { author: true },
					locks: {
						author: { mode: "pessimistic_read" },
					},
				},
			},
			response: {
				reference: { shape: EApiControllerRelationReferenceShape.OBJECT, key: "id" },
				load: {
					include: { author: true },
					relationLoadStrategy: "query",
				},
			},
		},
	},
}
```

Do not use old flat fields such as route-level `isEnabled`, `authentication`, `authorization`, `request.transformers`, `response.transformers`, `request.relations`, or `response.relations`. Do not use removed top-level `authentication.bearerStrategies` or `authentication.securityStrategies`; use `authentication.securityRequirements` groups instead.

Omitted route keys are generated with default configuration. There is no custom-only/default-disabled mode; explicitly disable CREATE, GET, GET_LIST, UPDATE, PARTIAL_UPDATE, and DELETE when only custom routes should be exposed.

Generated route transaction rules:

- Omitted `transaction` and `SUPPORTS` open no route transaction and preserve the legacy route boundary. The exception is every generated CREATE, scoped or not, which opens a `ROUTE` owner when none exists, rejects `NONE` at startup, and answers `403` after a rollback when the scoped reload misses the row.
- `REQUIRED` opens a `ROUTE` owner when none exists; `MANDATORY` requires an active owner; `NONE` rejects one.
- Request transformation and validation stay outside a route-owned transaction.
- Request relation hydration, generated service execution, and response relation reload share the active manager.
- When the route opens and owns the transaction, commit lifecycle finishes before response transformation, route-after, authorization result handling, and serialization. A joined outer owner commits later.
- Custom routes do not inherit generated route transaction config.

## Generated Error Responses

| Status | Declared when                                                                                                                              |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `400`  | always: DTO validation, typed GET_LIST/CURSOR codes, FK violation, relation reference, malformed JSON                                      |
| `401`  | a guard: `security.authentication`, `execution.guards`, `@UseGuards` on the class or the route                                             |
| `403`  | `security.authentication`, `execution.guards`, or securable controller + `authorization`                                                   |
| `404`  | GET, UPDATE, PARTIAL_UPDATE, DELETE; CREATE with an enabled `relations.request.load.include` (securable CREATE outside the scope is `403`) |
| `409`  | CREATE, UPDATE, PARTIAL_UPDATE                                                                                                             |
| `413`  | always: a body over the parser limit, 1 MiB in Fastify, 100 kB in Express                                                                  |
| `415`  | always: a content type Fastify refuses, a charset or content encoding Express refuses                                                      |
| `500`  | always                                                                                                                                     |
| other  | the `exception` status of each `request.<target>.validators` entry the route runs                                                          |

Each status uses `DtoGenerateException(status)` (`Exception<Status>DTO`): every status requires only `statusCode` and `message`; `error` is on the wire when the exception sets it, or when the interceptor or the filter answers a string or array response, an http-errors value, or an unknown failure, and `correlationID` and `timestamp` when the optional `CorrelationIDResponseBodyInterceptor` or that filter handles the error; a status `HttpStatus` does not list, such as `499`, is named by its status text or number (`ExceptionStatus499DTO`) and pins `statusCode` to its value; `message` is `string | string[]` and `error` a string, with no pattern or length limits; `details` only on `400` (`FOREIGN_KEY_VIOLATION`, `REFERENCE_NOT_VALID`, `TO_MANY_UPDATE_KEY`) and `409` (`UNIQUE_VIOLATION`). Guard rejections, guard failures, and body parser refusals skip the interceptor and carry only `statusCode` and `message` (plus `error` when a guard returns `false`) unless the exception filter is registered, which adds `correlationID` and `timestamp`. Every route, GET and DELETE included, also declares `413` and `415`: Express parses a body on GET and Fastify on DELETE.

Custom routes (`@ApiRouteCustom`, `@ApiMethod`) declare `401` and `403` with `security.authentication`, `execution.guards`, or `@UseGuards` on the class or the route, not counting the authorization guards the package attaches (only on the guarded subclass when the route is inherited; `APP_GUARD` is out of reach), `403` with a securable controller with `authorization` (only on the securable subclass when the route is inherited), `429` with `throttling.default`, `400`, `413`, `415`, `500` on every route, each `request.<target>.validators` exception status, and `404` with an enabled relation in `relations.request.load.include` or any key in `relations.response.load.include`, also one set to `false`; what a handler throws comes from `response.errors` (which has no `hasBadRequest` or `hasInternalServerError`). A status in `documentation.response.statuses` replaces the default response of that status.

## DTO Rules

- `EApiDtoType.BODY`, `QUERY`, `PARAMETERS`, and `RESPONSE` are the only DTO keys.
- `autoDto` supports `validators` only.
- Use entity `ApiPropertyDescribe.properties` for field enablement, requiredness, response exposure, filters, guards, and route/DTO-specific behavior.
- `ApiPropertyDescribe.isAutoDtoEnabled` defaults to enabled. `false` preserves metadata, TypeORM behavior, and manual DTO use while omitting the property from every generated DTO, generated Swagger relation component, and metadata-driven or typed client filter/order surface.
- DTO `isEnabled: true`, generated GET identity, `read.scope.parameters`, and client filter/order config cannot reopen a globally hidden property. Explicit `ApiPropertyCopy` bypasses only that global boundary and still applies all remaining source metadata rules.
- PAGE server-only `defaultOrder` and `tieBreakers` may target a described scalar with `isAutoDtoEnabled: false`. CURSOR order fields must be exposed in the generated response, so the same property is rejected for CURSOR ordering.
- Generated CREATE, UPDATE, and PARTIAL_UPDATE bodies omit date fields identified as `CREATED_AT`, `RECEIVED_AT`, or `UPDATED_AT`; responses retain them. Property names do not imply ownership, and `DATE` remains writable.
- Generated GET_LIST `request[QUERY].filter`, `order`, and `pagination` compile with entity/TypeORM metadata into one immutable plan. `INHERIT` overlays metadata; `REJECT` creates an allowlist; route config cannot re-enable a metadata-disabled field.
- Filter fields use exact disabled `{ isEnabled: false }` or enabled non-empty `allowedOperations` plus optional `OMIT`, `REJECT`, or `USE_DEFAULT` missing behavior. UUID fields accept `eq`, `ne`, `in`, `notin`, `isnull`, and `notnull` (nullary operators only when nullable); every `[values]` item must be a UUID, for direct `id` and one-hop paths such as `currency.id`. Client order fields are direct-scalar enabled/disabled overlays and have no filter-only settings. `isnull` and `notnull` need a column declared `nullable: true` or a property described with `isNullable: true`; the plan reads the column from the entity class and its parents, so one inherited from an abstract base or a mixin counts on PAGE and CURSOR routes.
- `order.defaultOrder` and `order.tieBreakers` are ordered server-only `{ field, direction }` arrays. They may target any described direct scalar field, including UUID fields left out of the client order enum. UUID and `timestamptz` fields listed in `fields` are client-sortable. A client order pair replaces defaults, tie-breakers are appended, and duplicate fields retain the earlier entry.
- `pagination.mode` is optional and defaults to `PAGE`. `PAGE` requires `limit` and `page` and returns `IApiGetListResponseResult<E>`. `CURSOR` requires `limit`, accepts zero or one of `after`/`before`, and returns `IApiGetListCursorResponseResult<E>` with exactly `items`, `nextCursor`, and `previousCursor`.
- `CURSOR` requires an explicit order whose final tie-breakers are the complete primary key, single or composite: each component exactly once, in any order among them, after every other order entry. No component can appear earlier or in the client order allowlist; every possible order field must be a selected, persisted, described non-null direct scalar with no TypeORM transformer/accessor and must be unconditionally raw-exposed.
- CURSOR v1 supports only PostgreSQL standard text results and only these TypeORM order declarations: `boolean`; signed `smallint` and `integer`, including increment-generated columns whose DDL uses `SMALLSERIAL`/`SERIAL`; numeric enums backed by `smallint` or `integer`; signed `bigint`, including increment-generated `BIGSERIAL` DDL, exposed as canonical decimal `BIGINT_STRING`; native `uuid`; and `timestamptz` with a declared integer `precision` from 0 to 3, described as `DATE_TIME`. An unset precision, any other precision, `timestamp`, and any date column the active driver does not store as `timestamptz`, such as an untyped `@CreateDateColumn`, fail at bootstrap naming the field. Temporal token values are canonical ISO-8601 UTC strings with millisecond precision for years 0001 through 9999, and a `timestamptz` field can be client-sortable through `fields` and is also available through `defaultOrder` and `tieBreakers`. SERIAL-family names are PostgreSQL DDL forms, not TypeORM column type literals. Binary mode, custom `extra.types`, all other PostgreSQL types, and all other drivers fail at application bootstrap (`Controller "<Name>" route "getList": CURSOR GET_LIST supports only PostgreSQL; the active driver is "<driver>"`) and again before CURSOR query I/O; PAGE is unchanged. CURSOR rejects entity `@AfterLoad` listeners at bootstrap and applicable active TypeORM `afterLoad` subscribers at bootstrap and again before query I/O. Subscriber `listenTo()` and active PostgreSQL parser configuration are trusted TypeORM extension code and must be deterministic. Request-only `ApiPropertyDescribe` bounds, lengths, patterns, and `multipleOf` rules do not define the opaque cursor boundary, and `BIGINT_STRING` values never pass through `Number`.
- A column the list response hides is neither filterable nor orderable: `select: false`, `isExpose: false`, a disabled GET_LIST response side, a response guard the route guard does not match, or a field a manual list response DTO does not publish; `relation.field` follows the rule for both segments. Such a filter or order returns `400` (`FILTER_NOT_VALID` for a filter) before any SQL. A typed `filter.fields` entry enabling one fails at startup naming the controller, route and field; `{ isEnabled: false }` stays valid. A PAGE route with a manual list response fails at instantiation while its generated filters name a field that response leaves out; fix with `{ isEnabled: false }`, a `REJECT` allowlist, or `properties.getList.query.isEnabled: false`.
- Manual GET_LIST QUERY DTOs cannot be combined with generated filter/order/pagination config. Manual RESPONSE DTOs remain compatible; CURSOR `{ itemType }` and full wrappers must prove same-name protected item fields and the exact flat envelope through Automator response metadata.
- Generated GET/GET_LIST `read.scope.parameters` creates the PARAMETERS DTO from inherited controller-path mappings and cannot be combined with a manual PARAMETERS DTO.
- Generated GET and GET_LIST over a single-table-inheritance root generate one RESPONSE DTO per variant, named `<Prefix>GetResponse<Value>DTO` and `<Prefix>GetListResponse<Value>DTO`, where `<Value>` is `CamelCaseString` of the discriminator value. GET is `oneOf` plus discriminator mapping; GET_LIST keeps its wrapper and puts `oneOf` on `items`. The discriminator property is kept. An unmapped or missing value on a row, including one removed by a subscriber or transform, fails with `500` without echoing it. The 4.x `<Root>GetResponseDTO` and `<Root>GetListResponseDTO` components are not generated for such a root.
- A leaf `@ChildEntity` is always a variant. The root and intermediate child entities are variants only when the discriminator column can store their value: no `enum`, or the value is in it. Bootstrap fails on a leaf value outside the enum; a non-string or empty value; a value with a character outside `[A-Za-z0-9_-]`; a DTO name suffix that collides with another suffix or produces another generated name of the entity such as the GET_LIST wrapper or a relation DTO of another variant; a discriminator column missing, undescribed, `select: false`, numeric, or hidden from GET/GET_LIST responses on the root; no child entity loaded at decoration. Values are never normalized. The property column options decide, not `@TableInheritance({ column })`.
- `CURSOR` over a single-table-inheritance root requires order fields on root columns. Each variant must also pass the raw-exposure, accessor, and `@AfterLoad` proofs.
- The column rule of path values is enforced by Crud Automator on every generated route that has path values (GET, UPDATE, PARTIAL_UPDATE, DELETE, and GET_LIST with `read.scope`). A configured `dto[EApiDtoType.PARAMETERS]` only validates the converted values afterwards, with `forbidUnknownValues: false`: an `@ApiProperty()`-only DTO and `@IsInt()` without `@Type` accept `/x/1`, and `/x/016` is `400` even with `@IsInt() @Type(() => Number)`; the Nest param type and OpenAPI path parameters come from the generated DTO. IAM sees the canonical text of path values (integer decimal, lower-case UUID, `true`/`false` for `BOOLEAN`, ISO 8601 UTC with ms for `DATE_TIME`, `YYYY-MM-DD` for `DATE`) in `request.parameters`, `resourcePath`, and `${request.parameters.*}`, and `resource.*` conditions compare by the same text; the guard writes the text back to `request.params`, while guards that run before it see raw text. `BOOLEAN` request values accept only `true`/`false`. A single-value NUMBER field given an array is `400`. Securable `@ApiRouteCustom` routes must copy each path parameter that their IAM `resourcePath` names with `ApiPropertyCopy` in their PARAMETERS DTO, or startup fails naming the placeholder. The guard runs the route's actual PARAMETERS DTO before authorization, with and without implicit conversion because it cannot see the host pipe's options: class-validator with `forbidUnknownValues: false`, only for properties that hold a path value; read through the `@Expose` name; canonical text. The handler reads the value authorization saw, or the request is refused: both conversions accept with different text → `400` `<param> converts differently with and without implicit conversion`; no text → `400` `<param> has no text form`; the canonical text is always written to `request.params`; the DTO runs again on changed text and an accepting conversion with other text → `400` `<param> does not keep its value when its DTO runs on it again`. A conversion that rejects or throws is not counted while another accepts. So `request.parameters` conditions see the value the DTO produces, for renames, mapped types, bare class-validator rules, and `@Transform` (with `@IsInt() @Type(() => Number)` a Deny on `"16"` is `403` for `/016` and `/0x10`; with `ApiPropertyNumber` `/016` is `400`). A securable `@ApiRouteCustom` or `@ApiMethod` route with a path parameter, IAM or HOOKS, fails at startup (naming controller, method, parameter, and the change) without a PARAMETERS DTO, when the DTO does not describe a path parameter with a class-validator rule, `ApiProperty*`, `ApiPropertyCopy`, `@Transform`, or `@Type`, for a HOOKS DTO property without `ApiPropertyCopy` or `ApiProperty*` (a bare `@IsInt() @Type(() => Number)` has no column type; the declared DTO type decides the canonical text, and `ApiPropertyCopy` declares the column's type, so `ApiPropertyString` on an integer column keeps `016` for handler and policy alike), for a pipe other than `ValidationPipe` (class or instance) in `@UsePipes` on the method or the controller, and for a `ValidationPipe` there with `expectedType` or with another class-transformer or class-validator from `transformerPackage`/`validatorPackage` (process-wide in Nest; startup runs the pipe once on a probe DTO that passes every rule, so its `exceptionFactory` never runs; the probe DTO is declared only when such a pipe is found and stays in the class-transformer and class-validator metadata), for any pipe on `@Param` (`ParseIntPipe`), for a `@Param("id")` whose type compiles to neither `String` nor `Object` (`number`, `Date`, a class; `string`, `unknown`, `any`, and unions start), and for a `@Param()` typed as another class than the DTO. A global host pipe (`useGlobalPipes`, `APP_PIPE`) is the host's choice and is not checked. The path parameters are those of the served paths: global prefix (not on a route `setGlobalPrefix` excludes), `RouterModule` path (nested modules too), controller path, and route path; each part is read as the router of the running adapter reads it (Express: `\:x` is text; Fastify: `a::b` is text and `\:x` is the parameter `x`; another adapter: the names of both count). A wildcard (`*`, `*name`, `{*name}`) in any part of a securable route fails at startup, and so does a generated route whose `RouterModule` path or global prefix adds a parameter its generated DTO does not describe (`read.scope.parameters` maps only controller path parameters, so use `@ApiRouteCustom` with a PARAMETERS DTO). An IAM route, generated or custom, that neither lists nor creates fails at startup when its `resourcePath` names a placeholder that is not a path parameter (a generated GET `identity.parameter` counts for the field it names): it would render as `*`, which no Deny on a value matches; serve it with `@ApiRouteCustom` under that path parameter copied with `ApiPropertyCopy`, or use HOOKS. A list (`route.type` `GET_LIST` or action `list`) keeps such a placeholder and maps it to row exclusions, but its handler must apply `decision.scope.where`, and its IAM action becomes `<policyNamespace>:list`, so a separate action such as `export` merges into `list`. A create (`route.type` `CREATE` or action `create`) keeps it too: it names no row yet. A request whose `request.params` holds a key startup did not record for its route, or that reaches a route startup did not check, answers `500` before the policy, the handler, and any query, logged with controller, method, and parameter; a test that replaces `ApiAuthorizationBootstrapValidationService` turns this off, but the guard then builds the rule of a custom route from its PARAMETERS DTO on its first request, so an upper-case UUID is still `400` and a route startup would refuse answers `500`. A path parameter is a UUID by any declaration: `ApiPropertyUUID`, `ApiPropertyString` with the UUID format, a bare `@IsUUID()`, or `ApiPropertyCopy` of a UUID column; an `ApiPropertyCopy` with `shouldAutoResolveContext` on a custom PARAMETERS DTO follows `route.type` + `PARAMETERS`, and one that no context reaches fails startup (a DTO with such a copy cannot serve two route types). `@Req()` and a custom param decorator read the canonical text the guard wrote to `request.params`; only their own conversion, or a pipe on them, is unchecked. A `@Transform` runs several times per request, in the guard and in a host pipe, and on samples at startup, so it must be pure; one that changes its own output (`p-` on every call, base64 decode) cannot serve a securable route. Startup runs the same checks on `"1"` and `"Aa"`, and `"true"`/`"false"` for a boolean property, which must also keep their values, and fails naming controller, method, DTO, and the change; a sample that a conversion rejects or that has no text says nothing, so such values are checked per request. Startup also fails for a path value that becomes an object or list, for a dropped value (`@Exclude({ toClassOnly: true })`, `constructor`, `__proto__`), for two properties exposing one parameter name, for a property exposed under another name, for a renamed property whose `@Transform` throws on write-back with every kind of sample (add `{ toClassOnly: true }`), and for `isResponse` in the DTO. Read from the metadata, startup also fails for a `@Transform` with `groups`, `since`, or `until`, an `@Expose` with `since` or `until`, and a validator with `groups`, on a path value, and for a decimal/numeric/float/double/money column as a path value on a securable route, IAM or HOOKS, generated or copied. Text of an integer column on a generated route or a copied property must be `0` or `-?[1-9]\d*`; otherwise `400` `<param> must be a decimal integer without leading zeros`. The default signed `BIGINT_STRING` pattern refuses `-0`. A Deny compares text, so under a case-insensitive collation `/ABC` finds the row of `abc`. `requestMetadata.parameters` and hooks context `parameters` are `Record<string, string>`. An upper-case UUID path value returns `400` under `ApiPropertyUUID`, its mapped types, and a bare `@IsUUID()`, with or without a known column; bare `@IsString()`, `@IsDateString()`, and `@IsNumberString()` keep the sent text. A HOOKS `@ApiRouteCustom` runs its PARAMETERS DTO in the guard as an IAM route does: its policy reads canonical `context.parameters`, and `/016` or an upper-case UUID returns `400` before it, with no query. `ApiAuthorizationGuard` and the bootstrap service require `ApiAuthorizationParametersRuleRegistry`; a manual `new` without it throws naming the registry. `DOUBLE` text is decimal text only (`^-?(0|[1-9]\d*)(\.\d+)?([eE][+-]?\d+)?$`; `""`, `" 16 "`, `0x10`, `.5` → `400`), in DTOs and typed list filters. A lone value of a list field of any type is a one-item list (`?counts=7` → `[7]`); a comma list is one item (`1,2`), which typed items reject. An empty value is one empty item the item rule checks: `?days=` on an optional date list and `""` on a single date are `400`, and a string list gives `[""]` only if its item rules allow it. The rule is built per controller class and kept per application, so a custom route inherited by several securable controllers is checked and validated by each controller's own `resourcePath`. Path values, typed GET_LIST query plans, and root-level discriminated `@ApiRouteCustom` bodies are enforced by Crud Automator without a host pipe; other request bodies, custom route query DTOs, and a GET_LIST query without `filter`/`order`/`pagination` configuration are validated only by a host `ValidationPipe`. `BOOLEAN` and `NUMBER` request DTO properties carry `Type(() => Object)` and check exactly the value the client sent, under any `@Expose` name and pipe options: `enableImplicitConversion` does not turn `"false"` into `true`, `"016"` into `16`, or `true` into `1`. UUID columns are lower-cased in generated write bodies and list filters; text columns with stored upper-case UUIDs need a one-time `UPDATE … SET col = lower(col)`. Path values are validated and converted once per request, by `ApiAuthorizationGuard` on a securable route or before route-before subscribers otherwise, cached on the request, and checked once more after route-before subscribers and PARAMETERS transformers/validators. Each value must fit its column's `ApiPropertyDescribe` type: `UUID` is a lower-case UUID (v1–v8, nil, max; upper-case → `400` `id must be a lower-case UUID`, never lower-cased), an integer `NUMBER` is canonical decimal text (`^-?(0|[1-9]\d*)$`) within `minimum`/`maximum`, a `DATE` is a real `YYYY-MM-DD` day and stays that string. Otherwise `400` with the Nest `ValidationPipe` body (`message: string[]` such as `id must be a UUID`, `error: "Bad Request"`, `statusCode`; `correlationID` and `timestamp` with `CorrelationIDResponseBodyInterceptor`; when the guard rejects, which is before interceptors run, only with `CorrelationIDResponseBodyExceptionFilter`), no SQL, no echoed value. Authorization (`request.parameters`, `resourcePath`, `${request.parameters.*}` conditions) uses the canonical text of those values; `read.scope`, subscribers, service calls, and the CURSOR context hash use the typed values. HOOKS/IAM scope scalars on described columns are converted with the same parser before merging; an invalid one becomes `In([])`. `BEFORE_ERROR` subscribers see the raw string when the check fails. A missing `read.scope` or identity value returns the same body with `<parameter> should not be null or undefined`. OpenAPI path parameters come from the same DTO (`format: uuid` with an `IsUUID`-equivalent pattern; `integer` with `format`, `minimum`, `maximum`). An integer `NUMBER` bound outside the safe integer range fails at startup; `bigint` is described only as `BIGINT_STRING`. Before 5.0.0 these values reached the database (PostgreSQL `22P02` became `500`).
- The package does not include a consumer-side typed URL/bracket-filter builder in the current 3.x contract.
- Generated DTO names are `<Prefix><Route><DtoType>DTO`; every nested generated DTO at any depth (relation, dynamic object variant, contextual manual DTO copy) is `<Parent><Property>[<Variant>]DTO`, where `<Parent>` is the holding DTO name without one trailing `DTO` in any case and the property is PascalCase without one trailing `DTO` in any case, unless nothing else is left (`dto` gives `…DtoDTO`, `fooDtoDto` gives `FooDto`; a name of separators only, such as `_`, fails startup, also for the handler of a custom route that generates DTOs): root relation `…GetResponseOwnerDTO`, the same relation in variant `V1` of `details` `…GetResponseDetailsV1OwnerDTO`, GET_LIST wrappers are `<Prefix>GetListPageDTO` and `<Prefix>GetListCursorPageDTO` (4.x `<Entity>GetList[Cursor]ResponseItemsDTO`), which no property name can produce, so a relation `items` is `<Prefix>GetListResponseItemsDTO` next to them; typed query, identity and read scope parameter DTOs are `<Prefix>GetListQuery<signature>DTO`, `<Prefix>GetIdentity<signature>DTO` and `<Prefix>Get[List]Parameters<signature>DTO`. `<Prefix>` is `ApiControllerGetSchemaPrefix(controllerClass)`: the class name without a trailing `Controller` (the full name when nothing is left). The entity name is not part of generated names. `@ApiRouteCustom` BODY, PARAMETERS and QUERY DTOs are `<Prefix><Method><DtoType>DTO`, with the handler method name in PascalCase in place of the route type. A nested name segment uppercases the first letter of the property or variant name and every letter after `_`, `-`, `.` or a space, drops those separators and keeps every other letter: `v2Item` → `V2Item`, `HTMLContent` → `HTMLContent`, `userID` → `UserID`, `ID` → `ID`, `created_by` → `CreatedBy`, `x-id` → `XId`, `v2-beta` → `V2Beta`. An anonymous controller class fails at decoration. A relation or dynamic object copied with `ApiPropertyCopy` is `<Host><Property>[<Variant>]DTO`, where `<Host>` is the DTO it is copied into without a trailing `DTO` and `<Property>` is the decorated host property, not the copied entity property (one relation copied into `currency` and `previousCurrency` gives two DTOs). A GET_LIST wrapper around `dto: { [EApiDtoType.RESPONSE]: { itemType } }` is `<Prefix>GetListResponse<ItemType>` with the item class name, unless `name` is set. Uniqueness is decided once per application at bootstrap by a check that `@ApiController` attaches to the controller class (an internal exception filter that never handles an exception, so its bootstrap hook also runs for REQUEST-scoped controllers and when `ApiAuthorizationGuard` is overridden), over every controller that application contains, plain `@Controller` classes included (only the prefix check needs `@ApiController`); decoration only names classes and records their origin on the class. `app.init()` fails for two different decorated classes with one prefix (the error names both controllers with module and path), for two different classes with one OpenAPI component name anywhere in a route schema of a generated, `@ApiRouteCustom` or plain route (responses, body, query, parameters and extra models, walked at any depth: generated DTOs, hand-written DTOs, nested plain Swagger classes; the error names both origins, for example `property address in XGetResponseHomeDTO` or `the 200 response of route mine in controller XController`), and for a lazy `type: () => Class` that throws or returns `undefined` (the error names the DTO and property). Re-evaluated modules (webpack HMR, `vi.resetModules`) and several applications in one process need no special case, because only the classes of one application are compared. A document exported with `SwaggerModule.createDocument` without `app.init()` is not checked. DTO generation caches are keyed by entity class, so a re-evaluated module generates its DTOs again. Generated routes on a subclass or mixin of the decorated controller use the decorated class's prefix at runtime. An `@ApiRouteCustom` handler that a decorated controller inherits from a base class or mixin gets an own copy on the controller (calling the inherited handler) whose BODY, PARAMETERS and QUERY DTOs use that controller's prefix, so two controllers extending one base each get `<Prefix><Method><DtoType>DTO`. The check is an exception filter `ApiControllerSchemaNameCheck` attached with `UseFilters`; it catches no route exception, but `Reflect.getMetadata(EXCEPTION_FILTERS_METADATA, controller)` lists it. `DtoGenerate`, `DtoGetGetListQueryBaseClass`, `ApiControllerGetDto`, `ApiControllerApplyDecorators`, and `DtoGenerateTableInheritanceResponse` require that `schemaPrefix` argument.
- `ApiPropertyObject` and `ApiPropertyCopy` register polymorphic variants as extra models of the DTO that holds the property. A Swagger mapped type (`PickType`, `OmitType`, `PartialType`, `IntersectionType`) drops them, so a mapped class that keeps such a property declares `@ApiExtraModels(...)` with the variant classes.
- `isExpose` is response-only and requires `isResponse: true`.
- `@Expose` and `@ApiProperty*` work in either order: an explicit `@Expose`, own or inherited, keeps its name, groups and versions, and `isExpose: false` or `@Exclude` wins over one without a name. A named `@Expose` next to `isExpose: false` or any `@Exclude` but `{ toPlainOnly: true }` fails at startup. A bundler that loads two copies of `class-transformer` fails at decoration with `Cannot read class-transformer metadata`. A request reads the exposed name; validation errors name the declared property. A response is built by property key (`toClassOnly` and undirected `@Transform` run, `obj` is the full row) and sent under the exposed name on every path, with or without `ClassSerializerInterceptor`; the schema publishes the exposed name. Under the interceptor and on CURSOR class-to-plain follows: `toPlainOnly` runs there, and undirected transforms run again with `obj` set to the DTO, so write masks as `toClassOnly`. A request that sends an `@ApiProperty*` property under its property key, alone or next to the exposed name, in a body, nested object, array item or query, gets a 400 `property q should not exist, send it as q_wire` (constraint `requestPropertyRenamed`); so does a server-side `plainToInstance` of a plain object that owns the key, so pass a class instance or the exposed names. A child class exposing another property under a parent's renamed property key fails at startup (or first conversion). A nested manual DTO on a generated route keeps its `@Expose`, `@Exclude`, `@Transform` and `@Type`; a copied `toClassOnly` or undirected mask also runs on a generated write body, so a DTO used for both request and response stores the masked value.
- Guard-scoped DTO generation depends on the route's configured guard class; it is not a per-request role check.
- An `@ApiPropertyDate` request value takes the published form of its `format`, the same as its list filter: `DATE` is `YYYY-MM-DD` text for an existing day and `TIME` is `HH:mm:ss` text, both kept as text; `DATE_TIME` is the UTC instant `YYYY-MM-DDTHH:mm:ss.sssZ`, turned into a `Date`; years run from 0001 to 9999, as in filters. The value is checked as sent, also under `enableImplicitConversion` on a property typed `Date`. The value is judged as sent under its exposed name, in any decorator order, so a consumer `@Transform` cannot make an off-form value pass. `ApiPropertyString` refuses `format: DATE` at decoration; on an entity use `ApiPropertyDescribe({ type: DATE, format: EApiPropertyDateType.DATE, identifier })`. Anything else fails with `<property> must be in <form> format` (`isDateFormatValue`). Bodies are checked only under a host `ValidationPipe`; without one a generated route stores the text as sent.
- `isUniqueItems: true` on a request array answers `400` for equal items, compared after transformation: a Date by instant, a top-level UUID without case, an object by value whatever its key order, a DTO class instance on its declared properties only. It runs where a `ValidationPipe` runs, generated routes included. Items nesting past 64 levels fail with their own `400`. On a response array it is OpenAPI schema metadata only. Set `isUniqueItems: false` on an array that accepts repeats.
- A free-form `@ApiPropertyObject` request value (`type: Object`, `dataType: Object`, or an explicit `undefined`; omitting the key does not compile) keeps its keys under `whitelist` and `forbidNonWhitelisted`, at any depth; a key `__proto__`, `constructor`, `hasOwnProperty` or `prototype` answers `400` on every `@ApiMethod` route before the pipe (on a plain Nest route any `ValidationPipe` removes `__proto__`, `prototype` and `constructor`). `shouldValidateNested: true` on it and `type: [Object]` do not compile and fail at decoration naming the class and property; a free-form array does not need `shouldValidateNested`. Only its being an object is checked (`single must be an object`, `each value in payloads must be an object`, which rejects `null` and nested arrays). OpenAPI publishes `{ type: "object" }` or `{ type: "array", items: { type: "object" } }` with no `properties`. With `isUniqueItems: true` items compare on all their keys, by value at any depth and whatever their key order, and an item nesting past 64 levels fails with its own `400`.
- A request body on an `@ApiMethod` route (generated and `@ApiRouteCustom` included) may nest 64 levels, the body being the first and each object or array one more, and each object may hold 1000 keys. Past that it answers `400` after the guards and before any pipe, with `request body must not nest more than 64 levels deep` or `request body must not hold an object with more than 1000 keys`. Array length is not limited by this check. A scalar, `Buffer`, stream or class instance is not walked. Form bodies count the same way on both adapters. An object reached from several places counts once at its shallowest level, so a cycle passes, as with multipart `attachFieldsToBody`. An interceptor in `execution.interceptors` that fills the body, such as multer, runs after the check; attach it through `generation.decorators` or a `@UseInterceptors` below the route decorator so the check sees its result. The depth is one constant shared with the unique-items comparison. The refusal is an exported `ApiRequestValidationException` (a `BadRequestException` whose response is the usual message list) with `validationErrors`: one `ValidationError` with no `value` or `target`, constraint `requestBodyMaximumKeys` or `requestBodyMaximumDepth`, and `property` the dotted body path, empty for the body itself. The path holds client keys, so never send it. `ApiRequestValidationGetErrors(exception)` returns the failures from the exception or its `cause` chain and `undefined` for any other value; the walk is bounded and safe on any thrown value. A translating filter builds its own exception from them, passes it through `CorrelationIDNormalizeException`, and lets `BaseExceptionFilter.catch` answer; the guide `docs/guides/error-handling` has the recipe. A guard-raised and an interceptor-wrapped failure then answer the same keys, with `correlationID` equal to the `x-correlation-id` response header.
- The same check answers `400` for a key `__proto__`, `constructor`, `hasOwnProperty` or `prototype` at any depth (`request body must not use the reserved key <key>`, constraint `requestBodyReservedKey`, `property` ending with the key), and for a NUL in any string or key (`request body must not hold a NUL character`, constraint `requestBodyNulCharacter`; for a key the path stops at the object that holds it), on every driver, with no option. Only keys are checked; the words as values pass, as do `toString` or `valueOf`. Some bodies get the parser's own `400` first: Fastify's JSON parser for `__proto__` and for a `constructor` whose value holds `prototype`, and `@fastify/multipart` for a field named `__proto__` or `constructor`. A free-form `@ApiPropertyObject` declares `Type(() => Object)` and a plain-only transform, so class-transformer never builds its value through a stored `constructor`: a row already stored with these keys reads back exactly as stored on `GET`, page `GET_LIST` and cursor `GET_LIST`. Under a host `ClassSerializerInterceptor` these routes answer `200` with the value less `constructor` and `__proto__`, which `instanceToPlain` always drops, and a cursor `GET_LIST` answers what a page `GET_LIST` answers for the same row.
- Every `@ApiProperty*` request array must declare `minItems`, `maxItems` and `isUniqueItems`; one that leaves any out from JavaScript or `any` fails at decoration naming the DTO class, the property and the missing bounds. On any array, a `minItems` or `maxItems` that is not a non-negative integer (`NaN` from `Number(process.env.X)`, `Number.POSITIVE_INFINITY`), an `isUniqueItems` that is not a boolean, or an `isArray` that is not a boolean fails at decoration. Response arrays (`isResponse: true`) may omit the bounds, and the schema then publishes none; every `@ApiProperty*` options type includes `TApiPropertyBaseResponseArrayProperties` for this, so narrowing one on `isArray === true` alone leaves the bounds possibly `undefined`.

## Service And Function Signatures

```ts
create(properties: DeepPartial<E>): Promise<E>;
update(criteria: FindOptionsWhere<E> | Array<FindOptionsWhere<E>>, properties: DeepPartial<E>): Promise<E>;
delete(criteria: FindOptionsWhere<E> | Array<FindOptionsWhere<E>>): Promise<void>;
get(properties: FindOneOptions<E>): Promise<E>;
getList(properties: FindManyOptions<E>): Promise<IApiGetListResponseResult<E>>;
getMany(properties: FindManyOptions<E>): Promise<Array<E>>;
```

In PAGE mode, controller query parameters (`limit`, `page`, `orderBy`, `orderDirection`, bracketed filters) become TypeORM `take`, `skip`, `order`, and `where` before `service.getList(...)`. With a typed plan, the authoritative parser validates exact paths, operations, cardinality, and scalar values independently of host `ValidationPipe`, then the route validates the generated QUERY DTO for the entity value constraints the OpenAPI value schema publishes. A `date`-format field takes `YYYY-MM-DD` calendar text and a `time`-format field `HH:mm:ss`, bound and compared as written on both paths in every time zone; a date-time field takes the UTC instant `YYYY-MM-DDTHH:mm:ss.sssZ`. Other forms return `400`. Without a typed filter, the route validates its generated or manual QUERY DTO from the raw request query, independently of host `ValidationPipe`, and throws `BadRequestException(ApiRouteValidationFlattenErrors(errors))` before any SQL, preceded by `property <key> should not exist` for each query key the DTO does not publish (properties with class-validator or Swagger metadata, inherited included, and own properties of a new instance; an `@Expose` name, read from class-transformer metadata through `ClassTransformerGetStorage`, replaces the property name behind it; read-only prototype members such as the generated `object` anchor are not keys), plain keys such as `_` or `utm_source` included; the generated DTO publishes one-hop filters through to-one relations only; `ApiControllerGetListTransformFilter` throws `BadRequestException("FILTER_NOT_VALID")` for a `<field>[operator]`/`[value]`/`[values]` group it cannot apply, or whose value key and count do not match the operand `FILTER_OPERATOR_REGISTRY_CONSTANT` gives its operator (the rule of the generated DTO's pairing validator), and leaves other keys to the DTO, and `ApiControllerFactory.assertGetListPublishedFilters` fails startup (controller instantiation, or `app.init()` for a REQUEST-scoped controller) when a manual QUERY DTO publishes one or exposes a filter property under another name, both through `ApiControllerGetListTransformGetFilterMetadata`; number, uuid, enum, boolean, and date-time filter values then bind as the shared value parser reads them (a boolean as a boolean, so SQLite compares it with the stored `1`/`0`), and other values bind as sent. `FilterOrderByFromEntity(entity, metadata, method, dtoType, fieldSelector?, currentGuard?, publishedFields?)` is the single source of the orderBy enum and its validation on legacy and typed routes: a column must have its value exposed by the GET_LIST response (the internal rule CURSOR order fields also use: not disabled, not `isExpose: false`), be enabled as a QUERY field, and not be `useAsOrderByFilter: false`, all evaluated for the route guard. A manual GET_LIST response DTO (wrapper or `{ itemType }`) passes the item properties of its generated OpenAPI schema as `publishedFields`. A route with a manual QUERY DTO holds the `orderBy` and `orderDirection` values that DTO produced to the same fields and to lowercase `asc`/`desc`, including values it exposes under other query names; a class default the client did not send stays the route's own order. It applies `USE_DEFAULT`, then the route transaction AND-merges query, path, and current authorization scope and applies the effective order.

In CURSOR mode, the generated route uses the existing decorated `service.getMany(...)`: the first window is one `limit + 1` query; an `after` or `before` window is that query plus exactly one opposite-direction `take: 1` probe. The GET_MANY BEFORE chain runs once per HTTP request against detached base options, and its candidate `where`/`withDeleted` is reused identically for the main query and probe. Both calls retain that candidate plus query, path, recalculated HOOKS/IAM, and cursor-window predicates. The route authorization action remains GET_LIST; GET_MANY AFTER runs for each actual query. Generated calls own `order`/`take`, force `cache: false`, shadow `select`/`skip`, reject `join`/`lock`, and fail closed on protected result/envelope changes; direct calls retain their ordinary per-call behavior. The strict canonical Base64URL token is stateless and unsigned; it stores version, context hash, and typed order values, so no cursor rows or keys are required. Context binds route, path values, plan signature, normalized actual filter AST, and effective order, but excludes `limit` and IAM scope.

## Generated Read Scope

Generated GET may expose its actual primary column under a different wire parameter with top-level route configuration:

```ts
routes: {
	[EApiRouteType.GET]: {
		identity: { parameter: "gameId" },
	},
}
```

This changes the generated path and PARAMETERS DTO to `:gameId`; it does not select another lookup field or rename response properties. Runtime service criteria still target the actual primary column. Before HOOKS/IAM evaluation, authorization receives both the external alias and the canonical primary-field key, so primary placeholders such as `{id}` and canonical conditions keep their normal meaning. `identity` is GET-only and cannot be combined with a manual PARAMETERS DTO.

An identity-only GET is valid only when the controller path has no inherited dynamic parameters. If the controller path contains any `:parameter`, the same GET must also configure `read.scope.parameters` and map every inherited parameter exactly once.

Generated GET and GET_LIST routes accept:

```ts
read: {
	scope: {
		parameters: [
			{ parameter: "providerKey", field: "providerId" },
		],
	},
}
```

This contract is intentionally closed:

- It is valid only on GET and GET_LIST.
- `parameters` must be a non-empty array and every entry has exactly `parameter` and `field`.
- Every required scalar `:parameter` in the inherited controller `path` must be mapped exactly once; parameters and fields cannot repeat. Wildcards and optional/grouped dynamic parameters fail at bootstrap.
- `field` must be a described direct scalar column. Relations and objects are rejected.
- A GET controller path cannot reuse the effective generated identity parameter or, when an alias differs, inherit the actual primary-field name. Read scope does not rename or replace GET identity.
- A manual `dto[EApiDtoType.PARAMETERS]` is mutually exclusive. `autoDto[PARAMETERS]` validators remain available.

The generated route-local PARAMETERS DTO applies selected entity field metadata under each external path name and drives Nest parameter metadata plus Swagger. GET includes its configured identity alias (or the ordinary primary-field parameter when no alias is configured) and the mappings; GET_LIST includes the mappings. Runtime criteria are merged as identity/query → path → HOOKS/IAM with logical AND. Field conflicts become match-nothing criteria, never last-write-wins replacement. Scalar leaves are normalized to explicit TypeORM `Equal(...)` predicates during an additional-scope merge; object-valued scalar columns must already be wrapped in `Equal(value)` because raw objects denote relation or embedded criteria.

`@ApiFunctionDelete` internally removes an entity snapshot, but generated service/controller delete APIs intentionally expose `Promise<void>`. Do not design public delete flows around receiving the removed entity unless the source contract is changed first.

Use `@ApiFunctionStep({ entity, transaction })` for private/protected/public helper methods inside service use-cases when they need the current transaction context. Direct calls are valid when the selected transaction mode permits. In a step, call `this.getApiFunctionStepContext()` for `eventManager`, `repository`, and `getRepository()`. Steps are not custom actions and do not dispatch function subscribers, route metadata, Swagger metadata, or authorization action identities.

## Custom Route Boundary

Use `@ApiRouteCustom` when a custom route should participate in route runtime behavior. Use `@ApiMethod` only when metadata composition is enough.

Route guard stages:

- `execution.guards` entries are a plain `CanActivate` class/instance or `IApiRouteGuardProperties` `{ guard, stage? }`. A function or an object exposing `canActivate` (prototype chain included) is treated as a plain guard instance and its other properties, such as `guard` or `stage` fields, are ignored; every other object is a staged guard descriptor whose `guard` must be a guard class or instance. Null/primitive entries and invalid descriptor guards throw at decoration.
- Chain order: `EApiRouteGuardStage.BEFORE_AUTHENTICATION` guards → `security.authentication.guard` (if configured) → `AFTER_AUTHENTICATION` guards → `ApiAuthorizationGuard` → `AFTER_AUTHORIZATION` guards. Declaration order is kept within a stage.
- Plain guards and entries without `stage` are `BEFORE_AUTHENTICATION`, so pre-stage configuration keeps its order.
- `AFTER_AUTHENTICATION` guards see the principal set by the authentication guard; on securable controllers `AFTER_AUTHORIZATION` guards also see the attached authorization decision.
- Generated routes, `@ApiRouteCustom`, and direct `@ApiMethod` share the same ordering because all compose through `@ApiMethod`. Guards added through `generation.decorators` or other `UseGuards` decorators are outside this staged chain.

Root-level discriminated custom route bodies:

- `dto.body: { type: [...], discriminator, validatorOptions?, transformOptions?, exceptionFactory? }` (`TApiRouteDiscriminatedDtoProperties`). Crud Automator selects, transforms, and validates the variant itself; the host `ValidationPipe` options never reach it, so mirror them with these three options.
- `shouldKeepDiscriminatorProperty` left out means keep, at root level and on `@ApiPropertyObject`; only `false` removes the property. At root level `false` selects the variant from the full body and removes the property before transformation and validation, so the variant must make it optional. A variant that requires it through an `@ApiProperty*` decorator fails at startup unless `validatorOptions.skipMissingProperties` is set, which answers `200`; one that requires it only through raw `class-validator` is not detected and answers `400` on every body. On an `@ApiPropertyObject` request property `false` fails at decoration naming the class and property; it stays allowed with `isResponse: true`, which a generated response DTO sets, where it removes the property from the response, also deletes it from the returned source object, and comes back through `instanceToPlain`.
- `exceptionFactory(errors: Array<ValidationError>) => unknown` has `ValidationPipe` semantics: it may be sync or async, and its awaited return value is thrown instead of the default `BadRequestException(string[])`. Variant failures pass native `ValidationError[]` (`value`/`target` follow `validatorOptions.validationError`); a non-object body or missing/unknown discriminator passes one synthetic `{ property, constraints: { mustMatchDiscriminatorMapping }, children: [] }` error with no `value` key.
- Request and response discriminator values resolve against own `discriminator.mapping` keys only; inherited names such as `constructor`, `toString`, or `__proto__` are unknown values. Mapping/type config errors are checked before payload resolution and stay server errors, never client validation errors.
- Transformation errors (class-transformer failures and any `HttpException` or other error thrown by a consumer `@Transform`) bypass `exceptionFactory` and propagate unchanged, as with Nest `ValidationPipe`; a non-HTTP error becomes a generic 500.
- Discriminator messages never echo the rejected value: `channel has invalid discriminator value. must be one of: 'email', 'username'`. The nested `MustMatchOneOfSchemasValidator` (`ApiPropertyObject` discriminators) follows the same rule: `<prop> has invalid discriminator value for field '<field>'. must be one of: ...`. Generated CRUD routes keep using the host `ValidationPipe` for bodies and untyped queries; their PARAMETERS DTO is enforced by Crud Automator.

Custom route caveats:

- Request relation hydration currently targets the body argument.
- Response relation reload uses `controller.service.get({ where: { id } })`.
- Response relation reload requires `controller.service instanceof ApiServiceBase`.
- If `response` is provided, include the required `type` and `status`.

Generated request relation caveats:

- `relations.request.load.include` selects the direct request body relations to hydrate. Every include and lock key must be a relation declared on the route entity or a parent class, checked at decoration on every enabled route and `@ApiRouteCustom`, with the lock, reference, and shape rules; nested keys and services are checked at application bootstrap. On a table-inheritance root a key declared only on a child entity fails startup naming the key, root, and child.
- `relations.request.load.services` is only an override map; omitted keys use `<relationName>Service` properties on the controller.
- `relations.request.load.relationLoadStrategy` is passed to the direct relation service get call alongside nested TypeORM `relations` when configured.
- `relations.request.load.locks` forwards native TypeORM `pessimistic_read` or `pessimistic_write` to enabled direct relation `get()` calls and requires an active Automator transaction.
- Direct relation locks follow `include` declaration order and disable implicit eager-relation loading. Locked direct relations with explicit nested includes require `relationLoadStrategy: "query"` so nested reads share the manager without receiving an automatic lock.
- Request relation hydration mutates direct relation references into loaded entity objects. Nested include objects are passed to the direct relation service as TypeORM `relations`; nested request references are not recursively hydrated.
- Scalar relation values are an HTTP/controller contract; generated service inputs remain entity-based.
- Response reference projection supports destructive `OBJECT` and `SCALAR` shapes only; there is no `FULL` or `PRESERVE` mode.
- Mandatory generated reads force an own `cache: false`. If requested relations use effective TypeORM `relationLoadStrategy: "query"` while the data-source query cache has `alwaysEnabled: true`, the call fails before repository I/O because relation subqueries cannot inherit that root cache bypass. Use join loading or disable the global always-on cache.
- On PostgreSQL and CockroachDB, GET, GET_MANY, and GET_LIST reads of an entity whose primary key includes a `timestamptz`, `timestamp`, or `date` column, paged and joined through `include`, eager relations, or relation filters, run a distinct key query that reads the keys as text and an entity query that binds that text; TypeORM's own two-step load would bind the parsed `Date` keys, which pg truncates to whole-minute offsets. Such a page orders only by entity columns. The key query, entity query, and count share one query runner (the transaction's when present). On PostgreSQL and CockroachDB, every `Date` compared with a column whose driver-normalized type is `timestamptz`, from filters, scopes, keys, or a service caller's where clause, binds as canonical UTC text when the read runs, as does a `Date` a transformer returns for another operand: the column transformers run once on every operand of the condition, in order, also inside `And`, `Not`, `In`, and `Between`, and the bound operator keeps TypeORM from running them again; other drivers bind what the transformers return, and on every driver a composed condition such as `And` or `Not` on a transformed `timestamptz`, `timestamp`, `datetime`, or `date` column runs the transformers once on each operand, so a client filter and a scope on one such column combine; an invalid `Date` fails before query I/O. A client date-time filter value is the UTC instant `YYYY-MM-DDTHH:mm:ss.sssZ` on every column, a calendar `date` field takes `YYYY-MM-DD`, and a `time` field takes `HH:mm:ss`, each naming a day of a year from 0001 to 9999 that exists (`2024-02-30` and `25:00:00` fail); this holds on every GET_LIST route, default routes and relation paths included, any other string, an offset or a zone-less date-time included, answers `400 FILTER_NOT_VALID` (the value of `isnull` and `notnull` is not checked). With effective `relationLoadStrategy: "query"`, every requested relation of an entity with a temporal primary key, and any relation whose join columns on either side are temporal, fails at every nesting level. A to-many `@RelationId` or `loadRelationIds` relation fails under the same conditions on every strategy, for the read entity and every entity its eager or requested relations reach. An entity a `"query"` relation loads joins its eager relations whatever `loadEagerRelations` says, so they count too. These fail at application bootstrap for every generated route that is not disabled, listed in `routes` or not, and for its request relation loads, and before query I/O otherwise; the error names the relation load, the bound column, and `relationLoadStrategy: "join"`, and goes to the error log as well. MySQL limits: mysql2 truncates `DATETIME(4)`–`DATETIME(6)` to milliseconds and shifts local times inside a DST gap of the process zone.
- For generated routes, request relation hydration reads relation fields from the request body for CREATE, UPDATE, and PARTIAL_UPDATE. It does not hydrate GET/DELETE route parameters.
- CREATE always reloads the created entity through `service.get(...)`, including configured response relations when present. UPDATE/PARTIAL_UPDATE reload only when response relation loading is configured. DELETE returns no body. PAGE GET_LIST maps required `limit`/`page` to `take`/`skip` and calls `getList`; CURSOR GET_LIST maps required `limit` plus optional `after`/`before` to `getMany` window/probe queries. Both modes use the configured normalized filter/order plan. Without client order they apply `defaultOrder` plus tie-breakers; with client order they replace defaults and append de-duplicated tie-breakers.

## Error String Codes

- Every rejected value code has one form, `{NAME}_NOT_VALID`. There are no `INVALID_*`, `WRONG_*`, `MALFORMED_*`, or `BAD_{property}` values; do not add them.
- `ErrorString({ entity, property, type: EErrorStringCompositeAction.NOT_VALID })` gives `USERENTITY_EMAIL_NOT_VALID`; `FORMAT_NOT_VALID` gives `USERENTITY_EMAIL_FORMAT_NOT_VALID`. `ErrorString({ entity, type: EErrorStringAction.PASSWORD_NOT_VALID })` gives `USERENTITY_PASSWORD_NOT_VALID`.
- `VALIDATION_ERROR` is for a failed rule that spans the request or several fields.
- Package codes: `FILTER_NOT_VALID`, `ORDER_NOT_VALID`, `CURSOR_NOT_VALID`, `LIMIT_NOT_VALID`, `PAGE_NOT_VALID`, `{ENTITY}_REFERENCE_NOT_VALID`. They were `INVALID_*` before 5.0.0.
- `TIMESTAMP_IN_FUTURE` renders as `{ENTITY}_TIMESTAMP_IN_FUTURE`; every `EErrorStringAction` value is its key, with or without the `{entity}_` prefix.
- `IApiRequestValidator.errorType` accepts `EErrorStringAction` only, so no composite value works there. To return a property-level code from a validator, throw it from `validationFunction`.

## Subscriber Contexts

Route before create result shape:

```ts
{
	authenticationRequest?: IApiAuthenticationRequest;
	body: DeepPartial<E>;
	headers: Record<string, string>;
	ip: string;
}
```

When a route subscriber only observes routes that guarantee authorization, use `EApiRouteSubscriberAuthorizationExpectation.REQUIRED` in both `@ApiRouteSubscriber({ authorization: { expectation } })` and the `ApiRouteSubscriberBase`/before-context generics. That narrows `context.result.authenticationRequest.authorizationDecision`; it does not add runtime guards.

Function before create result shape:

```ts
DeepPartial<E>;
```

For `onBeforeUpdate`, use `context.DATA.currentEntity: Readonly<E>` for the existing entity and keep `context.result` as the update patch. Automator resolves the transaction, runs one ordinary decorated GET through the active manager repository when a transaction exists or the service base repository otherwise, creates a top-level detached and frozen shallow snapshot, invokes UPDATE before-hooks, and merges their returned patch into the internal loaded entity without another explicit GET. Nested snapshot values retain aliases to that internal entity and can affect persistence if mutated; no row lock is added. A missing row keeps GET error lifecycle, skips UPDATE before-hooks, and then enters UPDATE error lifecycle.

For other function before-hooks, use `context.DATA.criteria`, `context.DATA.properties`, repository lookups, or TypeORM options when an existing entity or criteria is needed.

Function subscriber transaction expectations are subscriber-declared:

- Use `@ApiFunctionSubscriber({ transaction: { expectation: EApiFunctionSubscriberTransactionExpectation.REQUIRED } })` or `MANDATORY` only when the hook cannot run without `context.DATA.eventManager`.
- Pass the same expectation to `ApiFunctionSubscriberBase` and helper context generics to narrow `eventManager` to `EntityManager`.
- Do not infer subscriber transaction requirements from `@ApiService`, `@ApiFunctionCustom`, or `@ApiFunctionStep`; subscribers without metadata keep optional `eventManager`.

Post-transaction function subscriber lifecycle:

- `onAfterCommit` and `onAfterRollback` run once per matching subscriber after the outer owner has completed the database transaction.
- `context.DATA.transaction` contains the UUID and immutable `FUNCTION`, `ROUTE`, or `SCOPE` owner.
- `context.DATA.events` contains the full ordered trace; `matchedEvents` contains only events that selected that subscriber.
- Transaction events contain metadata only, never arguments, bodies, entities, or results.
- STEP events remain trace-only and never select subscribers.
- `onBeforeErrorCommit`/`onBeforeErrorRollback` receive raw failures; `onAfterErrorCommit`/`onAfterErrorRollback` receive normalized transaction exceptions.
- `ApiFunctionTransactionScope.runWithDataSource(dataSource, { name }, callback)` owns a named transaction and passes its `EntityManager` to the callback; `runWithEntityManager` only joins an existing Automator owner. Inside an active Automator transaction on the same `DataSource` it joins and refuses an `observation`; on another `DataSource` it runs on its own and does not roll back with the active one.
- `ApiFunctionTransactionPostCommitException` means `COMMITTED`. `ApiFunctionTransactionCommitUnknownOutcomeException` means `UNKNOWN`, still invokes commit-error lifecycle, and invokes neither post-commit nor post-rollback. A clean confirmed rollback rethrows the original operation error; `ApiFunctionTransactionRollbackException` is reserved for additional rollback, hook, or rollback-error lifecycle failures and preserves that operation error.

For generated CRUD before hooks, `context.result` includes request targets plus `authenticationRequest`, `headers`, and `ip`. For `@ApiRouteCustom`, `context.result` is only `{ body?, parameters?, query? }`; read `authenticationRequest`, `headers`, `ip`, route metadata, and runtime properties from `context.DATA`.

## Named Owner Execution Observation

`runWithDataSource(dataSource, { name, observation }, callback)` accepts `IApiFunctionTransactionObservationOptions` from the package root:

- `selectors`: up to 32 entries with `entity` constructor identity, `functionType` (native CRUD/CUSTOM or STEP) and exact `methodName`. Method names must be nonblank and at most 256 characters. Duplicate tuples reject before query-runner I/O. Selectors and `onSettled` are copied before any await; an empty selector list is valid.
- `onSettled`: bounded synchronous capture receiving `Readonly<IApiFunctionTransactionObservationSnapshot>` once after the best-effort release attempt, context teardown and terminal lifecycle, including hook failure. Failed startup and rejected nested owners do not deliver a snapshot. Synchronous throws and accidental asynchronous rejections are isolated; delivery is never awaited.
- `measurements`: at most 256 immutable records containing only `selectorIndex`, `durationMs` and `EApiFunctionTransactionEventStatus`. Capacity is reserved at invocation start, including concurrent work. Records follow invocation order; late completions after settlement are ignored.
- `outcome`: existing `COMMITTED`, `ROLLED_BACK` or `UNKNOWN`, independent of each execution status. A successful callback followed by failed commit stays successful in its measurement and has owner outcome `UNKNOWN`.
- `droppedCount`: omitted selected intervals, including capacity overflow, incomplete execution at settlement and invalid/unavailable clocks; saturates at the maximum safe integer. Do not silently treat a truncated snapshot as a complete sample.

The measured interval is the actual native callback after its own event registration and before its completion bookkeeping. It includes STEP context creation, CUSTOM subscribers and nested operations. Intervals overlap and cannot be summed; they are not isolated method-body, SQL or database-lock-wait duration. Mode preflight and unselected execution do not produce measurements. No observation clock is read when disabled or unmatched.

Observation is a separate diagnostic projection. It neither expands the ordinary event ABI nor alters pending-event errors, subscriber selection, transaction ownership or financial semantics. STEP remains trace-only. `runWithEntityManager` and nested joining functions use their existing owner; they cannot install another observer. No raw errors, UUIDs, managers, arguments, results or entity instances enter the output. The limits are exported through `API_FUNCTION_TRANSACTION_OBSERVATION_CONSTANT`. A synchronous capture callback still contributes request latency; transport and buffering remain application responsibilities.

## Authorization Notes

- Generated CRUD route actions map to the authorization runtime automatically.
- Custom route action identity is `metadata.resource.action` for `@ApiMethod` and `resource.action` for `@ApiRouteCustom`.
- On a securable controller, startup checks each custom route, declared or inherited, for `resource.action` and a `resource.entity` equal to the controller entity. The closest definition of a method name is the one checked. A route without `security.authorization.mode` runs in `authorization.defaultMode`, and the resolved mode selects the prerequisites: a route that resolves to hooks needs a registered policy, a route that resolves to IAM needs the IAM configuration.
- Custom `@ApiMethod(...)` and `@ApiRouteCustom(...)` routes without `metadata.route.type` do not dispatch to CRUD policy hooks; handle them in `getCustomActionRule(action, context)` and branch on the declared `resource.action`.
- Every handler Nest serves on a securable controller goes through authorization, or startup fails naming the controller, method, and path. A plain Nest route refuses to start, including one inherited from a base class and a plain override of a generated or custom route. An override with no route decorator and helper methods are not routes. Route metadata written by hand also needs `ApiAuthorizationGuard` or a subclass of it in `@UseGuards` on the method or the controller; a guard instance and `APP_GUARD` do not count. A `@MessagePattern`, `@EventPattern` or `@SubscribeMessage` handler refuses to start as well, with or without `@ApiMethod`, because a microservice or WebSocket transport has no identity that authorization can trust: the caller writes the payload the guard would read as the request, `user` included. So does a handler replaced on the instance by a function without its authorization, because Nest takes guards from that function. Route metadata without `route` refuses to start. `@ApiControllerSecurable` attaches a guard to the class, which applies the same rule per request in every scope, denies everything on a transport other than HTTP, a securable gateway included, and evaluates no policy. An application with a securable controller and no `ApiAuthorizationModule` also fails startup, on a bare `@Controller` and a request-scoped controller too; with a generated or `@ApiMethod` route Nest fails first with its dependency error. A test harness imports the module and overrides `ApiAuthorizationBootstrapValidationService` and `ApiAuthorizationRuntime`, which turns off the startup checks. The replaced `evaluate` returns a complete `IApiAuthorizationDecision` built with the enums (`EApiPolicyEffect.ALLOW` is `"Allow"`) and with `transforms: []`: a generated route runs the decision's `transforms` on the response, so `{ effect: "allow", principal: { id: "test" } }` answers `500`. Return `EApiPolicyEffect.DENY` to test a `403`. See the authorization guide, Test Harness.
- `resourceDefinition.resourcePath` may contain placeholders like `{id}`.
- Policy statement `Resource` values should be concrete strings or wildcard strings such as `gameport:admin:item/*`.
- Omitted authorization cache configuration means `EApiAuthorizationCacheMode.SOURCE_FIRST`: each evaluation re-reads hooks permissions, IAM attachments, and requested IAM documents, and does not read or populate cross-request resolver maps.
- Source-first errors propagate; the resolver never falls back to a previously successful value. Duplicate permissions, attachments, and document IDs are still collapsed inside one resolution.
- `MEMORY` requires explicit positive safe-integer `ttlMs` and `maxEntries`, is bounded independently per resolver cache, and is local to one process.
- `ApiAuthorizationCacheInvalidationService.clearAll()` clears policy, IAM attachment/document, and hook permission caches. Resolver entries exist only in memory mode; policy-rule caching is a separate default-disabled option and requires invalidation whenever enabled rules change.
- There is no arbitrary immutable controller `baseWhere`. `read.scope.parameters` is limited to request-bound inherited path values; fixed and principal-dependent restrictions belong in HOOKS/IAM scope.
- IAM conditions accept only `EApiPolicyConditionOperator` values with scalar operands. Allow `resource.*` keys compile for `StringEquals`/`StringEqualsIfExists` on `isFilterable` fields; matched Deny `resource.*` keys compile for all four operators into negated OR branches that keep exactly the rows the in-memory evaluator allows (`StringEquals`/`StringEqualsIfExists` → `<> value OR IS NULL`, `StringNotEquals`/`StringNotEqualsIfExists` → `= value`) ANDed with the Allow scope. The planner resolves each `queryPath` through TypeORM metadata at every step (relations of any depth, embedded entities, parent-class and single-table-inheritance columns); a path that does not end on a mapped column does not compile, and neither does any key of a resource entity no TypeORM decorator maps (`EntitySchema` only). On a boolean column (TypeORM type `boolean`/`bool`/`bit`, a bare `@Column()` on a `boolean` property, or described `BOOLEAN`; no describe needed) only `true`, `false` or that exact text compiles, bound as a boolean, in conditions and exact row-scoped Deny patterns (`bool:item/true` for `{isFeatured}`); any other value (`"1"`, `"TRUE"`, `"yes"`, `1`) does not compile. A list, object or `null` operand logs a warning at document load and fails closed: the key fails for an Allow and holds for a Deny, whose other keys still decide whether it matches (never `500`). Values that are `""` or resolve to `null`/`""`, non-compilable Deny keys, scopes over `AUTHORIZATION_IAM_SCOPE_CONSTANT.MAX_WHERE_BRANCHES`, and `resource.*` Deny on CREATE (or a `<namespace>:create` custom action) are an explicit deny. On list requests (GET_LIST or a `<namespace>:list` custom action), a Deny with a row-specific `Resource` compiles to `field <> id` or an escaped `NOT LIKE 'prefix%'` (STRING-described fields only, excluding the BIGINT_STRING and UUID formats), both keeping NULL placeholders; unmappable patterns are an explicit deny. Custom routes get the merged result in `decision.scope`.
- Array-form authorization `where` values are OR branches and must be non-empty arrays of non-empty plain objects. `AuthorizationScopeMergeWhere` rejects `[]` and empty branches before TypeORM instead of treating them as an unconstrained query. It normalizes scalar leaves to exact `Equal(...)` predicates whenever another scope is merged; use an explicit `Equal(value)` for JSON/JSONB, geometry, or another object-valued scalar.
- Generated service functions check every `where` before TypeORM with `DatabaseTypeOrmAssertEffectiveWhere` (`getList`, `getMany`) or `DatabaseTypeOrmAssertRequiredWhere` (`get`, and through it `update` and `delete`, plus the PATCH write and reload). `undefined`/`null` values, empty relation objects, empty OR arrays and empty OR branches throw; single-row calls also throw on a missing or empty `where`. The error maps to `InternalServerErrorException`.

## Peer Ranges

- Every peer dependency has an upper bound at the next major (next minor for 0.x lines): `@nestjs/common` and `@nestjs/core` `>=12.3.2 <13`, `@nestjs/swagger` `>=12.0.0 <13`, `@nestjs/throttler` `>=6.7.1 <7`, `typeorm` `>=1.1.2 <2`, `class-transformer` `>=0.5.1 <0.5.2` (the package reads its `cjs/storage.js`), `class-validator` `>=0.15.1 <0.16`, `lodash` `>=4.18.1 <5`. NestJS 11, Swagger 11 and TypeORM 0.3 need 4.x.
- The package is ESM-only: one build in `dist`, `exports["."]` with `types` and `default`, plus top-level `main` and `types` for `node10` resolution. TypeScript 6 resolves `module: commonjs` without `moduleResolution` as `bundler` (types from `exports`); an explicit `node10` uses the top-level `types` and needs `ignoreDeprecations: "6.0"`. TypeScript 6 defaults `types` to `[]`. CommonJS consumers use `require()` through Node.js `require(esm)`. Every relative import in `dist` (`.js` and `.d.ts`) carries a `.js` extension; `rollup.config.js` adds it to declarations and `scripts/check-declaration-imports.cjs` fails the build otherwise.
- `npm run test:consumer` (`scripts/test/consumer-smoke.mjs`) packs the build, installs the tarball with the peer stack into a temporary project and typechecks and runs `test/consumer/app` and `test/consumer/cyclic` (entities that import each other through `Relation<T>`) as four consumers: ESM `bundler`, ESM `nodenext`, CommonJS `node10` and CommonJS without `moduleResolution`, both CommonJS ones through `require(esm)`. The app covers CRUD with function and route subscribers, an eager owner relation, an IAM 403, a HOOKS policy with owner scope, a typed filter merged with that scope, PAGE and CURSOR pagination, the Swagger document and `close()`. A fifth consumer, `test/consumer/swc`, is the native ESM setup of Core and Gameport: its own app with extensionless `@`-alias imports and author/book entities that import each other through `Relation<T>`, built by SWC (`@swc/cli` and `@swc/core` pinned in the runner, `module.type: es6`, `resolveFully`, `jsc.paths`), typechecked by `tsc --noEmit` with `bundler` and `skipLibCheck: false`, and called over a socket. The app registers `CorrelationIDResponseBodyExceptionFilter`, and the runner fails if the project has `@nestjs/microservices`, `@nestjs/websockets`, `@nestjs/platform-socket.io` or `socket.io-client`, so the `dist` filter is proved to load without them. It uses `DATABASE_URL` or starts a testcontainers Postgres. The CI `consumer-smoke` job runs it on Node.js 22.13.0, 24.11.0 and 26.x. Run it after changing `package.json` exports, `rollup.config.js` or the peer ranges.
- `engines.node` is `^22.13.0 || >=24.11.0` (TypeORM 1's range). CI runs the full suite on the latest 22.x, 24.x and 26.x.
- `docs/guides/migrating-to-5-0` lists every 5.0 breaking change with links to each page's Migration Notes. Add a section there for any new breaking change before 5.0.0 is released.
- CI installs every peer at the latest release inside its range; `@nestjs/swagger` also runs against 12.0.0. The consumer smoke on Node.js 22.13.0 also runs with `--peer-floors`, which installs every peer at the `>=` floor of its range and fails when an installed version differs.
- `@nestjs/passport`, `@nestjs/platform-fastify`, and `fastify` are not peers: `dist` imports none of them (`fastify` appears only as `import type` in `src`). `CorrelationIDResponseBodyInterceptor` needs the Fastify adapter. Upgrading an installed peer past its range exits 0 with `npm warn ERESOLVE overriding peer dependency` and leaves `npm ls <peer>` `invalid`; adding Automator after such a peer fails with `ERESOLVE`. Install peers with explicit ranges.
- `dist` imports a package only when it is in `dependencies` or `peerDependencies` (or a `node:` builtin), and only through its root or an explicit, non-wildcard key of its `exports` map; packages without an `exports` map need an allowlist entry (`lodash/<name>.js`). `scripts/check-declaration-imports.cjs` checks every `.js` and `.d.ts` after the build and fails otherwise, so `@nestjs/swagger/dist/*`, `@nestjs/common/constants.js`, `typeorm/metadata/*` and undeclared packages never ship. Nest internals come from `@nestjs/common/internal` and `@nestjs/core/internal`. `rollup.config.js` keeps every `dependencies` and `peerDependencies` package and its subpaths external, and the check fails when one of them appears under `dist/external`; only build helpers such as `tslib` are bundled. The same check parses every `dist` `.js` file (comments and JSDoc excluded) and fails on member access on the global `console` or `process.stdout`/`process.stderr`, `process.loadEnvFile` or a call to the global or `node:process` `loadEnvFile`, a `dotenv` import or a `.env` path; names are resolved, so a local, parameter, object key or method named `console` or `loadEnvFile` passes. It does not follow `globalThis.console`, aliases, a destructured `process` or a default import of `node:process`, and `test/unit/check-declaration-imports.test.ts` covers each case: the package logs only through `LoggerUtility` and reads only `process.env`. `dist` has no source maps (`sourcemap: false`; they would point at the unpublished `src`), and the check fails on a `.map` file or a `sourceMappingURL` comment.
- `TSwaggerComponentSchema` (one `components.schemas` entry), `TSwaggerHeadersObject`, `TSwaggerReferenceObject`, `TSwaggerSchemaObject`, and `TSwaggerSecurityRequirementObject` are derived from the public `OpenAPIObject` type and exported from the package root.
- `multipleOf` on a numeric query parameter sits inside its `schema` (Swagger behavior from 11.4.3).
- `SWAGGER_METADATA_CONSTANT` (`src/constant/swagger`) is internal and holds the Swagger metadata keys Automator reads and writes. Those strings are Swagger internals, so CI runs the unit suite and two Swagger e2e files (`swagger.e2e.test.ts`, `typed-query-swagger.e2e.test.ts`) against 12.0.0 and the latest 12.x.
- `path-to-regexp` stays on 8.x, the release `@nestjs/core` 12 pins, so route paths are parsed the way Nest matches them.
- TypeORM 1: use `manager.dataSource` (not the deprecated `connection`); the `sqlite` driver is gone (tests use `better-sqlite3`); `PostgresDataSourceOptions` replaces `PostgresConnectionOptions`; `select` and `relations` take objects, not arrays; the find option `join` is removed.
